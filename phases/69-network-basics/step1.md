# Step 1: lecture-outline

## 배경

앱에 두 번째 과목 **네트워크**를 더하는 phase 69의 둘째 step이다. 사용자 결정(2026-10-26·10-27, 다시 묻지 마라):

- 출처는 셋이다. **강의 슬라이드**(패스트캠퍼스 「현실 세상의 컴퓨터공학 지식 with 30가지 실무 시나리오」 Course 1 Part 3 네트워크, 5장 32강)가 범위와 순서를
  정하고 사실도 준다. **표준 문서**(IETF RFC, IANA, IEEE 802, ITU-T X.200, MDN)가 설명을 채우고 오류를 고친다. **기술면접 Q&A 21~40번**은 사실 출처로 쓰되 틀리면 고친다.
- 주제는 **강의 순서대로 22개**다. 실습 강의(Ch1-3 와이어샤크, Ch3-4·Ch4-4 패킷 분석, Ch4-2 포트 확인, Ch5-7 HTTP 요청·응답 확인)는 주제로 두지 않는다.
- 자격증 목표가 정해지지 않아 별점은 비운다. 도식은 처음부터 함께 만든다. 문항은 4지선다와 예/아니요(ADR-054).

step 0이 원본을 뽑아 두었다. `docs/source/network/raw/lecture.md`가 강의 32강의 글자이고, 쪽 머리 `## p{n}`의 n이 **통합본 쪽 번호**다.
글자가 거의 없는 쪽에는 머리 끝에 ` — 그림 슬라이드`가 붙어 있다. 슬라이드는 글이 적고 핵심이 그림·표에 있다.

**이 step은 강의 32강을 직접 쓴 말로 정리한 `docs/source/network/lecture-outline.md`를 쓴다.** 그 안에 주제 지도와 강의 수정 이력을 둔다.
수정 이력의 근거가 되는 표준 문서 사실은 새 파일 `docs/source/network/standards.md`에 URL과 함께 적는다. 앞으로 모든 네트워크 phase가 이 두 문서를
범위와 근거의 기준으로 읽는다.

## 작업

### 1. 그림 슬라이드 보기

- ` — 그림 슬라이드` 표지가 붙은 쪽 가운데 **실습 강의가 아닌 강의**의 쪽은 렌더해서 무엇을 보이는지 확인한다. PyMuPDF로
  `docs/source/network/raw/pdf/lecture-merged.pdf`를 연다. 렌더 결과는 `docs/source/network/raw/render/`에 둔다(gitignore 안).
- 쪽 하나씩 보면 양이 많다. **여러 쪽을 한 장에 모아(예: 3×3) 렌더해서** 본다. 새 PDF 쪽에 `show_pdf_page`로 슬라이드를 칸마다 넣고 그 쪽을 PNG로 저장하면 된다.
  모은 장마다 어느 쪽들인지 파일 이름에 적는다(`p032-p040.png`).
- 실습 강의는 한두 장만 보고, 화면 캡처뿐이면 그렇다고만 적는다.
- 글자가 있는 쪽도 표·그림이 핵심이면(예: IPv4 헤더 그림, TCP 상태 전이도, DNS 질의 그림) 렌더해서 본다.

#### 2-2. 강의별 정리

강의마다 절 하나 — `## Ch1-1 네트워크 거시적으로 보기 (p1–p18) → network-basics`. 그 아래:

- 강의가 가르치는 것을 **직접 쓴 말로** 글머리 기호로 적는다. 항목마다 근거 쪽 `p6`을 붙인다. 정의, 구성 요소, 예시 값, 비교, 순서가 빠지지 않게 한다.
  뒤 phase가 이 문서만 읽고도 그 강의가 무엇을 다루는지 알 수 있어야 한다.
- 그림 슬라이드는 그림이 보이는 것을 적는다 — 「p32–p34: 응용 계층에서 내려온 데이터에 전송·인터넷·네트워크 액세스 계층이 차례로 헤더를 붙이는 그림.
  네트워크 액세스 계층은 트레일러도 붙인다」처럼. 그림 속 예시 값(주소·포트·숫자)도 적는다. 뒤의 도식이 이 값을 예시로 쓸 수 있다(ADR-038의 「본문에 있는 예시만」).
- 강의가 링크한 외부 페이지(위키백과·Cloudflare 등)는 「강의가 가리킨 곳」으로 이름만 적는다. 거기서 사실을 가져오지 않는다.
- 실습 강의는 한 줄 — 무엇을 하는지, 주제 없음.

#### 2-3. 강의 수정 이력

강의의 주장이 표준 문서와 다르거나, 오해를 부르게 줄여 말한 곳의 기록이다. 항목마다 번호(`L1`, `L2`…), 강의 쪽, 강의가 말한 것의 요지(직접 쓴 말),
표준이 말하는 것(직접 쓴 말), 근거(문서와 절, URL), 처리(고쳐 쓴다 / 쓰지 않는다 / 한정해 쓴다)를 적는다. **표준 문서를 실제로 열어(WebFetch) 확인한 것만** 적는다.

아래는 설계 때 찾은 후보다. **하나씩 표준으로 확인하고**, 맞으면 기록하고, 표준이 강의 편이면 「확인 결과 강의가 맞다」로 남긴다. 읽다가 다른 곳을 찾으면 더한다.

| 후보 | 강의 | 강의가 말한 것 | 확인할 표준 |
|---|---|---|---|
| a | Ch2-1 이더넷 프레임 | 이더타입/길이 필드 값이 1500 이하면 「프레임 크기」 | 1500 이하일 때 담기는 것은 데이터(페이로드) 길이인지 — IEEE 802.3, RFC 9542 |
| b | Ch2-1 MAC 주소 | NIC마다 할당된 고유한 주소, 「주민등록번호」 비유 | MAC 주소를 바꿀 수 있는지(로컬 관리 주소) — IEEE 802, RFC 9542. 비유는 쓰지 않는다 |
| c | Ch3-1 IPv6 주소 | 「할당 가능한 IPv4 주소 개수 == 2^128」 | 오타(IPv6) — RFC 8200, RFC 4291 |
| d | Ch3-6 NAT | NAT가 「IP 주소 부족 문제 해결」 | 해결인지 완화인지 — RFC 3022, RFC 1918 |
| e | Ch4-3 UDP | 「IP 패킷을 감싸는 껍데기일 뿐」, 「체크섬 필드는 신뢰성과는 관련이 없다」 | UDP 체크섬은 손상을 검출한다. 복구(재전송)는 하지 않는다. IPv4에서는 선택, IPv6에서는 필수 — RFC 768, RFC 8200 |
| f | Ch4-3 UDP를 쓰는 것 | HTTP/3, NTP, RIP, DNS, DHCP | DNS가 TCP도 쓰는지 — RFC 7766. 정정이 아니라 한정 |
| g | Ch4-7 빠른 재전송 | 「중복 세그먼트가 수신되면」 재전송 | 조건은 중복 ACK 세 개 — RFC 5681 |
| h | Ch4-7 TCP 오류 제어 | ARQ 세 방식(Stop-and-Wait, Go-Back-N, Selective Repeat)을 TCP의 오류 제어로 소개 | TCP가 그중 어느 하나와 같다고 말할 수 있는지 — 누적 확인 응답과 SACK 옵션, RFC 9293, RFC 2018 |
| i | Ch4-8 혼잡 제어 | 임계치를 「sshresh」로 표기, 혼잡 회피에서 「세 번의 중복 세그먼트」면 빠른 회복 | 이름은 ssthresh, 조건은 중복 ACK 세 개, 빠른 회복에서 ssthresh·혼잡 윈도우를 어떻게 정하는지, 타임아웃이면 어떻게 되는지 — RFC 5681 |
| j | Ch5-1 DNS 레코드 | SOA 레코드는 「도메인에 대한 관리자 정보」 | SOA가 담는 것 — RFC 1035 |
| k | Ch5-2 URL | `mailto://John.Doe@example.com`, 쿼리는 「key:value 형태」 | mailto는 `//` 없이 `mailto:…` — RFC 6068, RFC 3986. 쿼리의 이름=값 꼴은 표준이 정한 것인지 관례인지 — RFC 3986, MDN |
| l | Ch5-4 HTTP의 특성 | 「비연결성 프로토콜」과 「지속 연결 프로토콜」을 함께 나열 | HTTP/1.1은 지속 연결이 기본이고 HTTP/1.0은 응답 뒤 연결을 닫는 것이 기본이었는지 — RFC 9112, MDN |
| m | Ch5-5 HTTP 메시지 | 요청의 시작줄(메서드·대상·버전)을 「응답 헤더」 제목 아래, 응답의 시작줄을 「요청 헤더」 제목 아래 둠 | 요청줄·상태줄 — RFC 9112 |

### 3. `docs/source/network/standards.md`

표준 문서에서 가져온 사실의 목록이다. `docs/source/aws-docs.md`처럼 문서마다 절 하나:

```
## RFC 768 — User Datagram Protocol
https://www.rfc-editor.org/rfc/rfc768

- (직접 쓴 사실 한 줄) — §절 번호
- …
쓰인 곳: 강의 수정 이력 e
```

- 머리말에 이 파일의 규칙을 적는다 — 허용 도메인(`docs/source/network/CLAUDE.md`와 같다), 사실은 직접 쓴 말로, 절 번호를 붙인다, 「쓰인 곳」에 수정 이력 번호나
  개념 id를 적는다(뒤 step이 개념을 만들면 개념 id를 더한다).
- 이 step은 **수정 이력이 쓰는 사실만** 넣는다. 개념 본문용 사실은 각 주제 step이 필요할 때 더한다.
- RFC는 `https://www.rfc-editor.org/rfc/rfcNNNN` 꼴의 URL을 쓴다. 폐기된 RFC(예: RFC 2616, RFC 7230~7235)가 아니라 지금 유효한 것(RFC 9110·9111·9112)을 쓴다.

## 검증 절차

1. AC를 실행한다. 강의 절이 32개, 주제 지도 행이 22개여야 한다. 수정 이력 항목이 보여야 하고 `standards.md`의 절이 1개 이상이어야 한다.
2. **전사 검사**(`scripts/check-verbatim.mjs`는 아직 개념 데이터만 대조하므로 이 문서에는 쓸 수 없다): `lecture-outline.md`의 각 줄을 `raw/lecture.md`와 대조해 공백·문장부호를 지우고 32자 이상 연속으로 같은 구간이 있는지 확인한다(일회성 스크립트는
   저장소 밖 임시 폴더에 두고 끝나면 지운다). 한글이 없는 구간(주소·헤더 이름 나열)은 넘긴다. 걸리면 직접 쓴 말로 고친다.
3. 수정 이력의 근거 URL을 하나씩 다시 열어 절 번호가 맞는지 본다. 열 수 없었던 것은 「확인 못 함」으로 표시하고 처리를 「쓰지 않는다」로 둔다.
4. `git status`로 바뀐 파일이 `docs/source/network/lecture-outline.md`, `docs/source/network/standards.md`와 phase 메타데이터뿐인지 확인한다. `raw/render/`는 무시되어 나오지 않아야 한다.
5. `phases/69-network-basics/index.json`의 step 1을 갱신한다.
   - 성공 → `"summary"`에 두 파일, 렌더해서 본 쪽 수, 수정 이력 항목 수와 번호별 한 줄 요지(후보 a~o 각각의 결과 포함, 새로 더한 것 표시), `standards.md`에 넣은 문서 목록을 적는다.
   - WebFetch를 전혀 쓸 수 없어 표준을 하나도 확인하지 못하면 → `"status": "blocked"`, `"blocked_reason"`에 사유를 적고 멈춘다.

## 금지사항

- **강의 문장을 그대로 옮기지 마라.** 이유: 외부 강의 자료다. 커밋되는 문서에 원문이 들어가면 저장소를 공개할 때 원문이 공개된다(ADR-009). 슬라이드 문장은 짧아서 옮기기 쉽다.
- **위키백과·블로그·업체 페이지(Cloudflare 학습 센터 등)를 근거로 적지 마라.** 이유: 허용한 표준 문서가 아니다. 강의가 그 페이지를 링크했어도 같다.
- **강의가 다루지 않는 주제를 표준에서 끌어와 적지 마라.** 이유: 범위는 강의가 정한다(사용자 결정).
- **주제 지도 표의 id·제목·순서를 바꾸지 마라.** 이유: 사용자가 승인한 구성이다. 이상해 보이면 `"summary"`에 적는다.
- **`src/`·`docs/*.md`를 고치지 마라.** 이유: 이 step은 원본 문서만 만든다. ADR과 PRD는 step 5가 쓴다.
- 확인하지 못한 수정 후보를 「확인함」으로 적지 마라. 이유: 수정 이력은 뒤 step이 개념 본문을 고칠 근거다.
- 기존 테스트를 깨뜨리지 마라.

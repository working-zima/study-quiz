# phase 81 공통 안내 — Windows Server의 서버 역할, Hyper-V와 Windows 컨테이너

이 phase의 **모든 step이 먼저 읽는 문서**다. step 문서는 자기 개념의 세부만 적고, 두 주제의 전체 개념 표와 글·문항·도식·파일 형식의 공통 규칙은 여기에 둔다.
step 문서와 이 문서가 다르면 step 문서를 따르고 그 차이를 summary에 적는다.

## 배경 — 다시 묻지 말 결정

- 네트워크 과목의 목표 자격증은 네트워크관리사 2급이고, 범위는 강의와 그 시험의 출제 범위가 정한다(ADR-059). 주제 지도와 별점은 `docs/source/network/topic-map.md`가 갖는다.
  이 phase는 그 지도의 **39번 `windows-server-roles`(Windows Server의 서버 역할, ★★☆, 출제 8/11회)와 40번 `windows-hyperv`(Hyper-V와 Windows 컨테이너, ★★☆, 8/11회)** 를 만든다.
  사용자가 2026-11-18에 자리를 비우며 이 phase를 멈추지 말고 끝까지 진행하라고 했다 — 이 설계(개념 23개·문항 29개·step 15개)는 미리 보이지 않고 실행하며, 끝 보고에서 함께 보인다. phase 80(`windows-ad`·`windows-admin-tools`)에 이은 Windows 주제다.
- **두 주제 모두 강의 밖 주제다**(phase 80과 같은 꼴). 사실의 출처는 **허용한 공식 문서 하나 — learn.microsoft.com**이다(Windows Server·IIS·Hyper-V·Windows 컨테이너·Windows 명령·PowerShell 문서).
  강의와 면접은 이 주제를 다루지 않으므로 근거로 쓰지 않는다. `sourcePages`는 둘 다 `[0, 0]`이다(ADR-059).
- 무엇까지 쓸지는 **기출이 묻는 사실과 그것을 이해하는 데 필요한 바탕**으로 정했다(ADR-059 「범위」). 기출 22문항(`windows-server-roles` 13·`windows-hyperv` 9)이 묻는 것은 이렇다.
  - `windows-server-roles`: 파일·프린터 서버로 쓰려면 있어야 하는 통신 규칙(TCP/IP — 오답 SNMP·SMTP·IGMP), DNS 서버 역할을 설치하다 생긴 문제를 고치는 방법(고정 IP 주소로 바꾸기 — `ipconfig /renew`는 맞지 않다, 지문이 그림),
    DHCP 범위 구성(서브넷 지연은 밀리초 단위 — 임대 기간의 단위, WINS 서버 옵션, 예약이 지원하는 유형은 오답 보기, 2회), DHCP 장애 조치의 MCLT(파트너 서버가 기존 임대를 잠시 늘려 줄 수 있는 최대 시간),
    IIS 관리자를 여는 명령(`inetmgr.exe`), IIS 사이트 등록 정보(TCP 포트는 시리얼 포트가 아니다 — IP 주소·연결 수 제한·연결 시간 제한은 맞는 말로 둔다), IIS가 하는 일(요청 필터링 — HTTPS·PHP·응용 프로그램 풀은 오답 보기),
    IIS 로그(저장 위치를 바꿀 수 있다 — W3C만 지원·실시간 기록·오래된 로그 자동 삭제는 틀린 말), IIS 관리자의 홈 디렉터리·기본 문서·디렉터리 검색·가상 디렉터리, FTP 서버 설치(서버 관리자의 웹 서버(IIS) 역할 서비스 — 서드파티 필요·SFTP·PowerShell 불가는 틀린 말),
    원격 액세스의 웹 응용 프로그램 프록시(내부 웹 자원을 인터넷에 게시 — 원격 컴퓨터를 네트워크에 잇지 않는다, 오답 PPTP·L2TP·SSTP, 2회).
  - `windows-hyperv`: Hyper-V의 성질(실행 중인 가상 하드 디스크를 다른 저장소로 옮길 수 있다 — 다른 서버로 복제할 수 없다·물리 서버 하나에 가상 컴퓨터 하나·쓸수록 하드웨어 사용률이 낮아진다는 틀린 말, 3회),
    Hyper-V로 얻는 것(하드웨어 사용률·유지 비용·개발과 테스트 — 가용성이 줄어든다는 틀린 말), Windows 컨테이너(지문이 그림 — 오답 Virtual Machine·IIS·Nano Server, 3회), 검사점(지문이 그림 — 오답 가상 스위치·새로 고침·내보내기·롤백·타임머신, 2회).
  공식 문서에 있다는 이유만으로 기출이 묻지 않는 것 — 서버 관리자의 원격 관리 전체, NIC 팀, 저장소 공간·데이터 중복 제거·DFS, 프린트 관리의 드라이버 격리, DHCP의 IPv6·정책·필터·DNS 동적 업데이트 설정 전체, IPAM,
  IIS의 인증 방식 전체·URL 재작성·ASP.NET 구성·공유 구성, FTP 사용자 격리 전체, DirectAccess·VPN의 배포 절차와 인증서 구성, AD FS의 동작,
  Hyper-V의 장애 조치 클러스터·SLAT 같은 하드웨어 요구 전체·세대 1과 2의 차이 전체·동적 메모리·중첩 가상화·차폐된 가상 컴퓨터, 컨테이너의 Dockerfile 문법·오케스트레이션(Kubernetes)·네트워크 드라이버 전체 — 를 끌어오지 않는다. 아래 표의 「다룰 것」이 범위다.
- **Windows의 판**: 기출은 Windows Server 2016과 2022를 적는다. 본문은 learn.microsoft.com의 지금 문서(Windows Server 2025까지)가 말하는 사실을 쓰고, 판마다 다르면 판을 밝힌다.
  기출이 옛 판을 전제로 묻고 지금 문서가 다르면 본문은 지금 문서를 쓰고 「자격시험은 ~로 본다」를 덧붙인다(ADR-059 — `exam-notes.md`에 그 항목이 있어야 한다).
  지금 판에서 더 개발하지 않거나 빠진 기능(예: 웹 응용 프로그램 프록시·DirectAccess·WINS가 「Features removed or no longer developed」 목록에 있는지)은 출처 step이 확인하고, 있으면 본문에 판과 함께 한 줄로 쓴다.
- **용어는 Microsoft의 한국어 표기를 쓴다** — 학습자가 한국어 화면과 기출에서 보는 이름(서버 관리자, 역할 및 기능 추가 마법사, 역할 서비스, 범위, 임대 기간, 예약, 장애 조치, IIS 관리자, 사이트 바인딩, 실제 경로, 가상 디렉터리, 기본 문서, 디렉터리 검색, 응용 프로그램 풀,
  요청 필터링, 원격 액세스, 웹 응용 프로그램 프록시, 가상 컴퓨터, 가상 스위치, 검사점, 실시간 마이그레이션, 복제본 등)을 세우고 영문 이름을 함께 적는다.
  learn.microsoft.com/ko-kr 문서는 기계 번역이 섞여 같은 것을 여러 이름으로 부르기도 한다(예: virtual machine을 「가상 머신」·「가상 컴퓨터」로, checkpoint를 「검사점」·「체크포인트」로) — 그럴 때는 그 문서가 **화면 이름으로 보이는 것**(마법사·메뉴의 이름)과 기출이 함께 쓰는 이름을 쓰고,
  어느 이름을 왜 골랐는지 `standards.md` 항목에 적는다. 출처 step(0·4·9)이 개념마다 정한다.
- 앞 phase가 만든 주제는 고치지 않는다. 이미 다른 주제에 있는 것 — DHCP와 그 메시지·임대·갱신·예약이라는 생각(`ip-address-types.dhcp`·`dhcp-messages`), DNS와 Windows DNS 서버(`dns`), FTP와 그 두 모드·SSH(`app-protocols-mail-file`),
  HTTPS·TLS·인증서(`app-protocols-mgmt-security.tls`·`https`), 포트 번호(`ports`), `ipconfig`의 옵션(`diagnostic-commands.ipconfig-options`), Apache의 디렉터리 목록·요청 크기 제한(`linux-servers`), 스위치(`hub-switch-vlan`),
  AD DS·도메인 컨트롤러(`windows-ad`), MMC·실행 창 명령·PowerShell·BitLocker·클라우드 폴더(`windows-admin-tools`) — 는 이 phase의 개념으로 다시 만들지 않는다.
  이 phase의 개념은 그것을 **쓰는 쪽**을 다루고, 필요한 바탕은 이 주제 화면에서 한 줄로 다시 푼다(「글」). 앞 주제와 뜻·값이 어긋나지 않게 그 개념을 먼저 읽는다.
- 사실은 공식 문서로 확인한 것만 쓴다. **step 0·4·9는 그 주제가 쓸 사실을 확인하는 출처 step이다**(데이터·코드를 고치지 않는다). `windows-server-roles`는 개념이 14개라 출처 step을 둘(앞 6개는 step 0, 뒤 8개는 step 4)로 나눴고,
  `windows-hyperv`의 9개는 step 9가 맡는다. 출처 step 하나가 확인할 개념은 10개 이하다(phase 76 step 0이 개념 15개로 제한 시간을 넘겼다).
- 네트워크 개념은 **개념마다 도식이 하나 이상**이다(ADR-056). 그것을 `src/components/diagrams/networkDiagramCoverage.test.ts`가 지키므로, 개념을 `topics.json`에 넣는 step은
  **그 개념의 글·문항·도식을 한 step에서 함께** 만든다. 글만 먼저 넣으면 도식이 붙을 때까지 테스트가 실패하고, 저장소의 Stop 훅(`scripts/hooks/codex-verify-gate.sh`)이
  실패한 상태로는 step을 끝내지 못하게 한다. 그래서 개념 step은 **개념 2개씩**(주제의 끝 step은 하나와 통독) 글 → 문항 → 도식 순서로 만든다.
- **step 하나는 제한 시간 안에 끝나야 한다.** 개념 2개 step이 phase 77~80에서 20~45분이었다(Stop 훅의 lint·build·test가 5~11분 더 든다).
  그래서 이 phase의 step은 **브라우저 화면 실측(개발 서버·headless Chrome·CDP)을 하지 않는다** — phase가 끝난 뒤 메인 세션이 모든 도식을 한꺼번에 실측한다.
  시간을 아끼려고 검증 명령을 건너뛰지는 마라 — 아래 공통 AC는 모두 돌린다.
- **진행 안내 문장을 쓰지 않는다.** 「바로 다음 개념에서 다룬다」, 「이 주제의 뒤쪽에서 자세히 다룬다」, 「검사점은 아래에서 자세히 본다」처럼 글의 진행만 알리는 말은
  `src/data/network/data.test.ts`의 「요약과 문단에 「다음 개념에서 다룬다」 같은 진행 안내가 없다」 테스트가 막는다(WRITING_GUIDE 「본문 작성 원칙」).
  뒤 개념이 자세히 다룰 낱말이 지금 필요하면 그 자리에서 한 줄로 풀고 넘어간다. 「앞 개념에서 본 것처럼」 같은 되짚기는 써도 된다.

## 두 주제와 개념 23개

주제 객체를 `topics.json`의 **`windows-ad` 주제 객체와 `windows-admin-tools` 주제 객체 사이**에 차례로 끼운다 — 주제 지도의 순서(38 `windows-ad` → 39 → 40 → 41 `windows-admin-tools`)대로다.

- `windows-server-roles`는 **`windows-ad` 바로 뒤**.
- `windows-hyperv`는 **`windows-server-roles` 바로 뒤**(= `windows-admin-tools` 바로 앞).

```json
{ "id": "windows-server-roles", "title": "Windows Server의 서버 역할", "importance": 2, "sourcePages": [0, 0], "concepts": [ … ] }
{ "id": "windows-hyperv", "title": "Hyper-V와 Windows 컨테이너", "importance": 2, "sourcePages": [0, 0], "concepts": [ … ] }
```

개념 id는 `<주제 id>.<슬러그>`다. 표의 순서·슬러그·`name`·`parentId`를 바꾸지 않는다(바꿔야 할 이유가 있으면 바꾸지 말고 summary에 적는다).
`parentId` 열의 값은 같은 주제의 슬러그다 — JSON에는 `windows-server-roles.server-roles-features`처럼 전체 id로 쓴다. 딸린 개념은 부모 바로 뒤에 이어 둔다(ADR-041 — 두 단까지만).
「다룰 것」은 범위다. 문장은 직접 쓰고, 사실은 아래 「출처」대로 가져온다. 「step 0 결과」·「step 4 결과」·「step 9 결과」라고 적힌 사실은 그 step의 summary와 출처 문서에 적힌 처리를 따른다 —
확인되지 않았으면 쓰지 않고, 시험만 그렇게 보면 「자격시험은 ~로 본다」로 쓴다. 기출 표기 `[기출 날짜 #번호]`는 정답을 확인할 곳이다(문장은 옮기지 않는다).

### `windows-server-roles` — Windows Server의 서버 역할 (기출 13)

| # | 슬러그 | name | parentId | step | 다룰 것 |
|---|---|---|---|---|---|

- `summary`는 WRITING_GUIDE 2절 — 처음 보는 사람이 일상 말로 「무엇이고 무슨 역할인지」 알게 하는 한 문장. 다른 전문용어를 알아야 이해되면 안 되고, 제목 낱말을 되풀이하는 순환 정의, 명령 이름·설정 이름·값·수치·분류를 넣지 않는다.
- `paragraphs`는 3절의 흐름(개념 → 원리 → 예시 → 특징)을 필요한 만큼. 누가·무엇을·어디서 어디로를 빠뜨리지 않는다. 같은 말을 되풀이하지 않는다.
  헷갈리는 짝(역할과 역할 서비스와 기능, 고정 IP 주소와 DHCP로 받은 주소, 파일 서버와 프린트 서버, 범위와 제외 범위, 예약과 제외 범위, 예약과 고정 IP 주소, 부하 분산과 상시 대기, MCLT와 상태 전환 간격, 사이트와 응용 프로그램 풀,
  포트 번호와 시리얼 포트, 실제 경로와 가상 디렉터리, 기본 문서와 디렉터리 검색, 요청 필터링과 방화벽, 로그 형식과 롤오버, FTPS와 SFTP, VPN과 DirectAccess, 웹 응용 프로그램 프록시와 VPN,
  호스트와 게스트, VHD와 VHDX, 내부와 개인 스위치, 프로덕션 검사점과 표준 검사점, 검사점과 내보내기, 실시간 마이그레이션과 저장소 마이그레이션, 복제본과 실시간 마이그레이션, 복제본과 검사점,
  컨테이너와 가상 컴퓨터, 프로세스 격리와 Hyper-V 격리, Nano Server와 Server Core)은 4절대로 무엇이 다르고 왜 나눠 부르는지를 말한다.
- **관리 작업은 따라 할 수 있게 쓴다.** 역할을 설치하거나 범위·사이트·검사점을 만드는 개념은 어느 도구에서(실행 이름), 무엇을 고르고, 무엇을 하면, 그 결과 무엇이 달라지는지(어느 클라이언트가 어느 주소를 받는지, 어느 URL이 어느 파일을 여는지, 가상 컴퓨터가 어느 상태로 돌아가는지)를 차례대로 쓴다.
  메뉴·창 이름은 출처가 보이는 이름대로 쓴다 — 출처가 화면 꼴을 보이지 않으면 지어 보이지 않고 무엇을 하는지만 말로 쓴다. 명령 줄(`Install-WindowsFeature …`)은 출처가 보이는 꼴을 따르고, 그 줄이 하는 일을 함께 보인다. 값은 예시 값이라고 밝힌다.
  계산이 나오는 곳(나눠 줄 수 있는 주소 수, MCLT로 늘려 줄 수 있는 시간, URL과 파일 경로의 대응, 복제본이 가진 변경의 시점)은 예시 하나를 처음부터 끝까지 단계대로 보인다.
- **이 주제 화면만 읽고 뜻이 서야 한다.** 학습자는 주제 목록에서 아무 주제로나 바로 들어오므로, 다른 주제에 정의가 있다는 것은 도움이 되지 않는다.
  이 주제 안에서 처음 쓰는 낱말(운영 체제, 서버, 클라이언트, 프로토콜, IP 주소, 서브넷 마스크, 기본 게이트웨이, DHCP, DNS, MAC 주소, HTTP·HTTPS, URL, 포트 번호, 인증서, 프로세스, 프록시, VPN, 터널, 암호화, 커널, 스위치 등)은 그 자리에서 짧게 푼다.
  앞 step이 같은 주제에서 이미 푼 낱말은 다시 풀지 않는다 — 쓰기 전에 그 주제의 앞 개념을 읽는다. 도식의 라벨·곁말·캡션도 화면의 글이다.
  다른 주제의 개념(DHCP의 임대, FTP, SSH, HTTPS, 포트, `ipconfig`, Apache의 디렉터리 목록, 스위치, PowerShell, BitLocker)을 가져다 쓸 때도 이 주제 안에서 한 줄로 푼다. 앞 phase가 쓴 말과 뜻을 맞춘다.
- **진행 안내 문장을 쓰지 않는다**(「배경」). 다른 주제나 뒤 개념을 가리키는 말이 필요하면 그 낱말을 그 자리에서 한 줄로 풀고, 「~에서 다룬다」·「~에서 자세히」·「다음 개념의」·「(다음 개념)」을 붙이지 않는다.
- 비유는 이해를 돕는 데만 쓰고, 실제 동작과 다르면 그 자리에서 밝힌다(예: 검사점을 「게임의 저장 지점」에, 역방향 프록시를 「접수 창구」에 비유한다면 무엇이 다른지). 비유로 사실을 대신하지 않는다.
- `name`은 명사구다(ADR-030 기준 1). **굵은 글씨(`**`)는 목록 항목의 이름에만** 쓴다(ADR-055). 목록 개념은 소개 문단 하나 뒤에 `- **이름**(English name)은 …` 꼴 항목을 두고, 항목은 혼자 서지 않는다(ADR-046).
  **굵은 글씨 안에 백틱을 넣지 마라** — `src/components/EmphasizedText.tsx`는 `**…**` 안의 백틱을 코드로 바꾸지 않아 백틱이 글자로 보인다. 그래서 항목 이름은 둘 중 하나로 쓴다.
  (1) 한국어 이름에 영문 이름, 또는 영문 이름이 곧 화면 이름인 것: `- **외부**(External)는 …`, `- **Nano Server**는 …`.
  (2) 명령·실행 이름이 이름인 항목은 하는 일·도구를 한국어 이름으로 세우고 그 명령을 괄호 안 코드 표기로 붙인다 — phase 76·78·79·80과 같은 꼴이다.
  목록 개념도 항목 뒤에 문단을 더 둘 수 있다(선례 `routing.routing-table`, phase 79의 `linux-servers.named-conf-options`, phase 80의 `windows-ad.local-groups`).
  위 표에서 굵게 적은 말(예: 「**범위**」, 「**검사점**」)은 이 문서의 강조일 뿐이다 — 목록 항목이 아닌 문단에서는 굵게 쓰지 않는다.
- 관용 표현(`돌린다`·`띄운다`·`태운다`·`물린다`·`던진다`·`쏜다`·`찍는다`·`올린다`(서버를))을 쓰지 않고 하는 일을 그대로 쓴다(ADR-030 기준 5) — 가상 컴퓨터를 「돌린다」가 아니라 「실행한다」. 평서문 「~다」로 쓴다.
- 「A vs B」 제목은 쓰지 않는다(ADR-055·ADR-059).
- 도메인 이름·사이트 이름·컴퓨터 이름·주소·파일 경로·명령·실행 이름·cmdlet·확장자·URL은 백틱으로 감싼다(ADR-044 — 선례 phase 75~80의 본문).
  역할 이름(DHCP 서버·웹 서버(IIS))·기능 이름(검사점·요청 필터링)·도구 이름(서버 관리자·IIS 관리자·Hyper-V 관리자)·기본 이미지 이름(Nano Server)은 문장에서 설명할 때 백틱 없이 쓴다(선례 phase 80의 그룹 이름·도구 이름). 개념의 `name`에는 백틱을 쓰지 않는다.
- Windows 경로(`D:\Docs\guide.html`)와 UNC 경로(`\\SRV01\Data`)는 JSON 문자열 안에서 백슬래시를 `\\`로 적는다(「파일 형식」).

## 문항 — WRITING_GUIDE 「객관식 문제의 문장과 선택지 구성 원칙」과 ADR-054·ADR-030

가장 중요한 원칙: **질문은 쉽게 이해할 수 있도록, 선택은 충분한 생각이 필요하도록.**

1. **정의에서 이름만 지운 「무엇인가?」 꼴을 내지 않는다.** 개념에 맞는 방식 하나를 고른다 — 개념 확인, 원리 이해, 상황 적용, 개념 비교, 원인과 결과. 고른 방식과 이유를 summary에 적는다.
   관리 문항은 「이 일을 하려면 어디서 무엇을 하나」·「이렇게 하면 무엇이 달라지나」 꼴의 상황으로, 범위·MCLT·URL·복제 시점 문항은 본문과 다른 값의 장면을 주고 결과를 따지게 한다.
2. **사람이 사람에게 묻듯 쓴다.** 소리 내어 읽어 어색하거나 한 번에 이해되지 않으면 다시 쓴다. 쉼표로 조건을 줄줄이 잇는 압축문을 쓰지 않는다.
3. 무엇을 묻는지는 첫 읽기에 분명하고, 어려움은 보기를 고르는 데서 나온다. 문제문을 비틀어 난이도를 만들지 않는다.
   **문제문이 답의 이유를 먼저 알려 주지 않는다** — phase 75의 n115는 문제문에 이유를 적어 개념을 몰라도 「예」를 고를 수 있었고, 사용자 검토에서 고쳤다.
   예/아니요의 주장은 개념을 알아야 판단할 수 있는 결과나 동작으로 세운다.
4. 보기는 기술적으로 갈리고 정답은 하나다. 비슷한 개념을 보기로 둘 때는 그 차이를 판단할 조건을 문제문에 준다. 오답은 문제문이 묻는 범주 안에서, 실제로 헷갈리는 것에서 고른다(ADR-030 기준 4).
   정답의 이름이나 그 일부를 문제문에 쓰지 않는다(기준 3). 보기 넷은 서로 다르다. **오답은 흔한 혼동에서** 고른다 — 역할과 기능을 바꾼 것, 제외 범위와 예약을 바꾼 것, MCLT를 상태 전환 간격으로 읽은 것,
   실제 경로와 가상 디렉터리를 바꾼 것, FTPS와 SFTP를 바꾼 것, 웹 응용 프로그램 프록시와 VPN을 바꾼 것, 내부와 개인 스위치를 바꾼 것, 검사점과 내보내기를 바꾼 것, 실시간 마이그레이션과 저장소 마이그레이션을 바꾼 것, 컨테이너와 가상 컴퓨터를 바꾼 것.
   **보기는 하나만 맞는지 실제로 따져 본다** — 같은 결과를 내는 다른 방법이 오답에 끼지 않게(예: IIS 관리자를 여는 문항에 「컴퓨터 관리」를 오답으로 두지 마라 — 컴퓨터 관리 안에서 IIS 관리자를 열 수 있는지 출처로 확인하기 전에는).
5. 판단에 쓰이지 않는 정보(전문용어·수치·조건·부정문)를 늘어놓지 않는다. 판단에 필요한 조건은 남긴다.
6. **형식(ADR-054)**: 흔히 오해하는 것을 바로잡으면 예/아니요, 비슷한 개념을 구별하거나 계산하면 4지선다, 상황을 주는 문항은 문제문의 모양으로. 같은 범주의 그럴듯한 오답 셋을 출처 안에서 쓸 수 없으면 예/아니요.
   예/아니요는 주장 하나, 이중 부정·「항상」「절대」「반드시」·「~만」 금지, 「~인가요?」「~나요?」로 끝난다. **아니요 문항의 해설은 무엇이 틀렸는지에서 그치지 않고 맞는 사실을 가르친다.**
   예/아니요의 주장은 맞는 쪽으로도 틀린 쪽으로도 세울 수 있다 — 아래 균형을 맞추려고 주장의 방향을 고른다. step 문서가 적은 방향은 계획이고, 균형 규칙이 먼저다.
7. **문항은 풀면서 배우게 쓴다.** 문항은 섞여 나오고 랜덤 세트는 일부만 뽑으므로 혼자 읽혀야 한다. 문제문이 이 주제 밖의 낱말을 풀이 없이 전제하지 않는다(기준 5).
   상황에 쓰는 이름(「인사팀 서버」, `hr.example.com`)·숫자는 사실 주장이 아니어야 하고, 그 상황의 정답은 출처의 사실로 정해져야 한다. 문항 상황은 본문 예와 다르게 만들어 본문 문장을 외워서 풀리지 않게 한다
   (「예시 값」의 「문항은 본문과 다른 값」). 기출의 값(「예시 값」의 마지막 줄)도 쓰지 않는다.
   **문항 글에 백틱을 쓰지 않는다** — 퀴즈 화면(`QuizRunner`)은 문제문·보기·해설을 글자 그대로 그려 백틱이 기호로 보인다(phase 78 통독에서 n198·n199를 고쳤다). 이름·경로·명령은 백틱 없이 그대로 적는다.
8. **해설은 187자 이상**이고 그 개념을 가르치는 글이다(ADR-026·027). 4지선다는 정답이 왜 맞는지와 오답 셋이 각각 왜 아닌지를 담는다. 계산 문항의 해설은 계산을 단계대로 보인다. 약어는 해설마다 처음 쓸 때 풀어 쓴다.
   같은 말을 늘려 길이를 채우지 않는다. 해설의 사실은 개념 본문이나 출처 문서에 있는 것이다. 해설도 평서문 「~다」로 쓴다.
9. **균형 — step이 끝났을 때 과목 전체에서**: 예/아니요의 예와 아니요 수 차이 **1 이하**, 4지선다의 정답 위치(`answerIndex` 0~3) 수의 최대·최소 차이 **2 이하**.
   phase 81 시작 때는 문항 283개, 예/아니요 111개(예 56·아니요 55), 4지선다 172개(정답 위치 43/43/43/43)다. step 문서의 방향·정답 위치 계획대로 가면 끝에 예/아니요 124개(예 62·아니요 62), 4지선다 188개(정답 위치 47/47/47/47)가 된다.
10. 한 문항은 개념 하나만 묻는다(ADR-030 기준 2). 같은 개념의 두 문항은 서로 다른 것을 묻는다.
11. 기출 문항의 문장·보기 구성을 옮기지 않는다 — 시험이 같은 사실을 물어도 상황과 문장은 직접 만든다. **기출과 같은 보기 넷 묶음**은 정답만 바꿔서도 쓰지 않는다 —
    보기의 범주를 바꾸거나(기능 이름 대신 그 기능으로 일어나는 일을 보기로), 보기 가운데 둘 이상을 다른 것으로 바꾸거나, 상황을 바꿔 그 사실을 이해했는지 묻는다.
    이 phase의 기출 보기 묶음(정답만 바꿔도 쓰지 않는다):
    - `windows-server-roles`: 파일·프린터 서버의 통신 프로토콜(TCP/IP·SNMP·SMTP·IGMP), IIS 관리자 명령(`wf.msc`·`msconfig`·`inetmgr.exe`·`dsac.exe`), IIS 사이트 등록 정보(IP 주소·TCP 포트·연결 수 제한·연결 시간 제한),
      DHCP 구성(임대 기간 단위·WINS 구성·예약 유형·주소 분배 지연 시간), 원격 액세스 기능(WAP·PPTP·L2TP·SSTP), DNS 설치 문제의 해결(`ipconfig /renew`·고정 할당·다음 IP 주소 사용·다음 DNS 서버 주소 사용),
      IIS 기능(요청 필터링·HTTPS 미지원·PHP 불가·응용 프로그램 풀 하나의 사이트), IIS 로그(저장 위치 변경·W3C만·실시간·자동 삭제), DHCP 장애 조치의 MCLT(인증 최대 시간·임대 임시 갱신 최대 시간·Discover 재전송 간격·스코프 비활성화 유예),
      FTP 서버 설치(역할 서비스·서드파티·SFTP·PowerShell 불가), IIS 관리자 기능(홈 디렉터리 고정·기본 문서 추가·디렉터리 검색·가상 디렉터리 별칭).
    - `windows-hyperv`: Hyper-V 특징(복제 불가·실행 중 저장소 이동·물리 서버 하나에 가상 컴퓨터 하나·사용률 낮아짐), Hyper-V 설명(하드웨어 사용률·가용성 감소·유지 비용·개발과 테스트),
      컨테이너 빈칸(Hyper-V/Virtual Machine·IIS/Internet Information Services·Windows 컨테이너·Nano Server), 검사점 빈칸(가상 스위치·새로 고침·내보내기·검사점 / 내보내기·롤백·타임머신·검사점).
    지문이 빠진 기출(DNS 설치 문제, 컨테이너 셋, 검사점 둘)은 보기만 남았다 — 그 보기 묶음도 쓰지 않는다. 문항을 쓰기 전에 그 개념의 기출 문항(`docs/source/network/raw/exam/data.txt`에서 `X-windows`로 분류한 줄과 교사용 텍스트의 그 문항)을 읽고 보기 묶음이 겹치지 않는지 본다.

검수 — 문항마다 WRITING_GUIDE 객관식 7항의 여섯 질문으로 다시 읽고, 보기마다 「이것이 정답이라고 우길 수 있는가」를 따진다. 문제문만 읽고 보기를 보지 않은 채 정답 글자를 짐작할 수 있지 않은지도 본다.
계산·상황 문항은 정답을 손으로 다시 따지고(주소 수를 하나씩, 시간을 분 단위로, URL을 조각마다), 오답 셋이 정말 틀렸는지도 따진다.

## 도식 — 개념마다 하나 이상

선례는 phase 73~80의 도식들이다 — `src/components/diagrams/`의 `ThreeWayHandshakeDiagram`·`DhcpExchangeDiagram`(두 장치 사이를 오가는 차례), `MailPathDiagram`·`ArpHopsDiagram`(길과 구간),
`RoutingTableDiagram`·`FstabFieldsDiagram`(표 모양과 줄의 칸), `DirectoryTreeDiagram`·`AdForestStructureDiagram`(나무·포함), `ChmodChangeDiagram`·`IpconfigOptionsDiagram`(명령·설정 전과 뒤), `NetstatLinuxOptionsDiagram`·`IptablesChainsDiagram`(명령 줄의 조각·시나리오별 길),
`NamedFilesDiagram`·`BuiltinLocalGroupsDiagram`(도구·대상의 관계), `DomainTrustDiagram`(방향이 뜻인 화살표), `AccountLockoutDiagram`(설정 전과 뒤의 시간), `EfsKeyBackupDiagram`(했을 때와 안 했을 때)과 그 `.test.tsx`,
`src/data/network/visuals/linux-servers.json`·`windows-ad.json`·`windows-admin-tools.json`. 규칙의 근거는 UI_GUIDE 「도식 전용 색상」·「도식」 절 전체, ADR-036·037·038·047·048·056, `src/components/diagrams/CLAUDE.md`다.
사용자 미리보기 승인을 받지 않고 **step이 좌표를 설계한다.** 그래서 기계 검사를 모두 통과시키고 설계를 summary에 남긴다.

- **파일**: 컴포넌트는 `src/components/diagrams/<이름>Diagram.tsx`(이름이 `Diagram.tsx`로 끝나야 교차 검사와 커버리지 테스트가 도식으로 본다), 테스트는 같은 이름의 `.test.tsx`.
  문구(물음형 제목 `question`·노드 라벨·곁말·캡션·`idleCaption`·`legend`·figure `label`·`svgLabel`·시나리오·`sources`)는 그 주제의 `src/data/network/visuals/<주제 id>.json`의 `diagrams["<키>"]`에 둔다.
  `glossary`는 빈 배열이다(ADR-037·ADR-055). 도식 이름과 키는 step 문서가 정한다 — 이미 있는 도식 이름과 겹치지 않는 것을 골라 두었다.
- **사실은 본문에만 있는 것**(ADR-036). 캡션·곁말·라벨의 사실마다 그 개념(과 같은 주제의 다른 개념) 본문의 문단을 근거로 댈 수 있어야 한다. 예시 값도 본문에 나오는 것만(ADR-038).
  「서버」·「클라이언트」·「호스트」·「인터넷 사용자」처럼 대상을 가르는 이름표는 사실이 아니므로 써도 된다. 글과 도식을 같은 step이 만드므로, 도식에 필요한 사실은 **글에 먼저 쓴다** — 출처에 없으면 그리지 않는다.
  「자격시험은 ~로 본다」로만 쓴 것은 공식 문서의 사실이 아니므로 **도식에 사실처럼 그리지 않는다.**
- **화면을 흉내 내지 않는다.** 서버 관리자·DHCP 콘솔·IIS 관리자·Hyper-V 관리자의 창·메뉴·트리를 그림으로 꾸며 그리지 않는다 — 출처가 보이는 화면 꼴이 아니고, 판마다 다르다. 도식은 관계(역할과 역할 서비스, 서버와 클라이언트, 범위 안의 주소 구간, 사이트와 풀, URL과 폴더, 호스트와 가상 컴퓨터, 스위치와 네트워크)를 노드와 경로로 보인다.
- **말**: 노드 라벨·곁말은 본문에 쓰인 말과 같게 쓴다. 라벨을 줄이거나 영문 약어로 바꿔 폭을 맞추지 마라 — 노드를 넓히거나 배치를 바꾼다.
- **글자 크기**: 노드 라벨 10, 그룹 라벨·곁말 9(viewBox 단위). `estimateTextWidth(라벨, 10) + 12 <= 노드 폭`. 노드 높이는 32다(교차 검사기가 32로 본다 — 키 큰 노드를 만들지 말고 그룹 박스를 쓴다).
- **글자 폭의 여유**: `estimateTextWidth`는 반각 문자(영문·숫자·기호)를 0.55em으로 보지만 실제 화면에서는 0.61em까지 넓다(phase 72 화면 실측). 이 phase의 라벨은 주소·경로·URL·이미지 이름(`192.0.2.100`~`192.0.2.199`·`http://www.example.com/docs/guide.html`·`D:\VMs\VM01.vhdx`)처럼 **반각 문자가 많고 길다**.
  그래서 반각 문자가 섞인 노드 라벨·곁말·그룹 라벨은 `estimateTextWidth` 값의 **1.15배**를 폭으로 잡아 노드 폭·배치를 정하고, 그 범위가 둘레 박스와 `viewBox` 안에 들게 한다(phase 73~80이 이렇게 해서 화면 실측 걸침 0이었다).
  280 폭에 들지 않는 긴 이름은 줄이지 말고 노드를 한 줄 전체 폭으로 쓰거나, 이름을 조각 노드 여럿으로 나눠 놓는다(그 나눔이 본문의 설명과 같을 때만 — URL을 호스트 이름·별칭·파일 이름 조각으로 나누는 것처럼).
- **관계 그림**(역할과 역할 서비스, 서버와 클라이언트, 프록시를 거치는 길): 주체를 한쪽, 대상을 다른 쪽에 두고 직교 경로로 잇는다. 방향이 뜻인 화살표(요청과 응답, 복제의 방향, 마이그레이션의 방향)는 곁말로 어느 쪽인지 밝힌다(본문의 말).
  280 폭에서 한 줄에 노드 넷 이상을 나란히 두지 마라 — 세로로 쌓거나 그룹 박스로 묶는다.
- **나무·포함 그림**(역할 안의 역할 서비스, 호스트 안의 가상 컴퓨터, 범위 안의 제외 범위와 예약): 위에서 아래로 직교 경로(M/H/V)로 잇거나, 그룹 박스 안에 그룹 박스를 넣는다(선례 `DirectoryTreeDiagram`·`AdForestStructureDiagram`). 280 폭에 가지가 들지 않으면 한 갈래만 그리고 곁가지는 본문이 말한다.
- **차례 그림**(장애 조치 전과 뒤, 검사점을 만들고 적용하기, 복제의 시점): 같은 일의 단계나 두 결과를 시나리오로 나눈다. 시나리오마다 다른 결과 노드는 다른 id를 다른 자리에 둔다 — 같은 자리에 겹쳐 두고 opacity로 가리지 마라.
- **줄과 칸 그림**(사이트 바인딩의 네 값, URL과 파일 경로의 조각): 칸을 빈틈없이 이은 노드 줄이나 「칸 이름: 값」 줄 여럿으로 그린다(선례 `FstabFieldsDiagram`·`NetstatLinuxOptionsDiagram`).
  여러 열 표를 280 폭 한 줄에 억지로 넣지 마라. 명령 한 줄은 글자 하나씩이 아니라 뜻이 갈리는 조각 하나를 노드 하나로 그린다.
- **색**: 노드는 모두 회색(`stroke-disabled`, 선례와 같은 클래스). 도식 전용 두 색(`diagram-managed`·`diagram-resource`)은 AWS 계층의 뜻이라 쓰지 않는다. 초록·빨강·주황, 16진 색, 이모지, O/X, 자물쇠·방패 그림도 쓰지 않는다(ADR-036).
  강조는 opacity로만 한다 — 선택 밖 노드 `0.25`, 그룹 박스는 흐려지지 않는다. 나쁜 상태(멈춤·거부·막힘·잃은 변경)는 색이 아니라 곁말과 흐림·사라지는 경로로 보인다(UI_GUIDE 「수량과 상태를 바꾸는 도식」).
- **두 배치**: 세로형(`viewBox` 폭 280)과 가로형(폭 440)을 함께 만든다. 가로형은 `useWideDiagram()`이 `true`일 때 쓴다. `nodes`·`wideNodes`·경로·`wideGroups`·`wideNotes`를 **한 줄에 하나씩 글자 그대로** 적는다 —
  반복문이나 계산으로 만들지 마라(교차 검사기가 글자로 읽는다). 노드 id·경로 id·시나리오·문구는 두 배치가 함께 쓰고, 고른 시나리오는 배치가 바뀌어도 유지된다.
- **경로**: 직교(M/H/V)만, 노드 변에서 시작하고 끝나며, 다른 노드 상자 안을 지나지 않는다. 늘 보이는 연결선도 같은 경로 선언 꼴(`'id': 'M…'`)로 적는다.
  화살표 마커는 선례와 같고 마커 id는 `useId`로 만든다. 그룹 라벨 영역을 지나는 선분이 없어야 한다.
  `phases/38-service-diagrams/tools/check-path-crossings.mjs`는 `*Diagram.tsx`의 `const nodes = [`·`const wideNodes = [` 블록에서 `{ id: '…', x: N, y: N, width: N` 순서를, 경로 객체에서 `'id': 'M…'`를 정규식으로 읽는다. 이 형식을 지켜라.
- **물음형 제목**(ADR-038): 그림이 답하는 것 하나를 학습자의 말로. step 문서의 예는 바꿔도 된다.
- **시나리오**: step 문서에 적힌 시나리오를 둔다. 「정지 그림」은 `scenarios` 없이 `idleCaption`이 캡션 노릇을 한다. 시나리오가 있는 도식은 `전체`(아무것도 고르지 않음)에서 노드가 모두 선명하다.
  두 시나리오의 「선명한 노드 + 보이는 경로 + 보이는 곁말」이 같으면 그 시나리오는 아무것도 가르지 못한다 — 다르게 설계한다. 캡션은 20자를 넘는다(`visuals.test.ts`).
- **금지**: SVG 두 개를 그려 놓고 CSS로 하나를 숨기지 마라. 기준 폭 문자열(`'(min-width: 768px)'`)을 도식 파일에 쓰지 마라(ADR-047). 흐르는 점·자동 재생·움직이는 메시지·깜박이는 커서 같은 애니메이션 금지.
  공용 컴포넌트(`DiagramFrame.tsx`·`ComparisonTableFigure.tsx`·`ConceptList.tsx`·`useWideDiagram.ts`)와 교차 검사기, `src/lib/svg-bounds.ts`를 고치지 마라.
- **registry**: `src/components/diagrams/registry.ts`의 `diagramsByConceptId`에 `'<개념 id>': <이름>Diagram` 한 줄씩. import는 기존 정렬(모듈 경로 알파벳순)을 따른다. 키는 한 자리에 끼운다 —
  `'windows-ad.password-lockout-policy'` 줄 바로 뒤·`'windows-admin-tools.mmc-run-commands'` 줄 앞에, `windows-server-roles.*`를 개념 순서대로 둔 뒤 그 뒤에 `windows-hyperv.*`를 개념 순서대로. 기존 줄의 차례는 바꾸지 않는다.
- **주제의 시각 요소 파일**: 주제의 첫 개념을 넣는 step(`windows-server-roles`는 step 1, `windows-hyperv`는 step 10)이
  `src/data/network/visuals/<주제 id>.json`(`{ "diagrams": {}, "tables": {}, "glossary": [] }` 꼴)을 만들고 `src/data/network/index.ts`의 `visualsByTopicId`에 `'<주제 id>'`로 넣는다
  (import 이름은 `windowsServerRolesVisuals`·`windowsHypervVisuals`이고 import 줄은 기존 정렬(경로 알파벳순 — `windows-admin-tools.json` 뒤에 `windows-hyperv.json`, 그 뒤에 `windows-server-roles.json`)대로.
  `visualsByTopicId` 항목은 `'windows-server-roles'`를 **`'windows-ad'` 항목 바로 뒤**에, `'windows-hyperv'`를 **`'windows-server-roles'` 항목 바로 뒤**(= `'windows-admin-tools'` 앞)에 둔다). 비교표는 이 phase에서 만들지 않는다.

### 도식 테스트 — 도식마다 먼저 쓰고 실패를 확인한 뒤 구현한다

`<이름>Diagram.test.tsx` — 선례와 같은 관문을 건다. 세로형은 `matchMedia` 없이, 가로형은 `describe('가로형 (768px 이상)', …)` 안에서만 `vi.stubGlobal('matchMedia', …)`.

1. 물음형 제목이 시나리오 버튼보다(정지 그림이면 SVG보다) 앞에 보인다(헤딩이 아니다).
2. 처음(`전체`)에는 노드가 모두 선명하다. 시나리오에만 쓰이는 경로는 보이지 않는다(늘 보이는 연결선은 보인다).
3. 시나리오마다 선명한 노드 집합, 보이는 경로, 보이는 곁말, 캡션이 JSON·step 문서의 설계와 같다. 선택 밖 노드는 opacity `0.25`, 그룹 박스는 흐려지지 않는다.
4. 모든 `rect`가 `boxesOutsideViewBox`로 `viewBox` 안이고, 노드 라벨이 `estimateTextWidth(라벨, 10) + 12 <= 노드 폭`이다. 곁말·그룹 라벨은 `estimateTextWidth(문구, 9)`로 잰 가로 범위가 `viewBox` 안이다.
5. 경로의 끝점이 노드 변 위에 있고, 어떤 선분도 다른 노드 상자 안과 그룹 라벨 영역을 지나지 않는다.
6. **그 도식의 요점** — step 문서에 도식마다 적힌 「요점 테스트」.
7. 두 번 렌더해도 화살표 마커 id가 겹치지 않는다. JSON의 시나리오 id 집합과 컴포넌트의 것이 같고, 문구를 JSON에서 읽는다.
8. `ConceptList`에 앵커 개념을 주면 본문 뒤에 이 도식이 온다.
9. 가로형: `viewBox` 폭 440, 래퍼에 `w-full`이 있고 `max-w-[380px]`·`-mx-4`가 없다. 노드·그룹 id 집합과 경로 id 합집합이 세로형과 같고, 3~6번을 가로형에서도 통과한다. 폭이 바뀌어도 고른 시나리오와 캡션이 유지된다.

정지 그림은 시나리오에 관한 항목(2의 경로 부분, 3, 7의 시나리오 id, 9의 선택 유지)을 「캡션이 `idleCaption`이고 버튼이 없다」로 바꿔 건다.

## 파일 형식

- `topics.json`: 주제 객체는 2칸 들여쓰기, `concepts` 배열의 개념은 **한 줄에 하나**(6칸 들여쓰기 + `JSON.stringify(concept)`). 개념 키 순서는 `id`, `parentId`(있을 때), `name`, `summary`, `paragraphs`.
  주제 키 순서는 `id`, `title`, `importance`, `sourcePages`, `concepts`(기존 주제와 같게). 주제 객체 사이는 기존 꼴대로 `  }` 줄, `,` 줄, `  {` 줄로 잇는다.
  앞 step이 쓴 줄과 다른 주제의 줄은 글자 하나도 바꾸지 않고, 자기 개념을 그 주제의 `concepts` 끝에 덧붙인다.
  **새 주제는 `windows-ad`와 `windows-admin-tools` 사이에 끼운다** — `windows-server-roles`는 `windows-ad` 주제 객체 바로 뒤, `windows-hyperv`는 `windows-server-roles` 주제 객체 바로 뒤. 끼운 자리의 앞뒤 쉼표와 줄바꿈이 기존 꼴과 같은지 본다.
- `questions.json`: `[` 다음 줄부터 **한 줄에 문항 하나**, 마지막 줄 뒤에 `]`. 키 순서 — 4지선다 `id`, `topicId`, `conceptId`, `format`, `prompt`, `choices`, `answerIndex`, `explanation` /
  예/아니요 `id`, `topicId`, `conceptId`, `format`, `prompt`, `answer`, `explanation`. 기존 줄은 바꾸지 않고 끝에 덧붙인다.
- 파일 끝 줄바꿈 하나. 스크립트로 쓸 때 CRLF로 바꾸지 않는다. JSON 문자열 안의 백슬래시(Windows 경로 `D:\Docs`, UNC 경로 `\\SRV01\Data`)는 JSON 이스케이프(`\\`, UNC 앞머리는 `\\\\`)로 적고, 화면에 원하는 글자로 보이는지 테스트나 `node -e`로 확인한다.
- 이 저장소의 TDD 훅은 테스트 파일 없이 새 `.js`·`.ts` 파일을 쓰지 못하게 막는다. 데이터를 고치는 일회용 스크립트가 필요하면 저장소 밖(임시 디렉터리)에 `.cjs`로 두거나 `node -e`를 쓴다.

- `check-verbatim`은 「전사 이상 없음」이고 **「원본 2개」를 대조했다고 나와야 한다**(`raw/`가 없으면 「건너뜀」으로 통과하므로 그때는 blocked로 멈춘다). 두 주제는 강의 밖이라 강의 문장과 겹칠 일이 적지만 결과를 summary에 적는다.
  균형은 위 「문항」 9항, 교차 검사기는 「교차 없음」이고 노드·경로 수가 이 step이 더한 만큼 늘어야 한다(phase 81 시작 때 세로·가로 모두 노드 2471개·경로 1650개. 앞 step이 끝났을 때의 수는 그 step summary에 있다). **검사기를 고쳐서 통과시키지 마라.**
- **바뀌지 않아야 하는 것을 기계로 확인한다** — `git show HEAD:src/data/network/topics.json`·`questions.json`과 `visuals/*.json`을 지금 파일과 node로 읽어, 기존 주제 객체·기존 개념·기존 문항·기존 도식 문구가 통째로 같은지 본다.
  새 주제를 끼우므로 **주제 id의 차례**도 본다 — 기존 주제의 상대 차례가 그대로이고, `windows-server-roles`가 `windows-ad` 바로 뒤에, `windows-hyperv`가 `windows-server-roles` 바로 뒤에(만든 것까지만), `windows-admin-tools`가 그 뒤에 있어야 한다.
- **문항 글에 백틱이 없는지 본다** — `node -e`로 `n284` 이후 문항의 `prompt`·`choices`·`explanation`에 백틱이 없는지 센다(「문항」 7항).
- **글로 읽는다** — 그 주제의 개념을 처음부터 이 step의 개념까지 처음 배우는 사람의 눈으로 통독하고, 풀이 없이 처음 나오는 낱말을 세어 본다(도식 문구 포함). 진행 안내 문장이 없는지도 본다. 불변식과 테스트는 이런 결함을 잡지 못한다.
  관리 작업의 차례와 명령 줄은 출처의 절·예시와 하나씩 대조하고, 계산이 나오는 곳은 손으로 다시 해 본다. **공식 문서 문장을 옮기지 않았는지** 자기가 쓴 문장을 출처(영문·한국어 판 모두)와 나란히 놓고 본다.
  브라우저 화면 실측은 하지 않는다(「배경」의 시간 제한 — phase 끝에 메인 세션이 한다).

## 모든 step의 공통 금지

- **출처 문서에 없는 사실을 쓰거나 그리지 마라.** 이유: 원본에 없는 내용을 지어내지 않는 것이 이 저장소의 규칙이다(루트 CLAUDE.md, ADR-036). 필요하면 확인해서 `standards.md`에 먼저 더한다.
  메뉴 이름, 명령의 출력, 관리 작업의 차례, 화면의 꼴, 기본값도 사실이다 — 출처가 보이는 것이 아니면 지어서 보이지 마라.
- **공식 문서·기출의 문장을 옮기지 마라.** 이유: ADR-009·ADR-057. `check-verbatim --subject network`는 강의·면접만 대조하는 하한선일 뿐이다.
- **불변식 테스트·커버리지 테스트를 고치거나 예외를 더하지 마라.** 이유: 테스트가 실패하면 데이터를 고치거나 도식을 그린다(ADR-026·ADR-056). 진행 안내 가드 테스트도 마찬가지다 — 걸리면 문장을 고친다.
- **자기 step의 개념이 아닌 개념을 만들거나, 앞 step이 쓴 글·문항·도식을 고치지 마라.** 이유: 범위가 겹치면 사용자가 무엇이 어디서 바뀌었는지 따라갈 수 없다.
  앞 개념에 고칠 것을 찾으면 고치지 말고 summary에 적는다.
- AWS·Azure 데이터와 앞 phase의 스물다섯 주제(`network-basics`·`protocols-encapsulation`·`ethernet`·`hub-switch-vlan`·`ip-protocol`·`arp`·`icmp`·`ip-addressing`·`ip-address-types`·`routing`·`ports`·`tcp-udp`·`tcp-connection`·`dns`·
  `app-protocols-mail-file`·`app-protocols-mgmt-security`·`diagnostic-commands`·`linux-filesystem`·`linux-permissions`·`linux-shell`·`linux-process-boot`·`linux-accounts`·`linux-servers`·`windows-ad`·`windows-admin-tools`)를 고치지 마라. 기존 테스트를 깨뜨리지 마라.
- **`docs/source/network/topic-map.md`·`CLAUDE.md`·`lecture-outline.md`·`interview-facts.md`를 고치지 마라.** 이유: 이 phase는 주제를 더하거나 나누지 않고 새 출처를 더하지 않으며, 강의·면접은 이 주제를 다루지 않는다.
- **브라우저 실측을 하지 마라.** 이유: step 시간 제한(「배경」). 화면 확인은 phase 끝에 한꺼번에 한다.

# Step 2: well-known-client-server

## 배경

phase 77은 네트워크 과목의 `ports`·`tcp-udp`·`tcp-connection`을 만든다. 전체 계획·결정·공통 규칙은 `phases/77-network-ports-tcp/guide.md`에 있다.
**이 step은 주제 `ports`의 나머지 개념 둘(3 잘 알려진 포트, 4 서버 포트와 클라이언트 포트)의 글·문항·도식을 함께 만든다.**

`well-known-ports`는 이 주제의 기출 9문항이 거의 다 묻는 자리다(HTTPS 443, HTTP 80, SMTP 25, SSH 22와 Telnet 23, FTP 20·21). 외울 목록이 아니라 「무슨 일을 하는 서비스가 어느 번호에서 기다리는가」로 읽히게 쓴다.

| 3 | `ports.well-known-ports` | 잘 알려진 포트 | `ports.port-ranges` | **목록 개념** — 소개 문단(널리 쓰는 서비스의 서버 프로그램은 잘 알려진 포트 가운데 정해진 번호에서 요청을 기다린다 — 그래서 클라이언트는 따로 묻지 않고 그 번호로 연결한다) 뒤 항목 여덟(guide.md 표). 항목 꼴은 guide.md 「글」의 「서비스」 — `- **SSH**(Secure Shell)는 TCP `22`번을 쓴다. …`. 항목마다 그 서비스가 무엇을 하는지 한 줄(FTP — 파일을 주고받는다, SSH — 원격 접속을 암호화한다, Telnet — 원격 접속을 암호화하지 않는다, SMTP — 메일을 보낸다, DNS — 이름으로 IP 주소를 찾는다, DHCP — 호스트에 IP 주소를 나눠 준다, HTTP — 웹 페이지를 주고받는다, HTTPS — HTTP를 TLS로 암호화한다)와 번호·전송 프로토콜. FTP의 두 번호는 무엇이 다른지(명령이 오가는 제어 연결 `21`, 파일 내용이 오가는 데이터 연결 `20`), DNS가 UDP와 TCP를 함께 쓴다는 것(L11), DHCP의 서버·클라이언트 번호. 각 항목의 근거는 step 0 결과대로 — 확인되지 않은 항목은 넣지 않는다. 목록 뒤 문단: 잘 알려진 포트는 기본값이다 — 서버를 다른 번호로 열 수도 있고, 그러면 클라이언트가 그 번호를 적어 줘야 한다(웹 주소에 `:8080`처럼 — step 0 결과대로). Linux의 특권 포트 한 줄은 step 0 결과가 허락할 때만. SSH와 Telnet, HTTP와 HTTPS를 4절대로 |
| 4 | `ports.client-server-ports` | 서버 포트와 클라이언트 포트 | — | 서버 프로그램과 클라이언트 프로그램을 짧게 푼다(서비스를 주는 쪽과 받으려고 요청하는 쪽). 예는 guide.md 「예시 값」 — 클라이언트 `192.0.2.10`의 웹 브라우저가 출발지 포트 `50001`로 서버 `198.51.100.10`의 `80`에 요청하고, 응답은 출발지 `80` → 목적지 `50001`로 돌아온다. 요청과 응답에서 출발지·목적지 포트가 맞바뀐다는 것을 차례대로 쓴다. 클라이언트의 번호는 운영체제가 고르고 연결이 끝나면 다시 쓸 수 있다는 것, 실제로 고르는 범위(IANA의 동적 포트 범위와 다를 수 있다)는 step 0 결과대로. 같은 서버 포트 `80`에 두 번째 클라이언트 `192.0.2.11`(출발지 포트 `50001` — 첫 클라이언트와 번호가 같아도 된다)이 이어져도 섞이지 않는 까닭 — 연결은 양쪽의 IP 주소와 포트 넷으로 가린다(소켓이라는 이름은 step 0 결과대로). 서버 포트와 클라이언트 포트가 무엇이 다른지(4절 — 누가 정하는지, 얼마나 오래 쓰는지, 어느 범위인지) |

### 3. 도식

#### 3-1. `ports.well-known-ports` — `WellKnownPortsDiagram`, JSON 키 `well-known-ports`

- 물음형 제목 예: `어떤 서비스가 몇 번 포트에서 기다릴까?`
- 그릴 것: 표 모양 — 서비스 여덟을 행으로, 행마다 `서비스 이름`·`포트 번호`·`TCP`/`UDP` 노드(세로형은 행 하나에 노드 셋까지 — 넘치면 「이름 · 번호」 노드 하나와 전송 프로토콜 노드로). 본문 목록과 같은 차례. 확인되지 않아 본문에서 뺀 항목은 그리지 않는다.
- 시나리오:

  | id | label | 선명한 것 | 캡션이 말할 것 |
  |---|---|---|---|
  | `web` | 웹 | HTTP·HTTPS 행 | 웹은 `80`, 암호화한 웹은 `443` |
  | `remote-file` | 원격 접속·파일 | SSH·Telnet·FTP 행 | 원격 접속은 암호화하면 `22`, 하지 않으면 `23`. 파일 전송은 제어 `21`·데이터 `20` |
  | `mail-name-address` | 메일·이름·주소 | SMTP·DNS·DHCP 행 | 메일을 보내는 `25`, 이름을 찾는 `53`, 주소를 나눠 주는 `67`·`68` |

- 요점 테스트: 행 노드의 포트 번호가 모두 0~1023 안이다. 세 시나리오의 선명한 행을 합하면 모든 행이고 겹치지 않는다. `remote-file`에서 SSH 행과 Telnet 행의 포트 번호가 서로 다르다.

#### 3-2. `ports.client-server-ports` — `ClientServerPortsDiagram`, JSON 키 `client-server-ports`

- 물음형 제목 예: `응답은 어느 포트로 돌아올까?`
- 그릴 것: 두 기둥 — 왼쪽(세로형도 왼쪽) 클라이언트 그룹 `192.0.2.10`(노드 `웹 브라우저 · 50001`)과 그 아래 두 번째 클라이언트 그룹 `192.0.2.11`(노드 `웹 브라우저 · 50001`), 오른쪽 서버 그룹 `198.51.100.10`(노드 `웹 서버 프로그램 · 80`).
  두 기둥 사이에 세그먼트 노드 — `요청: 출발지 50001 → 목적지 80`, `응답: 출발지 80 → 목적지 50001`(라벨이 들지 않으면 그룹 박스 안 노드 둘로). 화살표는 노드 양옆의 짧은 직교 경로로(guide.md 「주고받는 차례 그림」).
- 시나리오:

  | id | label | 선명한 것 | 곁말·캡션이 말할 것 |
  |---|---|---|---|
  | `request` | 요청 | 첫 클라이언트, 요청 노드, 서버 | 클라이언트는 운영체제가 고른 번호를 출발지로, 서버의 정해진 번호를 목적지로 쓴다 |
  | `response` | 응답 | 서버, 응답 노드, 첫 클라이언트 | 응답은 출발지와 목적지 포트를 맞바꿔 돌아온다 |
  | `two-clients` | 두 클라이언트 | 두 클라이언트, 서버 | 클라이언트의 포트 번호가 같아도 IP 주소가 달라 두 연결이 섞이지 않는다 |

- 요점 테스트: `request` 곁말(또는 노드 라벨)의 출발지·목적지 포트가 `response`에서 서로 바뀌어 있다. `two-clients`의 선명한 두 클라이언트 노드 라벨의 포트 번호가 같고, 두 클라이언트 그룹의 IP 주소가 다르다.

위 도식 설계는 출발점이다. 본문(step 0 결과)과 맞지 않거나 280 폭에 들지 않으면 바꾸되, 바꾼 것과 이유를 summary에 적는다.

## 금지사항

guide.md 「모든 step의 공통 금지」에 더해:

- **응용 프로토콜 주제(phase 78)의 포트(POP3·IMAP·SNMP·NTP·TFTP 등)를 목록에 더하지 마라.** 이유: guide.md 표의 여덟이 이 개념의 범위다. 그 주제가 프로토콜과 함께 가르친다.
- **step 0이 확인하지 못한 번호나 전송 프로토콜을 쓰지 마라.** 이유: 번호 하나가 시험의 답이다 — 틀린 번호를 외우게 된다.
- **앞 step이 쓴 개념 1·2를 고치지 마라.** 이유: 범위가 겹치면 무엇이 어디서 바뀌었는지 따라갈 수 없다. 고칠 것을 찾으면 summary에 적는다.

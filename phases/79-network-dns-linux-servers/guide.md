# phase 79 공통 안내 — DNS, Linux 서버 설정

이 phase의 **모든 step이 먼저 읽는 문서**다. step 문서는 자기 개념의 세부만 적고, 두 주제의 전체 개념 표와 글·문항·도식·파일 형식의 공통 규칙은 여기에 둔다.
step 문서와 이 문서가 다르면 step 문서를 따르고 그 차이를 summary에 적는다.

## 배경 — 다시 묻지 말 결정

- 네트워크 과목의 목표 자격증은 네트워크관리사 2급이고, 범위는 강의와 그 시험의 출제 범위가 정한다(ADR-059). 주제 지도와 별점은 `docs/source/network/topic-map.md`가 갖는다.
  이 phase는 그 지도의 **19번 `dns`(DNS, ★★★, 출제 10/11회)와 37번 `linux-servers`(Linux 서버 설정, ★★☆, 8/11회)** 를 만든다. 사용자가 2026-11-12에 이 설계(개념 23개·문항 30개·step 15개)를 승인했다.
- **`dns`는 강의 주제다**(강의 Ch5-1, p328–p351). 사실은 강의(`lecture-outline.md`)·표준 문서(`standards.md`)·면접(`interview-facts.md`의 Q27)에서 가져오고, 강의·면접의 주장이 수정 이력에 걸려 있으면 고친 쪽을 쓴다 —
  특히 **L11**(DNS는 TCP도 쓴다), **L15**(SOA는 영역의 권한 정보, NS의 데이터는 네임 서버의 **이름**), **I11**(반복적 질의에서 차례로 묻고 다니는 쪽은 로컬 DNS 서버다). `sourcePages`는 `[328, 351]`이다.
  기출이 묻는 것 가운데 강의에 없는 것(영역과 영역 전송, SOA의 필드, 역방향 조회와 PTR, 라운드 로빈, DNSSEC, 이름 규칙)도 넣는다 — 출제 범위이기 때문이다(ADR-059). 그 사실은 표준·공식 문서에서만 가져온다.
- **`linux-servers`는 강의 밖 주제다**(phase 75·76·78과 같은 꼴). 사실의 출처는 **허용한 공식 문서 하나**다 — man7.org(Linux man-pages: `resolv.conf`·`nsswitch.conf`·`su`·`iptables`),
  bind9.readthedocs.io(ISC BIND 9), httpd.apache.org(Apache HTTP Server 2.4), netfilter.org(netfilter·iptables). 강의와 면접은 이 주제를 다루지 않으므로 근거로 쓰지 않는다. `sourcePages`는 `[0, 0]`이다(ADR-059).
- 무엇까지 쓸지는 **기출이 묻는 사실과 그것을 이해하는 데 필요한 바탕**으로 정했다(ADR-059 「범위」). 기출 41문항(`dns` 25·`linux-servers` 16)이 묻는 것은 이렇다.
  - `dns`: TTL(캐시에서 만료되기까지의 시간, 짧고 길게 잡을 때의 효과 — 4회), 이름과 주소의 짝을 적는 `/etc/hosts`(3회), 레코드(CNAME 별칭 3회, SOA와 그 필드 4회, 역방향 조회와 PTR 3회, NS는 메일과 관계없다 1회),
    TCP와 UDP를 모두 쓰는 응용 프로토콜(2회), 재귀적 질의, DNS의 역할(보안 장비가 아니다), DNS 라운드 로빈, 호스트 이름 규칙(특수 문자를 쓰지 않는다), DNSSEC(무결성과 출처 인증 — 암호화가 아니다).
    25문항 가운데 14문항이 Windows Server의 DNS 서버나 Linux BIND 문맥이다 — 그래서 레코드는 표준 이름으로 가르치고, Windows DNS 관리자의 메뉴 이름(새 호스트·새 별칭·정방향 조회 영역 등)을 해당 항목에 한 줄씩 짝지어 둔다.
  - `linux-servers`: DNS 서버의 주소를 적는 `/etc/resolv.conf`, BIND의 `named.conf`(`options` 문의 `directory`·`listen-on`·`allow-query`·`dnssec-validation`·`masterfile-format`, 운영할 때 열어야 할 포트와 설정 검사 명령),
    Apache의 `httpd.conf`(보안 설정을 하는 파일, `Listen`으로 포트 바꾸기, 1024 아래 포트와 관리자 권한, `KeepAliveTimeout`, `LimitRequestBody`, `Options Indexes`의 디렉터리 목록), `iptables`로 들어오는 연결 막기.
  공식 문서에 있다는 이유만으로 기출이 묻지 않는 것(DNS 메시지 형식의 칸 전부, EDNS의 옵션, DNSSEC의 키 관리, BIND의 `view`·ACL 문법 전체, Apache의 가상 호스트·모듈 전체·MPM, iptables의 `nat` 테이블·연결 추적,
  `nslookup`·`dig`, 패키지 관리 명령 `rpm`·`yum`, `sudo`)을 끌어오지 않는다 — 아래 표의 「다룰 것」이 범위다.
- 앞 phase가 만든 주제는 고치지 않는다. 이미 다른 주제에 있는 것 — DNS 포트 `53`이 UDP·TCP 둘 다라는 것(`ports.well-known-ports`), DNS가 주로 UDP를 쓰는 까닭(`tcp-udp.udp`·`tcp-udp.transport-choice`),
  DHCP가 DNS 서버 주소를 알려 준다는 것(`ip-address-types.dhcp`), 메일 서버를 MX 레코드로 찾는다는 것(`app-protocols-mail-file.email-delivery`), `ipconfig /displaydns`·`/flushdns`와 `nslookup`(`diagnostic-commands.ipconfig-options`),
  잘 알려진 포트와 1024 아래 포트의 권한(`ports.well-known-ports`), 데몬과 `systemctl`(`linux-process-boot`), 심볼릭 링크(`linux-filesystem`), Telnet·SSH(`app-protocols-mail-file`) — 은 이 phase의 개념으로 다시 만들지 않는다.
  이 phase의 개념은 그것을 **쓰는 쪽**을 다루고, 필요한 바탕은 이 주제 화면에서 한 줄로 다시 푼다(「글」). 앞 주제와 뜻·값이 어긋나지 않게 그 개념을 먼저 읽는다.
- 사실은 표준·공식 문서로 확인한 것만 쓴다. **step 0·5·9는 그 주제가 쓸 사실을 확인하는 출처 step이다**(데이터·코드를 고치지 않는다). `dns`는 개념이 14개라 출처 step을 둘(앞 8개는 step 0, 뒤 6개는 step 5)로 나눴다.
  출처 step 하나가 확인할 개념은 9개 이하다(phase 76 step 0이 개념 15개로 제한 시간을 넘겼다).
- 네트워크 개념은 **개념마다 도식이 하나 이상**이다(ADR-056). 그것을 `src/components/diagrams/networkDiagramCoverage.test.ts`가 지키므로, 개념을 `topics.json`에 넣는 step은
  **그 개념의 글·문항·도식을 한 step에서 함께** 만든다. 글만 먼저 넣으면 도식이 붙을 때까지 테스트가 실패하고, 저장소의 Stop 훅(`scripts/hooks/codex-verify-gate.sh`)이
  실패한 상태로는 step을 끝내지 못하게 한다. 그래서 개념 step은 **개념 2개씩**(혼자 남는 개념은 1개) 글 → 문항 → 도식 순서로 만든다.
- **step 하나는 제한 시간 안에 끝나야 한다.** 개념 2개 step이 phase 77·78에서 20~30분이었다(Stop 훅의 lint·build·test가 5~8분 더 든다).
  그래서 이 phase의 step은 **브라우저 화면 실측(개발 서버·headless Chrome·CDP)을 하지 않는다** — phase가 끝난 뒤 메인 세션이 모든 도식을 한꺼번에 실측한다.
  시간을 아끼려고 검증 명령을 건너뛰지는 마라 — 아래 공통 AC는 모두 돌린다.
- **진행 안내 문장을 쓰지 않는다.** 「바로 다음 개념에서 다룬다」, 「이 주제의 뒤쪽에서 자세히 다룬다」, 「SOA는 아래에서 자세히 본다」처럼 글의 진행만 알리는 말은
  `src/data/network/data.test.ts`의 「요약과 문단에 「다음 개념에서 다룬다」 같은 진행 안내가 없다」 테스트가 막는다(WRITING_GUIDE 「본문 작성 원칙」).
  뒤 개념이 자세히 다룰 낱말이 지금 필요하면 그 자리에서 한 줄로 풀고 넘어간다. 「앞 개념에서 본 것처럼」 같은 되짚기는 써도 된다.

## 두 주제와 개념 23개

주제 객체를 `topics.json`의 두 자리에 끼운다 — 주제 지도의 순서대로다.

- `dns`는 **`tcp-connection` 바로 뒤, `app-protocols-mail-file` 앞**(지도의 17·18번 `tcp-retransmission`·`tcp-flow-congestion`은 아직 없다).
- `linux-servers`는 **`linux-accounts` 바로 뒤** — 지금 네트워크 주제 배열의 맨 끝이다(지도에서 그 뒤인 Windows 주제는 아직 없다).

```json
{ "id": "dns", "title": "DNS", "importance": 3, "sourcePages": [328, 351], "concepts": [ … ] }
{ "id": "linux-servers", "title": "Linux 서버 설정", "importance": 2, "sourcePages": [0, 0], "concepts": [ … ] }
```

개념 id는 `<주제 id>.<슬러그>`다. 표의 순서·슬러그·`name`·`parentId`를 바꾸지 않는다(바꿔야 할 이유가 있으면 바꾸지 말고 summary에 적는다).
`parentId` 열의 값은 같은 주제의 슬러그다 — JSON에는 `dns.dns`처럼 전체 id로 쓴다. 딸린 개념은 부모 바로 뒤에 이어 둔다(ADR-041 — 두 단까지만).
「다룰 것」은 범위다. 문장은 직접 쓰고, 사실은 아래 「출처」대로 가져온다. 「step 0 결과」·「step 5 결과」·「step 9 결과」라고 적힌 사실은 그 step의 summary와 출처 문서에 적힌 처리를 따른다 —
확인되지 않았으면 쓰지 않고, 시험만 그렇게 보면 「자격시험은 ~로 본다」로 쓴다. 기출 표기 `[기출 날짜 #번호]`는 정답을 확인할 곳이다(문장은 옮기지 않는다).

IP 주소는 숫자라 외우기 어렵고 바뀔 수도 있다(p330–p332) → 사람이 읽기 쉬운 이름인 **도메인 이름**과 IP 주소를 짝지어 찾아 주는 시스템(p333). 이름으로 주소를 찾는 일을 부르는 말(이름 풀이 — name resolution)은 step 0 결과대로. 모든 이름을 한 곳이 갖지 않고 여러 서버가 나눠 갖는 **분산 데이터베이스**라는 것(근거는 step 0 결과대로, [기출 2025-05-25 #17]). 이름으로 주소만이 아니라 그 이름에 딸린 다른 정보(메일을 받는 서버 등)도 찾는다는 것은 근거대로 한 줄.   루트·TLD 네임 서버는 실제 주소를 쓰지 않고 「루트 네임 서버」·「`com` TLD 네임 서버」처럼 이름표로만 쓴다.
- **이름**: RFC 2606의 문서용 도메인만 — `example.com`(영역), `www.example.com`, `mail.example.com`, 네임 서버 `ns1.example.com`(주 서버)·`ns2.example.com`(보조 서버), 책임자 `hostmaster@example.com`(SOA에서는 `hostmaster.example.com.`).
- **TTL·SOA**: 레코드 TTL `3600`(1시간). SOA는 MNAME `ns1.example.com.`, RNAME `hostmaster.example.com.`이고 나머지 수(일련번호·간격들)는 step 5가 정해 예시 값이라고 밝힌다 — 수가 권고값처럼 읽히지 않게 한다.
- **Linux 서버**: `/etc/resolv.conf`의 `nameserver 192.0.2.53`·`nameserver 192.0.2.54`·`search example.com`, BIND가 맡는 영역 `example.com`, Apache의 `DocumentRoot "/srv/www/example"`·`Listen 8080`·`KeepAliveTimeout 15`·`LimitRequestBody 1048576`,
  iptables의 `--dport 8080`(막기)과 `--dport 53`(DNS 허용). 경로·수는 예시 값이고 그렇게 밝힌다 — 배포판의 기본 경로처럼 말하지 않는다.
- **이름표**: 「클라이언트」·「웹 브라우저」·「로컬 DNS 서버」·「주 서버」·「보조 서버」처럼 대상을 가르는 이름표는 사실 주장이 아니다.
- **문항은 본문과 다른 값을 쓴다** — 다른 이름(`example.org`·`example.net` 아래), 다른 주소(`192.0.2.30`, `203.0.113.10` 등 문서용 대역 안), 다른 TTL, 다른 포트(`8000` 등), 다른 크기.
- **기출 상황의 값을 옮기지 않는다** — 사람 이름(`Kim`·`Park`·`Gang`), `fastcampus.co.kr`, `icqa.or.kr`, `8081`, `KeepAliveTimeout 80`, `/var/named`, `/var/www/html`, `/etc/httpd`, `root@localhost`, `192.168.0.0/24`,
  기출의 iptables 규칙 넷과 보기 묶음(「문항」 11항)을 본문·문항·도식에 쓰지 않는다.

도식은 본문에 나온 예시 값만 쓴다(ADR-038) — 그러니 이 값들을 도식에 쓰려면 그 개념의 본문에 먼저 쓴다.

## 글 — `docs/WRITING_GUIDE.md`를 따른다(ADR-056)

- `summary`는 WRITING_GUIDE 2절 — 처음 보는 사람이 일상 말로 「무엇이고 무슨 역할인지」 알게 하는 한 문장. 다른 전문용어를 알아야 이해되면 안 되고, 제목 낱말을 되풀이하는 순환 정의, 포트 번호·필드 이름·지시자 값·수치·분류를 넣지 않는다.
- `paragraphs`는 3절의 흐름(개념 → 원리 → 예시 → 특징)을 필요한 만큼. 누가·무엇을·어디서 어디로를 빠뜨리지 않는다. 같은 말을 되풀이하지 않는다.
  헷갈리는 짝(hosts 파일과 DNS, hosts 파일과 `resolv.conf`, 도메인과 영역, 루트·TLD·권한 있는 서버와 로컬 DNS 서버, 주 서버와 보조 서버, 재귀적 질의와 반복적 질의, DNS의 TTL과 IP의 TTL, TTL을 짧게와 길게,
  A와 AAAA, A와 CNAME, NS와 MX, 정방향 조회와 역방향 조회, A와 PTR, UDP `53`과 TCP `53`, DNSSEC의 서명과 암호화, `named.conf`와 영역 파일, `options` 문과 `zone` 문, `allow-query`와 `listen-on`,
  `Listen`과 `KeepAlive`, root로 시작한 부모와 자식 프로세스, `KeepAliveTimeout`과 `Timeout`, `Indexes`를 켤 때와 끌 때, `INPUT`과 `OUTPUT`, `DROP`과 `REJECT`)은 4절대로 무엇이 다르고 왜 나눠 부르는지를 말한다.
- **주고받는 차례를 따라 할 수 있게 쓴다.** 질의·응답을 주고받는 개념(`dns`·`hosts-file`·`dns-zone`·`name-resolution`·`recursive-iterative-query`·`dns-cache-ttl`·`dns-round-robin`·`dns-transport`·`dnssec`·`resolv-conf`·`apache-keepalive`)은
  누가 누구에게 무엇을 묻고(어느 포트로, 어떤 이름을), 무엇을 돌려받고, 그 결과 무엇이 달라지는지(캐시에 남는다, 다음 서버에 묻는다)를 차례대로 쓴다.
- **설정은 따라 할 수 있게 쓴다.** 설정 파일의 줄(`/etc/hosts`의 한 줄, 레코드 한 줄, SOA, `resolv.conf`, `named.conf`의 문, `httpd.conf`의 지시자, iptables 규칙)을 보일 때는
  그 줄과 그 줄이 하는 일(그 줄 때문에 무엇이 달라지는지)을 함께 보인다. 줄의 꼴은 출처가 보이는 꼴을 따른다 — 출처가 꼴을 보이지 않으면 지어 보이지 않고 무엇을 적는지만 말로 쓴다. 값은 예시 값이라고 밝힌다.
  계산이 나오는 곳(`dns-cache-ttl`의 남은 TTL, `reverse-lookup`의 주소 뒤집기, `limit-request-body`의 바이트 수)은 예시 하나를 처음부터 끝까지 단계대로 보인다.
- **이 주제 화면만 읽고 뜻이 서야 한다.** 학습자는 주제 목록에서 아무 주제로나 바로 들어오므로, 다른 주제에 정의가 있다는 것은 도움이 되지 않는다.
  이 주제 안에서 처음 쓰는 낱말(호스트, IP 주소, 클라이언트·서버, 프로토콜, 캐시, UDP·TCP, 포트, 방화벽, 공개 키, 데몬, 설정 파일, 디렉터리, 웹 서버, 프로세스, root, 패킷, 커널 등)은 그 자리에서 짧게 푼다.
  앞 step이 같은 주제에서 이미 푼 낱말은 다시 풀지 않는다 — 쓰기 전에 그 주제의 앞 개념을 읽는다. 도식의 라벨·곁말·캡션도 화면의 글이다.
  다른 주제의 개념(DNS의 동작은 `linux-servers`에서, 포트·TCP·UDP는 두 주제 모두에서)을 가져다 쓸 때도 이 주제 안에서 한 줄로 푼다. 앞 phase가 쓴 말과 뜻을 맞춘다.
- **진행 안내 문장을 쓰지 않는다**(「배경」). 다른 주제나 뒤 개념을 가리키는 말이 필요하면 그 낱말을 그 자리에서 한 줄로 풀고, 「~에서 다룬다」·「~에서 자세히」·「다음 개념의」·「(다음 개념)」을 붙이지 않는다.
- 비유는 이해를 돕는 데만 쓰고, 실제 동작과 다르면 그 자리에서 밝힌다(예: DNS를 「전화번호부」에 비유한다면 무엇이 다른지). 비유로 사실을 대신하지 않는다.
- `name`은 명사구다(ADR-030 기준 1). **굵은 글씨(`**`)는 목록 항목의 이름에만** 쓴다(ADR-055). 목록 개념은 소개 문단 하나 뒤에 `- **이름**(English name)은 …` 꼴 항목을 두고, 항목은 혼자 서지 않는다(ADR-046).
  **굵은 글씨 안에 백틱을 넣지 마라** — `src/components/EmphasizedText.tsx`는 `**…**` 안의 백틱을 코드로 바꾸지 않아 백틱이 글자로 보인다. 그래서 항목 이름은 둘 중 하나로 쓴다.
  (1) 한국어 이름에 영문 이름, 또는 약어가 곧 이름인 것: `- **루트 네임 서버**(root name server)는 …`, `- **CNAME**(Canonical Name)은 …`, `- **SERIAL**은 …`.
  (2) 지시자·옵션이 이름인 항목은 하는 일을 한국어 이름으로 세우고 그 지시자를 괄호 안 코드 표기로 붙인다 — phase 76·78과 같은 꼴이다. 예: `- **영역 파일 디렉터리**(`directory`)는 …`.
  목록 개념도 항목 뒤에 문단을 더 둘 수 있다(선례 `routing.routing-table`, phase 78의 `diagnostic-commands.ipconfig-options`).
  위 표에서 굵게 적은 말(예: 「**분산 데이터베이스**」, 「**영역**」)은 이 문서의 강조일 뿐이다 — 목록 항목이 아닌 문단에서는 굵게 쓰지 않는다.
- 관용 표현(`돌린다`·`띄운다`·`태운다`·`물린다`·`던진다`·`쏜다`·`찍는다`)을 쓰지 않고 하는 일을 그대로 쓴다(ADR-030 기준 5) — 질의를 「던진다」가 아니라 「보낸다」. 평서문 「~다」로 쓴다.
- 「A vs B」 제목은 쓰지 않는다(ADR-055·ADR-059).
- 포트 번호·주소·도메인 이름·파일 경로·명령·지시자·옵션·레코드 한 줄·TTL 값은 백틱으로 감싼다(ADR-044 — 선례 phase 75~78의 본문). 레코드 유형 이름(A·CNAME·SOA)과 필드 이름(SERIAL·REFRESH),
  프로토콜 이름(DNS·UDP)은 문장에서 설명할 때 백틱 없이 쓴다(선례 `tcp-connection`의 상태 이름, `ip-protocol`의 필드 이름). 개념의 `name`에는 백틱을 쓰지 않는다.

## 문항 — WRITING_GUIDE 「객관식 문제의 문장과 선택지 구성 원칙」과 ADR-054·ADR-030

가장 중요한 원칙: **질문은 쉽게 이해할 수 있도록, 선택은 충분한 생각이 필요하도록.**

1. **정의에서 이름만 지운 「무엇인가?」 꼴을 내지 않는다.** 개념에 맞는 방식 하나를 고른다 — 개념 확인, 원리 이해, 상황 적용, 개념 비교, 원인과 결과. 고른 방식과 이유를 summary에 적는다.
   DNS 문항은 「이 이름을 풀 때 무엇이 일어나나」·「이렇게 바꾸면 무엇이 달라지나」 꼴의 상황으로, 설정 문항은 「이 일을 하려면 어느 줄을 고치나」·「이 줄이 있으면 무엇이 달라지나」 꼴로,
   레코드·규칙 읽기 문항은 본문과 다른 값의 줄을 주고 칸을 읽게 한다.
2. **사람이 사람에게 묻듯 쓴다.** 소리 내어 읽어 어색하거나 한 번에 이해되지 않으면 다시 쓴다. 쉼표로 조건을 줄줄이 잇는 압축문을 쓰지 않는다.
3. 무엇을 묻는지는 첫 읽기에 분명하고, 어려움은 보기를 고르는 데서 나온다. 문제문을 비틀어 난이도를 만들지 않는다.
   **문제문이 답의 이유를 먼저 알려 주지 않는다** — phase 75의 n115는 문제문에 이유를 적어 개념을 몰라도 「예」를 고를 수 있었고, 사용자 검토에서 고쳤다.
   예/아니요의 주장은 개념을 알아야 판단할 수 있는 결과나 동작으로 세운다.
4. 보기는 기술적으로 갈리고 정답은 하나다. 비슷한 개념을 보기로 둘 때는 그 차이를 판단할 조건을 문제문에 준다. 오답은 문제문이 묻는 범주 안에서, 실제로 헷갈리는 것에서 고른다(ADR-030 기준 4).
   정답의 이름이나 그 일부를 문제문에 쓰지 않는다(기준 3). 보기 넷은 서로 다르다. **설정·계산 문항의 오답은 흔한 실수에서 나온 값으로** 고른다 — 주소의 네 수를 거꾸로 적지 않은 것,
   `in-addr.arpa`를 앞에 붙인 것, NS와 MX를 바꾼 것, `INPUT`과 `OUTPUT`을 바꾼 것, `tcp`와 `udp`를 바꾼 것, `listen-on`과 `allow-query`를 바꾼 것, 남은 TTL을 지난 시간으로 읽은 것.
   **설정 보기는 하나만 맞는지 실제로 따져 본다** — 같은 결과를 내는 다른 줄이 오답에 끼지 않게.
5. 판단에 쓰이지 않는 정보(전문용어·수치·조건·부정문)를 늘어놓지 않는다. 판단에 필요한 조건은 남긴다.
6. **형식(ADR-054)**: 흔히 오해하는 것을 바로잡으면 예/아니요, 비슷한 개념을 구별하거나 계산하면 4지선다, 상황을 주는 문항은 문제문의 모양으로. 같은 범주의 그럴듯한 오답 셋을 출처 안에서 쓸 수 없으면 예/아니요.
   예/아니요는 주장 하나, 이중 부정·「항상」「절대」「반드시」·「~만」 금지, 「~인가요?」「~나요?」로 끝난다. **아니요 문항의 해설은 무엇이 틀렸는지에서 그치지 않고 맞는 사실을 가르친다.**
   예/아니요의 주장은 맞는 쪽으로도 틀린 쪽으로도 세울 수 있다 — 아래 균형을 맞추려고 주장의 방향을 고른다. step 문서가 적은 방향은 계획이고, 균형 규칙이 먼저다.
7. **문항은 풀면서 배우게 쓴다.** 문항은 섞여 나오고 랜덤 세트는 일부만 뽑으므로 혼자 읽혀야 한다. 문제문이 이 주제 밖의 낱말을 풀이 없이 전제하지 않는다(기준 5).
   상황에 쓰는 이름(「사무실 PC」, `www.example.org`)·숫자는 사실 주장이 아니어야 하고, 그 상황의 정답은 출처의 사실로 정해져야 한다. 문항 상황은 본문 예와 다르게 만들어 본문 문장을 외워서 풀리지 않게 한다
   (「예시 값」의 「문항은 본문과 다른 값」). 기출의 값(「예시 값」의 마지막 줄)도 쓰지 않는다.
   **문항 글에 백틱을 쓰지 않는다** — 퀴즈 화면(`QuizRunner`)은 문제문·보기·해설을 글자 그대로 그려 백틱이 기호로 보인다(phase 78 통독에서 n198·n199를 고쳤다). 이름·경로·지시자는 백틱 없이 그대로 적는다.
8. **해설은 187자 이상**이고 그 개념을 가르치는 글이다(ADR-026·027). 4지선다는 정답이 왜 맞는지와 오답 셋이 각각 왜 아닌지를 담는다. 계산 문항의 해설은 계산을 단계대로 보인다. 약어는 해설마다 처음 쓸 때 풀어 쓴다.
   같은 말을 늘려 길이를 채우지 않는다. 해설의 사실은 개념 본문이나 출처 문서에 있는 것이다. 해설도 평서문 「~다」로 쓴다.
9. **균형 — step이 끝났을 때 과목 전체에서**: 예/아니요의 예와 아니요 수 차이 **1 이하**, 4지선다의 정답 위치(`answerIndex` 0~3) 수의 최대·최소 차이 **2 이하**.
   phase 79 시작 때는 문항 225개, 예/아니요 85개(예 42·아니요 43), 4지선다 140개(정답 위치 35/35/35/35)다. step 문서의 방향·정답 위치 계획대로 가면 끝에 예/아니요 99개(예 49·아니요 50), 4지선다 156개(정답 위치 39/39/39/39)가 된다.
10. 한 문항은 개념 하나만 묻는다(ADR-030 기준 2). 같은 개념의 두 문항은 서로 다른 것을 묻는다.
11. 기출 문항의 문장·보기 구성을 옮기지 않는다 — 시험이 같은 사실을 물어도 상황과 문장은 직접 만든다. **기출과 같은 보기 넷 묶음**은 정답만 바꿔서도 쓰지 않는다 —
    보기의 범주를 바꾸거나(레코드 유형 이름 대신 그 레코드가 담는 데이터를 보기로, 지시자 이름 대신 그 줄이 있을 때의 결과를 보기로), 보기 가운데 둘 이상을 다른 것으로 바꾸거나, 상황을 바꿔 그 사실을 이해했는지 묻는다.
    이 phase의 기출 보기 묶음(정답만 바꿔도 쓰지 않는다):
    - `dns`: TTL 설정 효과(짧으면 부하·정하지 않으면 정방향 조회 불가·캐싱 주기·길면 갱신 늦음), SOA 설명(영역 파일의 시작·네임 서버를 유지할 기본 자료·Refresh는 동기 주기·TTL이 길면 부하),
      SOA 필드(일련번호·주 서버·책임자 메일 표기·새로 고침 간격), Windows 레코드 짝(A 32비트·AAAA 128비트·CNAME 가상 이름·NS 사서함 라우팅), 레코드 추가(새 호스트·새 포인터·새 별칭은 서브 도메인·새 메일 교환기),
      DNS 설명(기억하기 쉬운 이름·분산 데이터베이스·계층 구조·`@`·`#` 특수 문자), DNS 설정 방식(Round Robin·Cache Plugin·Cache Server·Azure AutoScaling), DNSSEC 설명(캐싱 메커니즘·무결성과 출처 인증·Windows Server 미지원·모든 질의 암호화),
      DNS 역할(방화벽 같은 보안 장비 등).
    - `linux-servers`: DNS 서버 주소 파일(`resolv.conf`·`networks`·`protocols`·`services`), BIND 운영(UDP 53번만·`iptables`·`rpm -qa`·`named-checkconf`), named.conf 디렉터리(`directory`·`listen-on`·`dump-file`·`allow-query`),
      named.conf `options` 해석(질의 대역 모두 허용·유효성 검사 오류 없음·53번 외부 접근·보조 서버의 text 동기화), Apache 설정 파일 이름(`httpd.conf`·`httpd-default.conf`·`httpd-vhosts.conf`·`httpd-mpm.conf`),
      포트 바꾸기(`KeepAlive`·`DocumentRoot`·`StartServers`·`Listen`), 포트 바꾸기 꼴(`Port`·`Default Port`·`Listening`·`Listen`), 잘 알려진 포트 주의(관리자 권한·명령 앞 `su`·충돌·1~1023),
      세션 종료 지시자(`Exec-timeout`·`Listen`·`KeepAliveTimeout`·`NameVirtualHost`), 요청 크기(`KeepRequestSize`·`LimitRequestBody`·`RestrictBodyRequest`·`PostRequestSize`),
      디렉터리 목록(`Options FollowSymLinks Indexes`·`ServerAdmin`·`DocumentRoot`·`ServerRoot`), 바깥 Telnet 막기 규칙 넷(`OUTPUT` tcp 23·`INPUT` udp 23·`INPUT` tcp 23·`INPUT` tcp 21).
    지문이 빠진 기출(`/etc/hosts` 셋, 재귀적 질의, SOA 하나)은 보기만 남았다 — 그 보기 묶음도 쓰지 않는다. 문항을 쓰기 전에 그 개념의 기출 문항(`docs/source/network/raw/exam/data.txt`에서 그 주제로 분류한 줄과 교사용 텍스트의 그 문항)을 읽고 보기 묶음이 겹치지 않는지 본다.

검수 — 문항마다 WRITING_GUIDE 객관식 7항의 여섯 질문으로 다시 읽고, 보기마다 「이것이 정답이라고 우길 수 있는가」를 따진다. 문제문만 읽고 보기를 보지 않은 채 정답 글자를 짐작할 수 있지 않은지도 본다.
계산·설정 문항은 정답을 손으로 다시 따지고(주소를 한 수씩 뒤집어, TTL을 초 단위로, 규칙을 조각마다), 오답 셋이 정말 틀렸는지도 따진다.

## 도식 — 개념마다 하나 이상

선례는 phase 73~78의 도식들이다 — `src/components/diagrams/`의 `ThreeWayHandshakeDiagram`·`SmtpDialogueDiagram`(두 장치 사이를 오가는 차례), `MailPathDiagram`·`ArpHopsDiagram`(길과 구간),
`RoutingTableDiagram`·`FstabFieldsDiagram`·`PasswdFieldsDiagram`(표 모양과 줄의 칸), `DirectoryTreeDiagram`(나무), `ChmodChangeDiagram`·`IpconfigOptionsDiagram`(명령·설정 전과 뒤), `NetstatLinuxOptionsDiagram`(명령 줄의 조각)과 그 `.test.tsx`,
`src/data/network/visuals/tcp-connection.json`·`app-protocols-mail-file.json`·`diagnostic-commands.json`·`linux-accounts.json`. 규칙의 근거는 UI_GUIDE 「도식 전용 색상」·「도식」 절 전체, ADR-036·037·038·047·048·056, `src/components/diagrams/CLAUDE.md`다.
사용자 미리보기 승인을 받지 않고 **step이 좌표를 설계한다.** 그래서 기계 검사를 모두 통과시키고 설계를 summary에 남긴다.

- **파일**: 컴포넌트는 `src/components/diagrams/<이름>Diagram.tsx`(이름이 `Diagram.tsx`로 끝나야 교차 검사와 커버리지 테스트가 도식으로 본다), 테스트는 같은 이름의 `.test.tsx`.
  문구(물음형 제목 `question`·노드 라벨·곁말·캡션·`idleCaption`·`legend`·figure `label`·`svgLabel`·시나리오·`sources`)는 그 주제의 `src/data/network/visuals/<주제 id>.json`의 `diagrams["<키>"]`에 둔다.
  `glossary`는 빈 배열이다(ADR-037·ADR-055). 도식 이름과 키는 step 문서가 정한다 — 이미 있는 도식 이름과 겹치지 않는 것을 골라 두었다.
- **사실은 본문에만 있는 것**(ADR-036). 캡션·곁말·라벨의 사실마다 그 개념(과 같은 주제의 다른 개념) 본문의 문단을 근거로 댈 수 있어야 한다. 예시 값도 본문에 나오는 것만(ADR-038).
  「클라이언트」·「로컬 DNS 서버」·「웹 브라우저」처럼 대상을 가르는 이름표는 사실이 아니므로 써도 된다. 글과 도식을 같은 step이 만드므로, 도식에 필요한 사실은 **글에 먼저 쓴다** — 출처에 없으면 그리지 않는다.
  「자격시험은 ~로 본다」로만 쓴 것은 공식 문서의 사실이 아니므로 **도식에 사실처럼 그리지 않는다.**
- **말**: 노드 라벨·곁말은 본문에 쓰인 말과 같게 쓴다. 라벨을 줄이거나 영문 약어로 바꿔 폭을 맞추지 마라 — 노드를 넓히거나 배치를 바꾼다.
- **글자 크기**: 노드 라벨 10, 그룹 라벨·곁말 9(viewBox 단위). `estimateTextWidth(라벨, 10) + 12 <= 노드 폭`. 노드 높이는 32다(교차 검사기가 32로 본다 — 키 큰 노드를 만들지 말고 그룹 박스를 쓴다).
- **글자 폭의 여유**: `estimateTextWidth`는 반각 문자(영문·숫자·기호)를 0.55em으로 보지만 실제 화면에서는 0.61em까지 넓다(phase 72 화면 실측). 이 phase의 라벨은 도메인 이름·주소·경로·지시자·규칙 조각(`10.100.51.198.in-addr.arpa.`·`LimitRequestBody 1048576`)처럼 **반각 문자가 많고 길다**.
  그래서 반각 문자가 섞인 노드 라벨·곁말·그룹 라벨은 `estimateTextWidth` 값의 **1.15배**를 폭으로 잡아 노드 폭·배치를 정하고, 그 범위가 둘레 박스와 `viewBox` 안에 들게 한다(phase 73~78이 이렇게 해서 화면 실측 걸침 0이었다).
  280 폭에 들지 않는 긴 이름은 줄이지 말고 노드를 한 줄 전체 폭으로 쓰거나, 이름을 레이블 단위 노드 여럿으로 나눠 놓는다(그 나눔이 본문의 설명과 같을 때만).
- **주고받는 차례 그림**(질의와 응답, 영역 전송, 지속 연결): 두 장치를 세로 줄(왼쪽·오른쪽 두 기둥 — 가로형도 같은 꼴로 폭만 넓힌다)로 두고,
  메시지 하나를 노드 하나로 두 기둥 사이에 위에서 아래로 차례대로 놓는다. 방향은 노드 양옆의 짧은 화살표 경로로 보인다(선례 `ThreeWayHandshakeDiagram`). **비스듬한 선을 쓰지 마라** — 경로는 직교만 된다.
  280 폭에서 한 줄에 노드 넷 이상을 나란히 두지 마라 — 세로로 쌓거나 그룹 박스로 묶는다.
- **여러 서버를 차례로 묻는 그림**(이름 풀이, 재귀적·반복적 질의): 클라이언트와 로컬 DNS 서버를 한쪽에, 루트·TLD·권한 있는 서버를 다른 쪽에 위에서 아래로 놓고, 질의·응답마다 번호 곁말(①②…)을 단 직교 경로로 잇는다.
  경로가 많아 겹치면 시나리오로 나눠 한 번에 보이는 경로를 줄인다.
- **나무 그림**(도메인 계층, DNSSEC의 믿음 사슬): 위에서 아래로 직교 경로(M/H/V)로 잇는다(선례 `DirectoryTreeDiagram`). 280 폭에 가지가 들지 않으면 한 갈래만 그리고 곁가지는 본문이 말한다.
- **줄과 칸 그림**(hosts 줄, 레코드 줄, SOA 필드, `resolv.conf`, `named.conf`의 `options`, `httpd.conf`의 지시자, iptables 규칙): 칸을 빈틈없이 이은 노드 줄이나 「칸 이름: 값」 줄 여럿으로 그린다(선례 `FstabFieldsDiagram`·`PasswdFieldsDiagram`).
  여러 열 표를 280 폭 한 줄에 억지로 넣지 마라. 명령·규칙 한 줄은 글자 하나씩이 아니라 뜻이 갈리는 조각 하나를 노드 하나로 그린다(선례 `NetstatLinuxOptionsDiagram`).
- **설정 전과 뒤 그림**(`Indexes`를 켤 때와 끌 때, 한도 안과 밖의 요청): 같은 요청의 두 결과를 시나리오로 나눈다. 시나리오마다 다른 결과 노드는 다른 id를 다른 자리에 둔다 — 같은 자리에 겹쳐 두고 opacity로 가리지 마라.
- **색**: 노드는 모두 회색(`stroke-disabled`, 선례와 같은 클래스). 도식 전용 두 색(`diagram-managed`·`diagram-resource`)은 AWS 계층의 뜻이라 쓰지 않는다. 초록·빨강·주황, 16진 색, 이모지, O/X, 자물쇠 그림도 쓰지 않는다(ADR-036).
  강조는 opacity로만 한다 — 선택 밖 노드 `0.25`, 그룹 박스는 흐려지지 않는다. 나쁜 상태(거절·버림·만료·멈춤·드러남)는 색이 아니라 곁말과 흐림·사라지는 경로로 보인다(UI_GUIDE 「수량과 상태를 바꾸는 도식」).
  서명으로 확인된 것과 아닌 것, 암호화되지 않은 것은 색이 아니라 곁말(본문의 말)로 가른다.
- **두 배치**: 세로형(`viewBox` 폭 280)과 가로형(폭 440)을 함께 만든다. 가로형은 `useWideDiagram()`이 `true`일 때 쓴다. `nodes`·`wideNodes`·경로·`wideGroups`·`wideNotes`를 **한 줄에 하나씩 글자 그대로** 적는다 —
  반복문이나 계산으로 만들지 마라(교차 검사기가 글자로 읽는다). 노드 id·경로 id·시나리오·문구는 두 배치가 함께 쓰고, 고른 시나리오는 배치가 바뀌어도 유지된다.
- **경로**: 직교(M/H/V)만, 노드 변에서 시작하고 끝나며, 다른 노드 상자 안을 지나지 않는다. 늘 보이는 연결선도 같은 경로 선언 꼴(`'id': 'M…'`)로 적는다.
  화살표 마커는 선례와 같고 마커 id는 `useId`로 만든다. 그룹 라벨 영역을 지나는 선분이 없어야 한다.
  `phases/38-service-diagrams/tools/check-path-crossings.mjs`는 `*Diagram.tsx`의 `const nodes = [`·`const wideNodes = [` 블록에서 `{ id: '…', x: N, y: N, width: N` 순서를, 경로 객체에서 `'id': 'M…'`를 정규식으로 읽는다. 이 형식을 지켜라.
- **물음형 제목**(ADR-038): 그림이 답하는 것 하나를 학습자의 말로. step 문서의 예는 바꿔도 된다.
- **시나리오**: step 문서에 적힌 시나리오를 둔다. 「정지 그림」은 `scenarios` 없이 `idleCaption`이 캡션 노릇을 한다. 시나리오가 있는 도식은 `전체`(아무것도 고르지 않음)에서 노드가 모두 선명하다.
  두 시나리오의 「선명한 노드 + 보이는 경로 + 보이는 곁말」이 같으면 그 시나리오는 아무것도 가르지 못한다 — 다르게 설계한다. 캡션은 20자를 넘는다(`visuals.test.ts`).
- **금지**: SVG 두 개를 그려 놓고 CSS로 하나를 숨기지 마라. 기준 폭 문자열(`'(min-width: 768px)'`)을 도식 파일에 쓰지 마라(ADR-047). 흐르는 점·자동 재생·움직이는 메시지·깜박이는 커서 같은 애니메이션 금지.
  공용 컴포넌트(`DiagramFrame.tsx`·`ComparisonTableFigure.tsx`·`ConceptList.tsx`·`useWideDiagram.ts`)와 교차 검사기, `src/lib/svg-bounds.ts`를 고치지 마라.
- **registry**: `src/components/diagrams/registry.ts`의 `diagramsByConceptId`에 `'<개념 id>': <이름>Diagram` 한 줄씩. import는 기존 정렬(모듈 경로 알파벳순)을 따른다. 키는 두 자리에 끼운다 —
  `dns.*`는 `'tcp-connection.time-wait'` 줄 바로 뒤·`'app-protocols-mail-file.email-delivery'` 줄 앞에, `linux-servers.*`는 `'linux-accounts.login-records'` 줄 바로 뒤·`'azure-cloud-computing.consumption-based-model'` 줄 앞에 개념 순서대로. 기존 줄의 차례는 바꾸지 않는다.
- **주제의 시각 요소 파일**: 주제의 첫 개념을 넣는 step(`dns`는 step 1, `linux-servers`는 step 10)이
  `src/data/network/visuals/<주제 id>.json`(`{ "diagrams": {}, "tables": {}, "glossary": [] }` 꼴)을 만들고 `src/data/network/index.ts`의 `visualsByTopicId`에 `'<주제 id>'`로 넣는다
  (import 이름은 `dnsVisuals`·`linuxServersVisuals`이고 import 줄은 기존 정렬(경로 알파벳순)대로. `visualsByTopicId` 항목은 `'dns'`를 **`'tcp-connection'` 항목 바로 뒤·`'app-protocols-mail-file'` 앞**에,
  `'linux-servers'`를 **`'linux-accounts'` 항목 바로 뒤**(지금 맨 끝)에 둔다). 비교표는 이 phase에서 만들지 않는다.

### 도식 테스트 — 도식마다 먼저 쓰고 실패를 확인한 뒤 구현한다

`<이름>Diagram.test.tsx` — 선례와 같은 관문을 건다. 세로형은 `matchMedia` 없이, 가로형은 `describe('가로형 (768px 이상)', …)` 안에서만 `vi.stubGlobal('matchMedia', …)`.

1. 물음형 제목이 시나리오 버튼보다(정지 그림이면 SVG보다) 앞에 보인다(헤딩이 아니다).
2. 처음(`전체`)에는 노드가 모두 선명하다. 시나리오에만 쓰이는 경로는 보이지 않는다(늘 보이는 연결선은 보인다).
3. 시나리오마다 선명한 노드 집합, 보이는 경로, 보이는 곁말, 캡션이 JSON·step 문서의 설계와 같다. 선택 밖 노드는 opacity `0.25`, 그룹 박스는 흐려지지 않는다.
4. 모든 `rect`가 `boxesOutsideViewBox`로 `viewBox` 안이고, 노드 라벨이 `estimateTextWidth(라벨, 10) + 12 <= 노드 폭`이다. 곁말·그룹 라벨은 `estimateTextWidth(문구, 9)`로 잰 가로 범위가 `viewBox` 안이다.
5. 경로의 끝점이 노드 변 위에 있고, 어떤 선분도 다른 노드 상자 안과 그룹 라벨 영역을 지나지 않는다.
6. **그 도식의 요점** — step 문서에 도식마다 적힌 「요점 테스트」.
7. 두 번 렌더해도 화살표 마커 id가 겹치지 않는다. JSON의 시나리오 id 집합과 컴포넌트의 것이 같고, 문구를 JSON에서 읽는다.
8. `ConceptList`에 앵커 개념을 주면 본문 뒤에 이 도식이 온다.
9. 가로형: `viewBox` 폭 440, 래퍼에 `w-full`이 있고 `max-w-[380px]`·`-mx-4`가 없다. 노드·그룹 id 집합과 경로 id 합집합이 세로형과 같고, 3~6번을 가로형에서도 통과한다. 폭이 바뀌어도 고른 시나리오와 캡션이 유지된다.

정지 그림은 시나리오에 관한 항목(2의 경로 부분, 3, 7의 시나리오 id, 9의 선택 유지)을 「캡션이 `idleCaption`이고 버튼이 없다」로 바꿔 건다.

## 파일 형식

- `topics.json`: 주제 객체는 2칸 들여쓰기, `concepts` 배열의 개념은 **한 줄에 하나**(6칸 들여쓰기 + `JSON.stringify(concept)`). 개념 키 순서는 `id`, `parentId`(있을 때), `name`, `summary`, `paragraphs`.
  주제 키 순서는 `id`, `title`, `importance`, `sourcePages`, `concepts`(기존 주제와 같게). 앞 step이 쓴 줄과 다른 주제의 줄은 글자 하나도 바꾸지 않고, 자기 개념을 그 주제의 `concepts` 끝에 덧붙인다.
  **새 주제는 끼울 자리에 둔다** — `dns`는 `tcp-connection` 주제 객체 바로 뒤(`app-protocols-mail-file` 앞), `linux-servers`는 `linux-accounts` 주제 객체 바로 뒤(지금 배열의 맨 끝).
  끼운 자리의 앞뒤 쉼표와 줄바꿈이 기존 꼴과 같은지 본다.
- `questions.json`: `[` 다음 줄부터 **한 줄에 문항 하나**, 마지막 줄 뒤에 `]`. 키 순서 — 4지선다 `id`, `topicId`, `conceptId`, `format`, `prompt`, `choices`, `answerIndex`, `explanation` /
  예/아니요 `id`, `topicId`, `conceptId`, `format`, `prompt`, `answer`, `explanation`. 기존 줄은 바꾸지 않고 끝에 덧붙인다.
- 파일 끝 줄바꿈 하나. 스크립트로 쓸 때 CRLF로 바꾸지 않는다. JSON 문자열 안의 백슬래시(Windows 경로 `C:\Windows\…`)는 JSON 이스케이프(`\\`)로 적고, 화면에 원하는 글자로 보이는지 테스트나 `node -e`로 확인한다.
- 이 저장소의 TDD 훅은 테스트 파일 없이 새 `.js`·`.ts` 파일을 쓰지 못하게 막는다. 데이터를 고치는 일회용 스크립트가 필요하면 저장소 밖(임시 디렉터리)에 `.cjs`로 두거나 `node -e`를 쓴다.

## 개념을 넣는 step(1~4, 6~8, 10~14)의 공통 AC와 검증

```bash

npm run lint
npm test

node scripts/check-verbatim.mjs --subject network
node -e "const q=require('./src/data/network/questions.json');const yn=q.filter(x=>x.format==='yes-no');const ch=q.filter(x=>x.format==='choice');const pos=[0,1,2,3].map(i=>ch.filter(x=>x.answerIndex===i).length);console.log('문항',q.length,'마지막',q[q.length-1].id,'정답 위치',pos.join('/'),'예',yn.filter(x=>x.answer).length,'아니요',yn.filter(x=>!x.answer).length)"
git status --porcelain
```

- `check-verbatim`은 「전사 이상 없음」이고 **「원본 2개」를 대조했다고 나와야 한다**(`raw/`가 없으면 「건너뜀」으로 통과하므로 그때는 blocked로 멈춘다). `dns`는 강의 주제라 강의 문장과 겹칠 수 있다 — 대조 결과를 summary에 적는다.
  균형은 위 「문항」 9항, 교차 검사기는 「교차 없음」이고 노드·경로 수가 이 step이 더한 만큼 늘어야 한다(phase 79 시작 때 세로·가로 모두 노드 2139개·경로 1446개. 앞 step이 끝났을 때의 수는 그 step summary에 있다). **검사기를 고쳐서 통과시키지 마라.**
- **바뀌지 않아야 하는 것을 기계로 확인한다** — `git show HEAD:src/data/network/topics.json`·`questions.json`과 `visuals/*.json`을 지금 파일과 node로 읽어, 기존 주제 객체·기존 개념·기존 문항·기존 도식 문구가 통째로 같은지 본다.
  새 주제를 끼우므로 **주제 id의 차례**도 본다 — 기존 주제의 상대 차례가 그대로이고, `dns`가 `tcp-connection` 바로 뒤·`app-protocols-mail-file` 앞에, `linux-servers`가 `linux-accounts` 바로 뒤에(만든 것까지만) 있어야 한다.
- **문항 글에 백틱이 없는지 본다** — `node -e`로 `n226` 이후 문항의 `prompt`·`choices`·`explanation`에 백틱이 없는지 센다(「문항」 7항).
- **글로 읽는다** — 그 주제의 개념을 처음부터 이 step의 개념까지 처음 배우는 사람의 눈으로 통독하고, 풀이 없이 처음 나오는 낱말을 세어 본다(도식 문구 포함). 진행 안내 문장이 없는지도 본다. 불변식과 테스트는 이런 결함을 잡지 못한다.
  주고받는 차례와 설정 줄은 출처의 절·예시와 하나씩 대조하고, 계산이 나오는 곳은 손으로 다시 해 본다. **강의·공식 문서 문장을 옮기지 않았는지** 자기가 쓴 문장을 출처와 나란히 놓고 본다.
  브라우저 화면 실측은 하지 않는다(「배경」의 시간 제한 — phase 끝에 메인 세션이 한다).
- 이모지·O/X·빨강·초록·주황·도식 전용 두 색·16진 색·애니메이션·기준 폭 문자열이 새 파일에 없는지 `grep`으로 본다.
- 바뀐 파일은 `src/data/network/topics.json`·`questions.json`·`visuals/<주제>.json`(과 주제를 만드는 step은 `src/data/network/index.ts`), 새 도식 컴포넌트·테스트,
  `src/components/diagrams/registry.ts`, (더했다면) `docs/source/network/standards.md`, phase 메타데이터뿐이어야 한다.

**summary에 적을 것**(사용자가 이것을 읽고 판단한다): 개념마다 id와 **새 요약문 전문**, 문항마다 id·개념·형식·고른 방식·**문제문 전문**·정답, 균형 줄(예/아니요·정답 위치),

## 모든 step의 공통 금지

- **출처 문서에 없는 사실을 쓰거나 그리지 마라.** 이유: 원본에 없는 내용을 지어내지 않는 것이 이 저장소의 규칙이다(루트 CLAUDE.md, ADR-036). 필요하면 확인해서 `standards.md`에 먼저 더한다.
  설정 파일의 꼴, 명령의 출력, 질의와 응답의 차례도 사실이다 — 출처가 보이는 꼴이 아니면 지어서 보이지 마라.
- **강의·면접·기출·공식 문서의 문장을 옮기지 마라.** 이유: ADR-009·ADR-057. `check-verbatim --subject network`는 강의·면접만 대조하는 하한선일 뿐이다.
- **수정 이력에 걸린 강의·면접의 주장을 그대로 가르치지 마라.** 이유: 틀린 사실을 학습자가 외우게 된다(ADR-055). 특히 L11·L15·I11과 이 phase의 출처 step이 더한 L·I 번호.
- **불변식 테스트·커버리지 테스트를 고치거나 예외를 더하지 마라.** 이유: 테스트가 실패하면 데이터를 고치거나 도식을 그린다(ADR-026·ADR-056). 진행 안내 가드 테스트도 마찬가지다 — 걸리면 문장을 고친다.
- **자기 step의 개념이 아닌 개념을 만들거나, 앞 step이 쓴 글·문항·도식을 고치지 마라.** 이유: 범위가 겹치면 사용자가 무엇이 어디서 바뀌었는지 따라갈 수 없다.
  앞 개념에 고칠 것을 찾으면 고치지 말고 summary에 적는다.
- AWS·Azure 데이터와 앞 phase의 스물한 주제(`network-basics`·`protocols-encapsulation`·`ethernet`·`hub-switch-vlan`·`ip-protocol`·`arp`·`icmp`·`ip-addressing`·`ip-address-types`·`routing`·`ports`·`tcp-udp`·`tcp-connection`·
  `app-protocols-mail-file`·`app-protocols-mgmt-security`·`diagnostic-commands`·`linux-filesystem`·`linux-permissions`·`linux-shell`·`linux-process-boot`·`linux-accounts`)를 고치지 마라. 기존 테스트를 깨뜨리지 마라.
- **`docs/source/network/topic-map.md`·`CLAUDE.md`를 고치지 마라.** 이유: 이 phase는 주제를 더하거나 나누지 않고 새 출처를 더하지 않는다. `lecture-outline.md`·`interview-facts.md`는 출처 step(0·5)만 수정 이력을 더한다.
- **브라우저 실측을 하지 마라.** 이유: step 시간 제한(「배경」). 화면 확인은 phase 끝에 한꺼번에 한다.

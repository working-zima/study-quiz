# UI 디자인 가이드

## 디자인 원칙

1. **읽는 앱이다.** 본문 가독성이 다른 모든 것보다 우선한다. 장식이 읽기를 방해하면 장식을 뺀다.
2. **색은 의미일 때만.** 무채색이 기본이고, 색이 붙었다는 건 정답/오답/중요도 중 하나라는 뜻이다.
   도식 내부의 계층 구분 두 색만 예외이며 그것도 보조 채널이다(아래 「도식 전용 색상」, ADR-036).
3. **도구처럼 보여야 한다.** 랜딩 페이지가 아니라 매일 여는 학습 도구다. 히어로 섹션·마케팅 카피를 만들지 않는다.

## AI 슬롭 안티패턴 — 하지 마라

| 금지 사항 | 이유 |
|-----------|------|
| backdrop-filter: blur() | glass morphism은 AI 템플릿의 가장 흔한 징후 |
| gradient-text (배경 그라데이션 텍스트) | AI가 만든 SaaS 랜딩의 1번 특징 |
| "Powered by AI" 배지 | 기능이 아니라 장식. 사용자에게 가치 없음 |
| box-shadow 글로우 애니메이션 | 네온 글로우 = AI 슬롭 |
| 보라/인디고 브랜드 색상 | "AI = 보라색" 클리셰 |
| 모든 카드에 동일한 rounded-2xl | 균일한 둥근 모서리는 템플릿 느낌 |
| 배경 gradient orb (blur-3xl 원형) | 모든 AI 랜딩 페이지에 있는 장식 |
| 이모지 아이콘 (📚 ✅ 🚀) | 원본 PDF에는 있지만 UI에서는 쓰지 않는다 |

## 컴포넌트

### 카드 (주제 목록 항목)
```
rounded-lg bg-[#141414] border border-neutral-800 p-5 hover:border-neutral-700
```

#### 과목 카드 (과목 목록)

첫 화면(과목 목록, `#/`)의 과목 카드도 같은 카드 스타일이다. 카드 전체가 그 과목 홈으로 가는 링크다.
안에는 과목 이름(`text-lg font-medium text-neutral-100`, 주제 제목과 같다)과 그 아래 한 줄
「주제 N개 · 문항 M개」(`text-xs text-neutral-500`)만 둔다. 진행률·별점·설명은 넣지 않는다(ADR-053).

### 보기 버튼 (확인 문제)
```
기본:   w-full text-left rounded-md border border-neutral-800 bg-[#141414] px-4 py-3
선택:   border-neutral-600 bg-[#1f1f1f]
정답:   border-green-500/60 bg-green-500/5
오답:   border-red-500/60 bg-red-500/5
```
정답 공개 후에는 **정답 보기 하나만 활성으로 남기고 나머지는 비활성화한다.**
남겨 둔 정답 보기를 한 번 더 누르는 것이 다음 문제로 넘어가는 조작이다.
이유: 넘어가는 버튼을 본문 아래에 두면 문항마다 스크롤을 내려야 한다.
손가락이 이미 가 있는 자리에서 그대로 넘어가게 한다.

정답을 다시 고를 수 있다는 뜻이 아니다. 채점은 첫 선택으로 이미 끝났고,
두 번째 누름은 이동일 뿐 점수에 영향을 주지 않는다.

#### 예/아니요 버튼

```
[        예        ]  [      아니요      ]
```

```
묶음:   grid grid-cols-2 gap-3
버튼:   위 보기 버튼과 같은 클래스. text-left 대신 text-center
```

예/아니요 문항(ADR-054)은 버튼 둘을 **가로로 나란히** 둔다. 왼쪽이 「예」, 오른쪽이 「아니요」다.
이유: 나란히 두어야 보기가 둘뿐이라는 것이 한눈에 보인다. 글자를 가운데 두는 것은
짧은 낱말이 버튼 왼쪽에 붙으면 나란한 두 칸의 모양이 무너지기 때문이다.

- **순서를 섞지 마라.** 보기가 둘이라 위치가 답을 흘리지 않고, 섞으면 잘못 누르는 일만 는다.
- 선택·정답·오답 색, 정답 공개 후 정답 하나만 남기고 비활성화하기, 정답 재탭으로 넘어가기는
  위 보기 버튼과 같다.

#### 개념 펼치기

```
[ 보기 4 ]
─────────────────────────────────────
∨ 개념 보기
```

문제를 풀다 개념이 기억나지 않을 때 **화면을 벗어나지 않고 그 문항이 속한 주제의
개념 페이지를 펼친다.** 보기 블록 아래에 토글 하나를 두고, 열면 주제 제목과 그 주제의
**개념 전체**가 개념 읽기 화면과 같은 본문으로 그 자리에 나타난다.

- **근거 개념 하나만 펼치지 마라.** 개념은 이웃 개념과 대비될 때 이해된다. `q180`
  "다중 AZ 배포의 대기 인스턴스로 할 수 없는 작업은?"의 근거는 `multi-az-standby-limits`
  하나지만, **왜** 그런지는 같은 주제의 `features`(다중 AZ는 고가용성, 읽기 전용 복제본은
  읽기 확장)와 함께 읽어야 선다. 근거만 떼어 주면 답의 출처는 확인되고 이유는 남지 않는다.
- **개념 읽기 화면으로 보내지 마라.** 라우트를 옮기면 `QuizRunner`가 언마운트되고
  진행 위치·고른 보기가 사라진다. 돌아와도 1번 문항부터 다시 섞인 세트가 나온다.
  ADR-011·012가 순서를 저장하지 않기로 했으므로 **나가면 반드시 잃는다** — 그래서
  나가지 않는 쪽으로 푼다. 헤더에 "근거 개념" 링크를 되살리지 마라.
- **정답을 고르기 전에도 열린다.** 채점을 기다리지 않고 개념을 확인하는 통로가 필요하다.
  위치가 보기 아래로 고정이라 정답 공개 여부에 따라 자리가 옮겨 다니지 않는다.
- **분량을 이유로 범위를 좁히지 마라.** 가장 큰 주제가 개념 11개·3043자다(20개 주제 실측).
  사용자가 일부러 여는 펼치기이므로 길면 스크롤하면 된다. 이 앱은 읽는 앱이다.
- **보기 위쪽에 두지 마라.** 문제문과 보기 사이에 넣으면 펼칠 때 보기가 아래로 밀린다.
  보기 좌표를 지키는 것이 정답 재탭 방식을 고른 이유다 — 위 "보기 버튼" 절을 봐라.
- 토글은 열림·닫힘에서 **라벨이 "개념 보기" 그대로다.** 상태는 화살표 방향과
  `aria-expanded`가 전달한다. "접기"로 바꾸면 무엇을 접는 버튼인지가 라벨에서 사라진다.
- 화살표는 `∨`(닫힘) / `∧`(열림) **SVG 20px**이다. 아래 "아이콘" 절.
- **문항을 옮기면 닫힌다.** 다음 문항에 앞 문항의 주제가 펼쳐진 채로 남지 않는다.
- **어느 개념이 이 문항의 근거인지 표시하지 않는다.** 표시하면 펼치기가 다시 "정답의 출처"를
  가리키는 장치가 되어, 페이지를 읽게 하려던 목적과 어긋난다. 개념 읽기 화면에도 그런
  표시는 없다 — 두 화면이 같은 본문을 보여준다는 것이 이 펼치기의 약속이다.

#### 문항 사이 이동

```
확인 문제                                    [←]  2 / 7
```

**푼 문항으로 되돌아갈 수 있다.** 방금 지나온 문제와 해설을 다시 읽는 통로다.
문제를 풀다 앞 문항이 걸릴 때 주제를 벗어났다가 처음부터 다시 풀게 하지 마라.

**앞으로 가는 조작은 정답 보기 재탭 하나뿐이다.** 위 절에서 정한 것이고, 뒤로 가기가
생겨도 그대로다. 대칭을 맞추려고 오른쪽에 `→` 화살표를 두지 마라 — 같은 이동에 조작이
둘이 되고, 둘 중 어느 쪽이 채점에 영향을 주는지 헷갈리게 된다.

**뒤로 가는 화살표는 진행 카운터 왼쪽에 둔다.** 지금 몇 번째인지 알려주는 숫자 옆이
위치를 되짚는 조작의 자리다. 본문 아래에 두면 해설 길이에 따라 자리가 움직인다.

- 화살표는 개념 읽기 하단 바와 **같은 SVG 20px**을 쓴다. 아래 "아이콘" 절.
- 라벨을 붙이지 마라. 의미는 `aria-label="이전 문제"`로 전달한다.
- **첫 문항에서는 렌더하지 않는다.** 회색 비활성으로 남기지 마라 — 셸이 `justify-between`
  이라 화살표가 빠져도 카운터는 오른쪽 끝에 그대로 있다. **가로** 자리를 지켜야 할 이유가 없다.
  개념 읽기 하단 바가 비활성 화살표를 두는 것은 가운데 버튼이 밀리기 때문이고,
  여기엔 그 이유가 없다.
- **대신 제목 줄에 `min-h-[44px]`를 건다.** 지키지 못하는 것은 가로가 아니라 **세로**다.
  화살표가 없는 첫 문항은 줄 높이가 `h1`의 32px로 줄고, 2번 문항으로 넘어가는 순간
  44px로 커지면서 본문 전체가 아래로 밀린다. 390×844에서 실측한 값이다.

| 문항 | 제목 줄 높이 | 문제문 y | 첫 보기 y |
|---|---|---|---|
| 1번 (화살표 없음) | 32 | 153 | 241 |
| 2번 (화살표 있음) | 44 | 165 | **253 — 12px 밀림** |
| 3번 이후 | 44 | 165 | 253 |

  `min-h-[44px]`를 걸면 세 행이 모두 44 / 165 / 253으로 같아진다. 12px은 작아 보이지만
  넘어가는 조작이 정답 보기 재탭이라 손가락이 이미 보기 버튼 위에 있다. **그 자리를
  유지하는 것이 재탭 방식을 고른 이유다** — 위 "보기 버튼" 절을 봐라.

되돌아간 문항은 **읽기 전용이다.** 채점은 처음 골랐을 때 이미 끝났고 진행 상태에도
기록됐다. 고른 보기와 정답이 색으로 남고 해설이 펼쳐진 채 보이며, 보기를 다시 고를 수
없다. 남아 있는 정답 보기를 누르면 채점이 아니라 다음 문항으로 넘어간다 — 처음 풀 때와
같은 조작이다.

**아직 풀지 않은 문항으로 건너뛰게 하지 마라.** 문항 번호를 눌러 아무 데나 가는 목록을
만들지 마라. 문항은 순서대로 하나씩 푼다.

#### 복습에 넣기

```
(해설)
정답을 한 번 더 누르면 다음 문제로 넘어갑니다
☐ 복습에 넣기                     ← 누르면 ☑ 복습에 넣기
─────────────────────────────────────
∨ 개념 보기
```

답을 고르면 해설과 조작 안내 **아래에** 스위치 하나가 나온다. 누르면 그 문항이 복습 목록에
들어가고, 다시 누르면 빠진다. 확인 문제·랜덤 문제·복습 문제 풀기가 같은 `QuizRunner`를 쓰므로
세 화면에 모두 있다(ADR-032).

- **틀렸다고 켜 두지 마라.** 스위치는 정오답과 무관하게 그 문항이 지금 복습 목록에 있는지만
  보여준다. 무엇을 복습할지는 해설을 읽은 학습자가 정한다.
- **답을 고르기 전에는 렌더하지 않는다.** 판단 근거인 해설이 아직 없다. 되돌아간 문항(읽기 전용)
  에서는 보인다 — 채점과 무관한 조작이기 때문이다.
- **라벨은 켜짐·꺼짐에서 `복습에 넣기` 그대로다.** 상태는 체크 표시와 `aria-pressed`가 전달한다.
  위 "개념 펼치기" 토글과 같은 규칙이다. "복습에 넣음"처럼 바꾸면 라벨이 할 일 대신 상태를
  말하게 되고, 스크린 리더는 그 상태를 `aria-pressed`와 겹쳐 두 번 읽는다.
- 아이콘은 빈 사각형(꺼짐) / 체크가 든 사각형(켜짐) **SVG 20px**이다. 색을 붙이지 마라 —
  색은 정답/오답/중요도에만 쓴다.
- 스타일은 "개념 보기" 토글과 같다: `inline-flex min-h-[44px] items-center gap-2 text-sm
  text-neutral-400 hover:text-neutral-100`.
- **보기 위쪽이나 제목 줄에 두지 마라.** 보기 좌표를 지키는 것이 정답 재탭 방식을 고른
  이유다 — 위 "보기 버튼" 절을 봐라.

### 버튼
```
Primary: inline-flex items-center min-h-[44px] rounded-md bg-neutral-100 text-neutral-900 px-4 py-2 hover:bg-white
Ghost:   inline-flex items-center min-h-[44px] rounded-md text-neutral-400 px-4 py-2 hover:text-neutral-100
```
`min-h-[44px]`는 장식이 아니다. 손가락으로 누르는 최소 크기다. 아래 "터치 영역"을 봐라.

### 돌아가기

읽던 흐름에서 잠깐 벗어나는 화면(`검색`·`복습`)의 **제목 줄 위**에 한 줄로 둔다.
`src/components/BackButton.tsx` 하나를 두 화면이 함께 쓴다.

```
← 돌아가기
검색                                        결과 12개
```

```
-ml-4 inline-flex min-h-[44px] items-center gap-2 rounded-md px-4 py-2 text-sm
text-neutral-400 transition-colors hover:text-neutral-100
```

- **왜 필요한가.** 이 두 화면은 헤더 링크로 들어오는데, 들어오고 나면 그 링크가 자기 자신을
  가리켜 나가는 길이 되지 못한다. 로고는 주제 목록으로만 가므로 읽던 자리로는 돌아오지 못한다.
- **헤더에 넣지 마라.** 링크가 세 개가 되어 로고가 눌린다 — 아래 "헤더 안의 링크"를 봐라.
- **제목 왼쪽에 붙이지 마라.** 제목이 본문보다 오른쪽으로 밀려 화면 왼쪽 세로선이 깨진다.
- 하단 액션 바의 화살표와 달리 **라벨을 붙인다.** 이 줄에 다른 요소가 없어 320px에서
  116×44px만 쓴다(실측). 화살표만 남겨 뜻을 `aria-label`에 숨길 이유가 없다.
- `-ml-4`로 `px-4`를 상쇄해 **화살표가 제목·본문과 같은 세로선**에 서게 한다(320px에서 20px).
- 아이콘은 개념 읽기 하단 바와 같은 SVG 20px이다. 아래 "아이콘" 절.
- **개념 읽기·확인 문제에는 두지 마라.** 거기는 하단 액션 바와 정답 보기 재탭이 이동을 맡는다.
  확인 문제에서 개념을 보는 길도 화면 밖으로 나가지 않는다 — 위 "개념 펼치기"를 봐라.
- 목적지는 **직전 화면**이다. 새 탭·공유 링크로 직접 열었으면 그 과목의 주제 목록(과목 홈)으로 보낸다 —
  구현에서 걸리는 함정은 ARCHITECTURE "개념·주제 검색"에 있다.

#### 모든 과목

```
← 모든 과목
주제 목록                                        37%
```

주제 목록의 **제목 줄 위**에 첫 화면(과목 목록, `#/`)으로 가는 링크 「모든 과목」을 둔다(ADR-053).

- **모양은 「돌아가기」와 같다.** 같은 클래스, 같은 왼쪽 화살표 SVG 20px, 라벨을 붙인다. 클래스와 아이콘은
  `BackButton.tsx`가 export한 `backButtonClass`·`backIcon`을 함께 쓴다.
- **동작은 다르다.** 직전 화면(`navigate(-1)`)이 아니라 **늘 `#/`로 가는 링크**다. 그래서 `BackButton`을 재사용하지 않는다.
- **주제 목록에만 둔다.** 과목 안 어디서든 로고가 주제 목록(과목 홈)으로 오므로, 첫 화면까지는 로고 → 「모든 과목」
  두 번이면 닿는다. 헤더에 두지 않는 이유는 아래 "헤더 안의 링크"의 링크 둘 상한이다. 헤더의 과목 전환은 사용자가 기각했다.

### 상단 고정 헤더

헤더는 **모든 화면에서 상단에 고정한다.** `Layout`의 `<header>` 한 곳에 걸며,
화면마다 켜고 끄지 않는다. 과목 안 어느 화면에서든 주제 목록·복습으로 한 번에 돌아갈 수 있어야 한다.
안의 링크 구성은 과목 안에서 화면에 따라 달라지지 않는다 — 아래 "헤더 안의 링크"를 봐라.

```
sticky top-0 border-b border-border bg-page
```

- **`bg-page`가 필수다.** `<header>` 자체의 배경은 투명이고, 지금 검게 보이는 것은
  부모 `div`의 `bg-page`가 비치기 때문이다. 흐름 안에 있을 때는 문제가 없지만 고정하는
  순간 아래로 흘러가는 본문이 헤더 글자와 그대로 겹쳐 **둘 다 읽을 수 없다.**
  390px에서 실제로 확인한 결과다. 반투명·`backdrop-blur`를 쓰지 마라 — 안티패턴 표를 봐라.
- `fixed`가 아니라 **`sticky`**를 쓴다. 하단 액션 바와 같은 이유다. 문서 흐름 안에 남으므로
  본문에 상단 여백 보정(`pt-*`·`margin-top`)을 넣을 필요가 없다.
- **`z-index`를 붙이지 마라.** `sticky`는 그 자체로 positioned 요소라 static인 본문 위에
  그려진다. `main` 안에서 positioned인 것은 하단 액션 바 하나뿐이고, 그 둘은 뷰포트 높이가
  146px 아래로 내려가야 겹친다.
- 스크롤 방향에 따라 헤더를 숨기거나 축소하지 마라. 높이는 항상 77px이다.
- 조상 요소에 `overflow: hidden|auto`가 있으면 `sticky`는 조용히 동작을 멈춘다. 새로 넣지 마라.

고정하면 뷰포트를 상시 차지한다. 남는 읽기 영역을 실측한 값이다
(개념 읽기 화면 — 헤더와 하단 액션 바가 동시에 고정되는 유일한 화면).

| 뷰포트 | 헤더 | 하단 액션 바 | 남는 영역 |
|---|---|---|---|
| 390×844 | 77 | 69 | 698 (82.7%) |
| 375×667 | 77 | 69 | 521 (78.1%) |
| 1440×900 | 77 | 69 | 754 (83.8%) |

헤더 높이를 줄여 이 영역을 넓히려 하지 마라. 77px은 `py-4`와 로고·내비 링크의
`min-h-[44px]`에서 나온 값이고, 44px은 터치 영역 최소치다. 아래 "터치 영역" 절을 봐라.

#### 헤더 안의 링크

```
[AWS SAA-C03]              [검색]   [복습]      ← 과목 안 (로고 = 과목 이름)
[Study Quiz]                                   ← 과목 밖 (과목 목록)
```

**헤더 구성은 과목 안에서 화면마다 달라지지 않는다**(ADR-053). 과목 밖(과목 목록)에서는 로고 「Study Quiz」만 있다 —
검색·복습은 과목 안의 기능이라 과목 목록에서는 갈 곳이 없다. `Layout`이 아는 것은 과목 컨텍스트가 있는가 하나이고,
지금 어느 화면인지 알 필요가 없다. 라우트를 판별하는 분기를 두지 않는다.

**같은 목적지를 두 번 두지 마라.** 과목 안에서 주제 목록(과목 홈)은 로고가 맡는다. 로고 옆에 "주제 목록" 링크를
나란히 두면 헤더의 두 자리가 같은 화면으로 간다. 로고 클릭이 홈이라는 것은 웹의 표준
관례이므로 별도 링크가 없어도 길을 잃지 않는다.

**확인 문제 화면용 "근거 개념" 링크를 되살리지 마라.** 헤더에서 개념 읽기로 보내면
문항 화면이 언마운트되어 진행 위치와 고른 보기가 사라지고, 돌아와도 1번 문항부터
다시 섞인 세트가 나온다. 확인 문제에서 개념을 보는 길은 문항 화면 안에서 펼치는
토글이 맡는다 — 위 "보기 버튼 > 개념 펼치기"를 봐라.

**링크는 두 개가 상한이다.** 320px에서 세 개가 되면 넘치는 게 아니라 **로고가 찌그러진다.**
실측한 값이다.

| 헤더 구성 | 로고 | 링크 | 가로 스크롤 |
|---|---|---|---|
| `검색` + `복습` | 104 | 60 / 60 — 여유 52px | 0 |
| 세 번째 링크를 더한 경우 | **82 — 20px 압축** | 49 / 69 / 49 | 0 |

셸이 `justify-between`이고 로고와 링크가 모두 `min-width: auto`로 줄어들 수 있어서,
폭이 모자라면 **가로 스크롤 대신 전부가 눌린다.** `AWS SAA-C03`은 82px에 들어가지 않아
두 줄로 접히고, 링크 글자도 같이 찌그러진다. 넘침이 0이라고 통과한 것이 아니다 —
`overflow`만 보는 검사로는 이 파손을 못 잡는다.

- **새 화면으로 가는 링크가 필요하면 헤더가 아니라 본문에 둔다.** 주제 목록의
  "랜덤 문제" 진입점이 그렇게 놓였다.
- 돋보기 아이콘으로 줄여 세 항목을 다 넣으려 하지 마라. 링크 세 개일 때 눌리는 것은
  링크만이 아니라 **로고**다. 한 칸을 좁혀도 세 칸이 나눠 갖는 폭 자체가 모자라 로고가
  제 폭을 되찾지 못한다. 아이콘이 없애는 것은 폭이 아니라 "무슨 링크였는지"다.

### 하단 고정 액션 바

본문이 한 화면을 넘는 화면에서 다음으로 넘어가는 주요 버튼은 화면 하단에 고정한다.
본문 끝까지 스크롤해야 버튼에 닿는 상태를 만들지 마라.

지금 쓰는 곳은 **개념 읽기 화면 하나뿐이다.** 확인 문제 화면에는 쓰지 않는다 —
거기는 정답 보기 재탭으로 넘어가므로 버튼 자체가 없다. 위 "보기 버튼" 절을 봐라.

```
sticky bottom-0 -mx-5 border-t border-border bg-page px-5 py-3 sm:mx-0 sm:px-0
```

- `fixed`가 아니라 **`sticky`**를 쓴다. 이유: 문서 흐름 안에 남으므로 스크롤 최하단에서는
  제자리로 돌아간다. 마지막 본문 줄을 영구히 가리지 않고, 본문에 하단 여백 보정을 넣을 필요도 없다.
- 모바일에서는 `-mx-5`가 `main`의 좌우 패딩을 상쇄해 바 배경이 화면 폭을 채운다.
  같은 값의 `px-5`를 다시 넣어 내용 정렬은 본문과 맞춘다.
- 데스크톱에서는 `sm:mx-0 sm:px-0`으로 **본문 폭에 맞춘다.** 음수 마진을 유지하지 마라.
  이유: 셸이 화면 가운데 있으므로 음수 마진을 늘려도 화면 폭에는 닿지 못한다. 본문보다
  좌우 32px씩만 튀어나온 어중간한 띠가 될 뿐이다. 위 "데스크톱" 절을 봐라.
- 배경은 **불투명**해야 한다(`bg-page`). 반투명·`backdrop-blur`를 쓰지 마라 — 안티패턴 표를 봐라.
- 조상 요소에 `overflow: hidden|auto`가 있으면 `sticky`는 조용히 동작을 멈춘다. 새로 넣지 마라.
- 스크롤이 생기지 않는 짧은 화면(퀴즈 완료·빈 상태·에러 분기)에는 쓰지 않는다. 고정할 이유가 없다.
- **640px 미만에서는 아래로 스크롤하는 동안 고정을 푼다**(`max-sm:static`). 위로 스크롤하거나 맨 위로 돌아오면
  다시 고정한다. 이유: iOS 26 Safari는 하단 툴바가 접혀도 sticky 바를 따라 내리지 않아, 바가 떠 보이고 그 밑으로
  본문이 비친다. 툴바와 같은 리듬으로 숨기면 떠 있을 바가 없다(ADR-052). 조금만 올려도 나타나므로 위의
  "본문 끝까지 스크롤해야 버튼에 닿는 상태"가 아니다. 전환은 즉시다 — 슬라이드를 넣지 마라(「애니메이션」).
  헤더에는 같은 처리를 하지 마라. 증상은 하단 툴바에서만 난다.

#### 바 안의 3분할 — 주제 이동

개념 읽기의 바는 세 칸이다. **주제 목록을 거치지 않고 앞뒤 주제로 넘어갈 수 있어야 한다.**

```
[← 아이콘]      [확인 문제 풀기]      [→ 아이콘]
```

```
바 안쪽: flex items-center justify-between gap-3
화살표:  Ghost 버튼 클래스 + SVG 20px (아래 "아이콘" 절)
```

**화살표에 텍스트 라벨을 붙이지 마라.** 320px에서 들어가지 않는다. 빌드된 CSS로 실측한 값이다.

| 좌우 칸의 내용 | 320px | 375px | 390px |
|---|---|---|---|
| `← 이전` (텍스트 화살표) | **26px 넘침** | 여유 29 | 여유 44 |
| SVG 16px + `이전` 라벨 | **21px 넘침** | 여유 34 | 여유 49 |
| `이전` (라벨만) | 여유 **0** | 여유 55 | 여유 70 |
| **SVG 20px 화살표만** | 여유 **51** | 여유 106 | 여유 121 |

320px에서 쓸 수 있는 폭은 278px이고 `확인 문제 풀기`가 123px을 가져간다. 남는 155px을
좌우 두 칸과 `gap-3` 두 개(24px)가 나눠 갖는다. 라벨만 남긴 안이 여유 0으로 통과하지만
글꼴이 1px만 넓어도 넘친다. **화살표만 쓴다.** 의미는 `aria-label`로 전달한다.

`sm:` 이상에서만 라벨을 보이게 하는 안도 재봤다. 375px 이상에서는 들어가지만 320px 문제는
그대로고, 화면 폭에 따라 버튼 모양이 바뀌는 대가를 치른다. 쓰지 않는다.

**첫 주제·마지막 주제에서 칸을 비우지 마라.** 폭이 0이 되면 가운데 버튼이 끌려간다.
갈 곳이 없는 쪽은 **같은 화살표를 `text-disabled`로 칠한 `span`으로 렌더한다.**
링크가 아니므로 `aria-hidden="true"`를 붙인다. 320px에서 잰 `확인 문제 풀기`의 왼쪽 좌표다.

| 이전 칸 | 가운데 버튼 좌표 |
|---|---|
| 이전 버튼 있음 (기준) | 77 |
| 빈 `span` | 51 — **26px 밀림** |
| 44px 스페이서 | 73 — 4px 밀림 |
| 비활성 화살표 `span` (52px) | 77 — 기준과 같다 |

### 진행률 표시
막대 하나. 퍼센트 숫자를 옆에 둔다.
```
h-1 rounded-full bg-neutral-800  /  내부: bg-neutral-300
```
원형 게이지·애니메이션 카운터를 만들지 마라.

### 랜덤 문제 진입점 (주제 목록)

주제 목록의 **진행률 바 아래, 주제 카드 위**에 한 줄로 둔다. 헤더에 넣지 않는다 —
320px에서 헤더 링크가 세 개가 되면 로고와 부딪힌다.

```
block rounded-lg border border-neutral-800 px-5 py-4 hover:border-neutral-700
```

**주제 카드와 같은 배경(`bg-[#141414]`)을 쓰지 마라.** 배경 없이 테두리만 두어
21번째 주제처럼 보이지 않게 한다. 이것 하나가 카드 줄과 구분되는 유일한 신호다.

- 왼쪽에 제목, 오른쪽에 문항 수 안내를 보조 색(`text-neutral-500`)으로 둔다.
- 문항 총계를 **숫자로 하드코딩하지 마라.** `questions.length`에서 온다.
- 아이콘·배지·강조색을 붙이지 마라. 색은 정답/오답/중요도에만 쓴다.

### 랜덤 문제 시작 화면

문항 수 버튼뿐인 화면이다. 10 · 20 · 30 · 50 · 100과 `전체`, 여섯 개다.
폭은 확인 문제와 같은 `max-w-2xl`.

```
inline-flex min-h-[44px] items-center rounded-md border border-neutral-800 bg-[#141414]
px-4 py-2 text-neutral-300 hover:border-neutral-700 hover:text-neutral-100
```

- **여섯을 같은 스타일로 둔다.** 하나만 Primary로 만들어 "추천"처럼 보이게 하지 마라.
  동등한 선택지다. `전체`도 예외가 아니다 — 분량이 많다고 경고를 붙이지 마라.
- 가로로 `gap-3`. 320px에서 넘칠 수 있으므로 `flex-wrap`을 둔다. 버튼이 여섯이라
  좁은 화면에서는 여러 줄로 접힌다.
- 예상 소요 시간·난이도 같은 부가 정보를 만들지 마라. 없는 데이터다.

### 랜덤 문제 완료 화면

주제별 확인 문제 완료 화면과 **같은 구성**이되 "다음 주제 이어가기"가 없다.
이어갈 주제가 없기 때문이다.

| 상황 | Primary | Ghost |
|---|---|---|
| 방금 푼 세트에 복습 목록의 문항이 있다 | `복습하기` → `/review` | `다시 뽑기` → `/random`, `주제 목록으로` → 과목 홈 |
| 없다 | `다시 뽑기` → `/random` | `주제 목록으로` → 과목 홈 |

경로는 과목 안 경로다(앞에 `/:subjectId`가 붙는다 — ARCHITECTURE "라우트").

**정오답으로 가르지 마라.** 틀린 문항은 저절로 복습 목록에 들어가지 않으므로, 틀렸다는 사실만으로는
복습 화면에 볼 것이 있다는 보장이 없다. 세트 밖의 복습 문항은 세지 않는다 — 목록이 길기만 하면
모든 완료 화면이 복습을 주요 출구로 내세우게 된다(ADR-032). 확인 문제 완료 화면도 같은 규칙이다.

**`다시 뽑기`는 방금 푼 `/random/:count`가 아니라 `/random`으로 보낸다.** 같은 경로로
이동하는 링크는 아무 일도 일으키지 않아 화면이 멈춘 것처럼 보인다. 시작 화면을 거치면
문항 수를 다시 고를 수도 있다.

### 검색 입력

검색 화면 맨 위의 입력 하나다. 폭은 `max-w-3xl` 안에서 100%.

```
w-full rounded-md border border-neutral-800 bg-[#141414] px-4 py-3
text-[15px] text-neutral-100 placeholder:text-neutral-500
focus:border-neutral-600 focus:outline-none
```

- **`focus:outline-none`만 쓰고 끝내지 마라.** 초점 표시를 없애는 게 아니라 테두리 색으로
  옮기는 것이다(`focus:border-neutral-600` — 보기 버튼의 선택 상태와 같은 값).
- `py-3` + `text-[15px]`로 높이가 46px이다. 터치 영역 44px을 넘는다.
- 검색 버튼을 만들지 마라. 입력하는 동안 결과가 바뀐다. `form`으로 감싸 엔터를 받는 구조도
  필요 없다 — 제출할 곳이 없다.
- 돋보기 아이콘을 입력 안에 넣지 마라. 자리표시자(`개념·주제 검색`)가 같은 일을 하고,
  아이콘을 넣으면 좌측 패딩을 따로 계산해야 한다.
- 화면에 들어오면 입력에 **초점을 준다.** 검색만 하는 화면이라 다른 곳에 줄 초점이 없다.

### 검색 화면

```
← 돌아가기
검색                                        결과 12개
[                                                    ]

Aurora                                    ← 개념 히트
Aurora·DynamoDB·ElastiCache
MySQL·PostgreSQL과 호환되는 관계형 데이터베이스다

S3 스토리지 클래스 유형                      ← 주제 히트
주제

∨ 본문에서 66개 더 찾음                     ← 본문에만 걸린 히트는 접는다
```

- 제목 줄 위의 `돌아가기`는 위 "돌아가기" 절에서 정한 그대로다.
- 결과 개수는 제목 줄 오른쪽에 `text-sm text-neutral-500`으로 둔다. 진행률 퍼센트와 같은 자리다.
- 개념 히트 카드: 개념 이름(`text-base font-medium text-neutral-100`) → 주제 제목
  (`text-xs text-neutral-500`) → 한 줄 요약(`text-sm text-neutral-400`).
  **한 줄 요약을 빼지 마라.** AWS 과목은 개념이 640개라 이름만으로는 어느 것인지 가려지지 않는 것이
  많고, 열기 전에 목록에서 가려내게 하는 장치다. 개념 히트를 누르면 그 개념 위치로
  이동한다(ADR-020, ARCHITECTURE "개념·주제 검색").
- 주제 히트 카드: 주제 제목(`text-lg font-medium text-neutral-100`)과 `주제` 라벨
  (`text-xs text-neutral-500`). 중요도 별을 붙이지 마라 — 여기는 학습 순서를 고르는
  자리가 아니라 찾은 것을 확인하는 자리다.
- 카드는 주제 목록과 같다: `rounded-lg bg-[#141414] border border-neutral-800 p-5
  hover:border-neutral-700`. 개념 히트와 주제 히트를 다른 색으로 구분하지 마라 —
  색은 정답/오답/중요도에만 쓴다. 구분은 카드 안의 글자가 한다.
- **맞은 글자를 강조 표시하지 마라.** 하이라이트는 색이거나 배경이고, 둘 다 위 규칙에 걸린다.
- 질의가 비었을 때: 안내 한 줄(`text-[15px] leading-7 text-neutral-400`). 인기 검색어·
  추천 개념 같은 것을 만들지 마라. 없는 데이터다.
- 결과가 없을 때: `검색 결과가 없습니다.` 한 줄. 오타 교정 제안을 만들지 마라.
- 결과 개수를 자르지 마라(`더 보기` 버튼을 만들지 마라). 자르면 찾으려던 것이 잘린 쪽에
  있을 때 사용자가 알 방법이 없다. 상한은 그 과목의 개념 수 + 주제 수다(AWS는 개념 640개 + 주제 39개).
- **본문에만 걸린 히트는 접어 둔다**(ADR-024). 개념 이름·한 줄 요약·주제 제목에 걸린 히트를
  먼저 그리고, 그 아래에 `본문에서 66개 더 찾음` 토글을 둔다. 위 규칙과 부딪치지 않는다 —
  개수를 밝히고 펼칠 수 있으므로 자르는 것이 아니라 접는 것이다.
  - 토글 라벨은 열림·닫힘에서 **그대로다.** 상태는 화살표(`∨` 닫힘 / `∧` 열림, SVG 20px)와
    `aria-expanded`가 전달한다. 위 "개념 펼치기"와 같은 규칙이다.
  - **질의가 바뀌면 닫힌다.** 앞 질의에서 펼친 상태가 남지 않는다.
  - **이름·요약에 걸린 히트가 하나도 없으면 접지 마라.** 남길 것이 없는데 접으면 빈 목록과
    토글만 남아 결과가 없는 것처럼 보인다. 그때는 본문 히트를 그냥 결과 목록으로 그린다.
  - 결과 개수(제목 줄 오른쪽)는 **접힌 것까지 센다.** 찾은 수를 줄여 보고하지 않는다.

### 딸린 개념 (ADR-041)

`parentId`가 있는 개념은 머리 개념 아래로 들여쓴다. `ConceptList`가 개념 읽기와 확인 문제의
개념 펼치기를 함께 그리므로 두 화면이 같다.

```text
<article 머리>                      ← 지금 그대로
<div 딸린 무리>                     ← space-y-8 border-l border-border pl-4 max-sm:[&_figure]:-ml-[37px]
  <article 딸린 개념>               ← 제목 한 단계 아래. 클래스는 「개념 이름」 그대로
  <article 딸린 개념>
</div>
<article 다음 머리>
```

- **세로선은 경계선 색(`border-border`, `#262626`)이다.** 색을 칠하거나 굵게 하지 마라. 무리를
  묶는 일은 들여쓰기가 하고 선은 무리의 시작과 끝을 보인다.
- **제목은 한 단계만 내린다.** 개념 읽기 h2 → h3, 개념 펼치기 h4 → h5. 글자 크기·굵기는 머리와
  같다. 소속은 들여쓰기가 보이고, 제목 크기까지 줄이면 딸린 개념이 덜 중요해 보인다.
- **머리 이름·화살표·접기를 붙이지 마라.** 사용자가 고른 장치는 들여쓰기와 세로선이다.
- **모바일에서 도식·비교표는 지금처럼 화면 끝까지 펼친다.** `figure`의 `-mx-5`(20px)에 무리의
  세로선 1px과 `pl-4` 16px을 더해 왼쪽을 `-37px`로 당긴다. 그래서 320px에서도 도식 표시 폭
  320px, 비교표 폭 288px이 그대로이고 phase 38~52의 실측이 산다. 들여쓰기 폭을 바꾸면 이 값도
  같이 바꾼다. 도식은 `bg-panel` 띠라 세로선이 그 자리에서 끊긴다. `sm:`부터는 도식도 무리 안쪽에
  선다(`sm:mx-0`).
- 320px에서 딸린 개념의 글 폭은 263px이다(280px에서 17px 줄어든다).

### 도식

개념 본문 바로 뒤에 넣는 SVG다. `ConceptList`가 개념 읽기와 확인 문제의 개념 펼치기에
같은 도식을 보여주고, `DiagramFrame`이 시나리오 버튼·캡션·범례를 함께 감싼다.

**네트워크 과목은 개념마다 도식이 하나 이상 있다**(ADR-056). 비교표는 도식을 대신하지 않는다 — 표가 붙은 개념에도
도식이 따로 있고, 둘이 함께 붙으면 도식을 먼저 둔다(아래 「한 개념 뒤의 여러 도식」). AWS 과목에는 이 규칙이 없다.
**Azure 과목은 주제마다 도식이 하나 이상 있고**, 구조·흐름이 있는 개념에는 개념마다 둔다(ADR-060). 비교표가 도식을 대신하지 않는 것과 도식을 먼저 두는 것은 같다.

**`viewBox` 폭은 280이다. 1:1 표시 비율이 아니라 좌표계의 약속이다.** 세로는 필요한 만큼
늘린다. 세로 스크롤은 이 앱의 기본 동작이고, 가로 넘침은 버그다. 가로는 두 열을 기본으로
하되 라벨이 길면 한 줄 전체 폭을 쓴다. 화면 폭 768px 이상에서 쓰는 가로형(폭 440)은 아래
「넓은 화면의 가로형」을 본다. 이 절의 나머지 규칙은 세로형 이야기다.

세로형 SVG를 감싸는 요소는 `w-full max-w-[380px]`이며 `mx-auto`를 붙이지 않는다. 본문처럼
왼쪽에 맞춘다. 모바일에서는 `figure`의 `-mx-5 sm:mx-0`과 SVG 래퍼의 `-mx-4 sm:mx-0`으로
본문과 틀의 좌우 여백을 차례로 상쇄한다. **`w-full`은 음수 마진만으로 넓어지지 않으므로**
래퍼에 `max-sm:w-[calc(100%+2rem)]`도 둔다. 모바일의 좌우 테두리·둥근 모서리는 없애고
`sm:`부터 복원한다. 래퍼의 최종 클래스는 다음과 같다.

```text
-mx-4 w-full max-w-[380px] max-sm:w-[calc(100%+2rem)] sm:mx-0
```

step 1의 폭 계산은 `DiagramFrame`의 패딩과 테두리를 빠뜨렸고, step 7이 이를 고쳤다.
아래는 **보정 뒤**의 브라우저 실측이다. 출처는
[phase 38 실측 기록의 「전 도식 공통」](../phases/38-service-diagrams/measurements.md#전-도식-공통)이며,
측정 방법과 전후 비교도 그 파일에 있다. step별 `summary`의 당시 미측정 기록을 추정치로
메우지 않는다.

| 뷰포트 | SVG 표시 폭 | 배율 | 노드 라벨 | 그룹 라벨 |
|---|---|---|---|---|
| 320px | 320px | 1.143 | 11.43px | 10.29px |
| 390px·1280px | 380px | 1.357 | 13.57px | 12.21px |

열여섯 도식과 비교표 아홉 모두 320·390·1280px에서 가로 넘침이 없었고 버튼 최소 높이는 44px이었다.
phase 38의 다섯 장은 위 기록에서, phase 39가 메시징 주제에 더한 네 장은
[phase 39 실측 기록](../phases/39-messaging-diagrams/measurements.md)에서, phase 40이 VPC 주제에 더한
네 장과 비교표는 [phase 40 실측 기록](../phases/40-vpc-visuals/measurements.md)에서, phase 41이 백업 주제에 더한
두 장과 비교표 셋은 [phase 41 실측 기록](../phases/41-backup-visuals/measurements.md)에서, phase 42가 보안 그룹·NACL
주제에 더한 한 장과 비교표는 [phase 42 실측 기록](../phases/42-sg-nacl-visuals/measurements.md)에서 같은 방법으로 쟀고
표시 폭·배율·라벨 크기가 위 표와 같았다. 도식별 버튼 줄 높이와 도식 전체 높이는 각 기록의
「도식별」 표를 본다. 다시 재기 전에는 새 숫자를 쓰지 마라.

- **글자 크기는 노드 라벨 10, 그룹 라벨·곁말 9**(viewBox 단위)다. 라벨을 줄이거나 영문
  약어로 바꾸지 마라. 안 들어가면 노드를 넓히거나 한 줄 전체 폭으로 편다. 본문에 쓰인 말과
  도식에 쓰인 말이 다르면 도식이 본문을 가리키지 못한다.
  곁말(9)의 한글 글리프 윗선은 기준선 위 8이다(Windows Chrome, phase 64 실측). 곁말을 노드 바로 아래에 둘 때는 기준선을
  노드 아래 변에서 10 이상 띄운다. 기준선 위 7로 어림하면 테두리에 닿는 자리를 놓친다.
- **색은 보조 채널이고 위치가 1차 채널이다.** 라벨 붙은 그룹 박스의 안과 밖으로 계층을
  구분한다. 모든 색을 회색으로 바꿔도 읽혀야 한다(ADR-036).
- **강조는 opacity로 한다.** 선택한 시나리오에 없는 노드는 `0.25`, 있는 노드는 `1`이다.
  그룹 박스는 흐려지지 않는다. 선택한 경로만 표시하며, `전체`에서는 모든 노드가 선명하고
  경로는 숨는다. 경로는 기존 `title` 색을 쓰고 opacity 전환 애니메이션은 넣지 않는다.
- **접근성 이름은 `figure`의 `aria-label`로 준다. 헤딩을 쓰지 마라.** `ConceptList`가
  호출 화면에 따라 헤딩 레벨을 바꾸기 때문이다. 캡션은 `aria-live="polite"`, 시나리오 버튼은
  `aria-pressed`로 상태를 전달한다. 버튼은 `flex-wrap gap-2`로 배치하고 `px-2.5`와
  `min-h-[44px]`를 유지한다. 정적 도식은 `전체`를 포함해 버튼을 렌더하지 않는다.
- 캡션은 경로를 되풀이하는 대신 개념 본문에 있는 조건·제약을 직접 쓴 문장으로 설명한다.
  `figcaption`의 `min-h-24`로 공간을 확보한다. 이것은 최대 높이나 줄 수 제한이 아니다.

**넘침은 눈으로만 확인하지 않는다.** 테스트에서 `src/lib/svg-bounds.ts`의
`boxesOutsideViewBox`로 모든 `rect`가 `viewBox` 안에 있는지 검사하고,
`estimateTextWidth(라벨, 10) + 12 <= 노드 폭`을 단언한다. 경계 검사는 **`rect` 좌표만**
보며 실제 `text` 폭은 어림값이다. 두 함수는 경로선이 상자를 가로지르는지도 보지 않는다.
**실제 글자 폭과 경로선의 가독성은 사람이 브라우저로 확인한다.**
[경로·노드 교차 검사기](../phases/38-service-diagrams/tools/check-path-crossings.mjs)가 현재
직교 경로의 노드 내부 통과를 보완 검사하지만, 글자·그룹 라벨·화살표까지 검증하지는 않는다.

**도식도 콘텐츠다.** 비용을 좌표축으로 그려 본문에 없는 대소 관계를 만들지 마라.
S3 클래스 도식의 비용은 본문이 말하는 관계만 SVG 아래 글로 적는다(ADR-036).

#### 넓은 화면의 가로형 (ADR-047·ADR-048)

화면 폭이 768px 이상이면 도식이 가로형 배치로 바뀐다. 도식 48장이 모두 가로형을 갖는다(phase 60이 시범 세 장, phase 61이 나머지 24장,
phase 62의 새 다섯 장과 phase 63·64의 새 여덟 장씩은 처음부터 두 배치로 만들었다).
새 도식을 만들 때도 두 배치를 함께 짠다.

- **`viewBox` 폭은 440이다.** 글자 크기 단위는 세로형과 같다(노드 라벨 10, 그룹 라벨·곁말 9). 768px 이상에서 도식 틀
  안쪽 폭은 638px(딸린 개념 안 621px)로 고정이라 배율이 1.45(1.41)다. 실측은 [phase 60 실측 기록](../phases/60-wide-diagrams/measurements.md)과
  [phase 61 실측 기록](../phases/61-wide-diagrams-rest/measurements.md)(27장 전부, Windows Chrome, 실시간 전환 포함),
  [phase 62 실측 기록](../phases/62-analytics-visuals/measurements.md)(새 다섯 장),
  [phase 63 실측 기록](../phases/63-iam-visuals/measurements.md)(새 여덟 장),
  [phase 64 실측 기록](../phases/64-container-visuals/measurements.md)(새 여덟 장)에 둔다.
- **래퍼는 `w-full` 하나다.** `max-w-[380px]`·`-mx-4`·`max-sm:` 보정을 붙이지 마라. 768px 이상은 이미 `sm:` 구간이라 상쇄할 모바일
  여백이 없다.
- **배치를 고르는 것은 `useWideDiagram()` 하나다.** 기준 폭을 도식마다 다시 쓰지 마라. 이유: 기준이 한 곳에 있어야 도식끼리 같은 폭에서
  바뀐다. `matchMedia`가 없으면(jsdom) 세로형이다.
- **바뀌는 것은 좌표뿐이다.** `wideNodes`·`widePaths`·`wideGroups`가 노드 x·y·폭, 경로 `d`, 그룹 박스와 라벨 자리를 갖는다. 노드 id·경로 id·
  시나리오·문구·색은 세로형과 함께 쓴다. `wideNodes`는 `nodes`와 같은 한 줄 형식(`{ id: '…', x: N, y: N, width: N`)으로 쓴다 — 교차 검사기가
  이 형식을 읽는다. 노드 배열 이름이 `nodes`가 아니면 가로형도 그 이름을 따른다(`storageClasses` → `wideStorageClasses`).
- 곁말·연결선·서브넷 곁말처럼 그림 위에 놓이는 것의 자리도 좌표다. `wideNotes`처럼 배치마다 짝을 두고, 글은 같은 JSON에서 읽는다.
  노드 높이도 배치마다 다를 수 있다(세로형의 전체 폭 상자 → 가로형의 두 줄을 잇는 높은 상자). 이때도 세로형 DOM은 그대로여야 한다.
- **소속은 세로형과 같다.** 어느 그룹 안에 있는지는 그대로이고, 위아래 순서와 흐름의 방향(위 → 아래를 왼쪽 → 오른쪽으로)은 바뀔 수 있다.
  세로형에만 맞는 위치 단언(「세로로 쌓는다」 등)은 가로형 테스트에서 대응 단언으로 바꾸고, 기존 `it`은 고치지 않는다.
- 출발과 도착은 되도록 같은 열에 세워 화살표를 곧게 둔다. 노드를 피해 도는 경로는 정해 둔 통로를 함께 쓴다.
- 가로형도 세로형과 같은 관문을 지난다. 상자가 `viewBox`(폭 440) 안에 있고, 라벨이 `estimateTextWidth + 12`로 들어가며,
  교차 검사기를 통과해야 한다.

#### 한 개념 뒤의 여러 도식 (ADR-037)

`registry`의 값이 배열이면 `ConceptList`가 배열 순서대로 본문 뒤에 붙인다. 도식 사이 간격은
개념 안의 다른 블록과 같은 `space-y-3`이다. 같은 개념에 둘 이상 붙일 때는 **넓은 그림을 먼저,
판단 규칙을 나중에** 둔다.

#### 수량과 상태를 바꾸는 도식 (ADR-037)

슬라이더·토글·스테퍼를 만들지 마라. 바꿀 수 있는 값은 몇 개의 **시나리오 버튼**으로 고정한다.
버튼 라벨은 값 자체를 쓴다(`VPC 3개`, `개발 · AZ A 장애`). 시나리오 이름과 달리 `전체`는
"아무 값도 고르지 않은 기본 그림"이며, 그 도식의 `idleCaption`이 무엇을 누르라고 안내한다.

- **장애는 색으로 칠하지 마라.** 무너진 영역의 노드는 흐리게(`0.25`) 두고, 그 그룹 라벨 옆에
  곁말(9) `장애`를 붙인다. 나가지 못하는 자원은 **경로가 사라지는 것**으로 보인다.
  예외: Route 53 주제는 곁말을 `비정상`으로 쓴다. 본문이 상태 검사의 판정을 그 말로 쓰기 때문이다
  (ADR-037 phase 43 확장).
- **계산한 숫자는 전제를 캡션에 적는다.** 피어링 연결 수 `n(n-1)/2`는 "모든 VPC가 서로
  통신해야 한다면"일 때의 값이다. 계산은 `src/lib/`의 순수 함수로 두고 테스트한다.
- 메시·허브처럼 원형으로 놓는 그림만 **사선**을 허용한다. 나머지 도식의 경로는 지금처럼 직교다.

#### 물음형 제목과 예시 (ADR-038)

`question`이 있는 도식은 시나리오 버튼 위에 그 물음을 보인다. 모양은 비교표 제목과 같다(`text-sm text-title`, 헤딩 아님).
물음은 그림이 답하는 것 하나를 학습자의 말로 쓴다. 예: `리전 A가 멈추면 Route 53은 어디를 알려 줄까?`

도식 안의 예시 값은 **본문에 나오는 것만** 쓴다(`www.example.com`, `db.corp.local` 등). 설명용 가상 리전·IP를 지어내지 마라.
예시 곁말은 시나리오와 상관없이 늘 보이고, 자기 노드의 opacity를 따른다. 물음형 제목은 Route 53 도식 셋(시범), 거버넌스 주제의
도식 둘(phase 48), 조직·Identity Center 도식 둘(phase 50), API Gateway·Step Functions 도식 넷(phase 59),
EMR·Glue·Athena·Lake Formation 도식 다섯(phase 62), IAM 도식 여덟(phase 63), ECS·EKS·Fargate 도식 여덟(phase 64)에 있다.
예시는 Route 53 도식 셋에만 있다.

#### 단계 그림 (ADR-050)

단계 목록의 번호 항목마다 첫 줄 바로 아래에 붙는 작은 정지 그림이다. 버튼·캡션·범례·물음형 제목이 없고, 접근성 이름은 `figure`의 `aria-label`
(「6단계 그림: …」)로 준다.

- **`viewBox` 폭은 208, 배치는 하나다.** 목록 안이라 320px 화면에서 그림 폭이 약 235px이고(딸린 개념 263px − 번호 들여쓰기 28px) 배율이 1.13이라
  노드 라벨이 다른 도식의 320px 값(11.43px)과 비슷하다. SVG는 `w-full max-w-[288px]`라 넓은 화면에서도 288px(배율 1.38)에서 멈춘다. 가로형을 두지 않는다.
- **틀은 가볍게 둔다.** `figure`는 `mt-2 !ml-0 max-w-[290px] rounded-md border border-border bg-panel`이고 안쪽 여백은 SVG 좌표의 8로 낸다. 다른 도식처럼 화면 끝까지
  펼치지 않는다 — 단계와 그림이 한 항목으로 묶여 보여야 한다.
  - `max-w-[290px]`(그림 288px + 테두리 2px): 빼면 틀만 항목 폭까지 퍼진다. 실측(2026-10-22) 768px 이상에서 틀 627px 안에 그림이 왼쪽 288px만 차지하고 오른쪽 337px가 비었다.
  - `!ml-0`: 이 개념은 딸린 개념이라, 딸린 무리의 `max-sm:[&_figure]:-ml-[37px]`(본문 뒤 도식을 화면 끝까지 펼치는 규칙)가 목록 안의 틀까지 끌어낸다.
    그 규칙의 선택자 `.… figure`가 클래스 하나보다 구체적이라 `!`로 막는다. 빼면 320px에서 틀이 항목 글보다 37px 왼쪽, 번호 칸 너머로 튀어나온다.
- 글자 크기(노드 10, 그룹 라벨·곁말 9)와 색(파랑·청록·회색) 규칙, 경계·라벨 폭·교차 검사는 다른 도식과 같다. 경로는 노드 변이나 그룹 박스 변에서
  시작하고 끝난다. 설계 검사기는 `phases/65-roles-anywhere-steps/tools/check-steps.mjs`다.
- 단계 그림 19장은 위 「넓은 화면의 가로형」의 도식 수(48장)에 들지 않는다(가로형이 없다). 실측은 [phase 65 실측 기록](../phases/65-roles-anywhere-steps/measurements.md)에 둔다.
- 같은 대상은 모든 그림에서 같은 라벨·색이다(`private.key`, `S3UploadRole`, `IAM Roles Anywhere` 등). 본문에 이름이 있는 것은 이름으로 쓴다(ADR-038 「예시」).

### 비교표 (ADR-037)

개념 본문 뒤에 붙는 `<table>`이다. 도식과 같은 자리(`registry`)로 붙고, 틀도 도식 `figure`와 같은
테두리·패딩을 쓴다. 접근성 이름은 `figure`의 `aria-label`이다.

- **열은 셋 이하다.** 첫 열은 행 머리(`th scope="row"`)다. 넷 이상이 필요하면 두 열을 합치거나
  표를 둘로 나눈다. 320px에서 가로 스크롤이 생기면 버그다 — `table-fixed w-full`과 `break-keep`으로
  칸 안에서 줄을 바꾼다. `overflow-x-auto`로 가리지 마라.
- **끊을 수 없는 영문 이름은 320px에서 그 열에 한 줄로 들어가야 한다.** 들어가지 않으면 가로 넘침 대신
  단어 중간에서 끊긴다(`break-anywhere`). 320px에서 표 폭은 288px이고 칸마다 9px(오른쪽 패딩 8px 등)이 빠진다.
  `CloudFormation`(굵기 500, 105.7px)은 41%, `Organizations`(89.4px)는 35% 열이어야 들어간다(phase 48, 배포 사이트
  Chrome 실측). `PrivateLink`(73.4px)는 32% 열이어야 들어간다 — 24% 행 머리 열에서는 `Priva`와 `teLink`로 끊겼다(phase 52).
  긴 한글 낱말도 같다. `애플리케이션`·`엔드포인트로`(굵기 400, 72.7px)는 줄을 바꿀 자리가 없어 이보다 좁은 칸에서 끊긴다.
  **글꼴은 운영체제를 따르므로 폭도 기기마다 다르다.** Windows Chrome에서는 한글이 한 글자 14px이라 `애플리케이션`·`엔드포인트를`이
  84px, `스로틀링이`가 70px이고, `CloudFormation`은 101.9px, `WebSocket`(굵기 500)은 70.6px이다(phase 59, 배포 사이트 실측).
  같은 환경에서 `OpenSearch`·`CloudWatch`(굵기 500)는 76.7px, `Formation`은 64.6px, `DataBrew`는 60.2px이다(phase 62, `vite preview` 실측).
  `비활성화하거나`(굵기 400, 98px)는 40% 열(안쪽 폭 100px)에 2px 여유로 들어갔다(phase 63, 같은 환경). 이 칸의 글을 고칠 때 더 긴 낱말을 넣지 마라.
  **표는 스크롤 막대가 15px를 차지하는 320px(Windows Chrome iframe, 표 폭 273px)에서도 끊기지 않게 맞춘다.** phase 61~63은 그 폭에서도 들어갔고,
  phase 64의 컨테이너 표 둘은 그 폭에서 끊겨 고쳤다. 실행 방식 표는 `App2Container`(굵기 500, 95.2px)가 들어가도록 행 머리 열을 39%(안쪽 97px)로 두고,
  37% 열(안쪽 92px)에 들어가지 않는 `애플리케이션을`(98px)은 `애플리케이션`(84px) 뒤를 띄어 쓰도록 문장을 바꿨다. Connector·Anywhere 표는
  `마이그레이션`(굵기 500, 84px)이 들어가도록 35% 열로 두었다. 이 표들의 글을 고칠 때 더 긴 낱말을 넣지 마라.
  열 폭은 더 넓게 잰 쪽에 맞춘다.
  영문 이름 바로 뒤에 조사를 붙이면 그만큼 한 덩어리가 길어진다. `X-Ray`처럼 하이픈이 있는 이름은
  줄 끝에서 하이픈 뒤로 갈라지므로 칸의 첫머리에 둔다.
- **판정을 색으로 칠하지 마라.** `가능`/`불가`를 글자로 쓰고 굵기만 준다. 초록·빨강은 정답/오답
  표시가 점유했다(ADR-036).
- 글자 크기는 `text-sm`, 행 구분선은 `border-disabled`. 줄무늬 배경을 쓰지 마라.

### 약어 툴팁 (ADR-037)

VPC 주제의 개념 본문에서, 데이터 안에 뜻풀이 근거가 있는 약어에만 붙는다. **개념마다 처음 나오는
곳 하나**에만 단다. 주제 맨 위의 약어 사전 패널은 두지 않는다.

- 약어는 `<button type="button">`이다. 점선 밑줄(`underline decoration-dotted underline-offset-4`)만
  두고 색을 바꾸지 않는다. 터치 영역 규칙의 예외다 — 본문 글자 안에 있으므로 줄 높이를 늘리지 않는다.
- 마우스를 올리거나, 초점을 받거나, 누르면 툴팁이 뜬다. `Escape`·바깥 누르기·초점 이탈·스크롤로
  닫힌다. 툴팁은 `role="tooltip"`이고 약어 버튼이 `aria-describedby`로 가리킨다.
- 툴팁은 `bg-panel`·`border-disabled`·`text-sm`이다. 화면 가장자리에서 8px 안쪽으로 붙잡아
  320px에서도 잘리지 않게 한다. **나타나는 애니메이션을 넣지 마라**(「애니메이션」).
- 내용은 두 줄이다. 윗줄은 `약어 = 풀네임`(풀네임이 데이터에 없으면 약어만), 아랫줄은 뜻.

## 레이아웃

- 주제 목록: `max-w-3xl`
- 개념 본문: `max-w-2xl` — 한 줄이 길어지면 읽기가 무너진다. 이 값을 넘기지 마라.
- 확인 문제: `max-w-2xl`
- 검색: `max-w-3xl` — 목록형 화면이라 주제 목록과 같다
- 정렬: 셸 안에서 좌측 정렬 기본. 텍스트를 중앙 정렬하지 마라.
  (셸 자체를 화면 가운데 두는 것은 아래 "데스크톱"을 봐라. 둘은 다른 이야기다.)
- 간격: 요소 간 `gap-3`, 섹션 간 `space-y-8`

### 데스크톱

**넓은 화면에서 콘텐츠가 왼쪽에 붙으면 안 된다.** `max-w-*`만으로는 폭이 상한선에서
멈출 뿐 화면 가운데로 오지 않는다. 1440px에서 실측한 결과다.

| 항목 | `mx-auto` 없을 때 | 셸 적용 후 |
|------|------|------|
| 본문 위치 | left=32, right=800 (오른쪽 640px 공백) | left=336, right=1104 |
| 본문 중심 ↔ 화면 중심 | **-304px** | 0 |
| 헤더 로고 ↔ 내비 간격 | **1123px** | 515px |
| 로고 왼쪽 ↔ 본문 왼쪽 | 어긋남 | **0px (세로축 일치)** |

**헤더와 본문은 같은 셸을 공유한다.** `Layout`이 헤더 안쪽과 `main` 안쪽에 동일한
중앙 정렬 컨테이너를 둔다. 헤더에 폭 제한이 없으면 `justify-between`이 로고와 내비를
화면 양 끝으로 밀어내, 본문은 왼쪽에 몰려 있는데 헤더만 가로로 찢어진다.

셸 폭은 `max-w-3xl`(768px)이다. 주제 목록·복습의 폭과 같다.

**패딩과 폭 제한은 서로 다른 요소에 나눠 건다.**

```
바깥: px-5 py-8 sm:px-8        <- 좌우 패딩만
안쪽: mx-auto max-w-3xl        <- 폭 제한 + 중앙 정렬만
```

한 요소에 둘 다 걸지 마라. `box-sizing: border-box`라 `max-w-3xl`에서 패딩이 안쪽으로
파고들어 실제 본문 폭이 768px보다 좁아진다.

개념 읽기·확인 문제(`max-w-2xl`)는 셸 안에서 **왼쪽 정렬로 둔다.** `mx-auto`를 붙이지 마라.
화면 중심에서 48px 왼쪽에 놓이지만, 로고·페이지 제목·본문이 한 세로축에서 시작한다.
시선이 세로축 하나만 따라가는 쪽이 낫다.

큰 화면 전용 브레이크포인트(`lg:`·`xl:`)를 새로 도입하지 마라. 셸 하나로 충분하다.
예외는 도식의 배치 전환 하나다(768px, `useWideDiagram()`, 「도식」의 「넓은 화면의 가로형」, ADR-047·ADR-048). 셸과 본문 폭은 그대로다.
다단 레이아웃·사이드바·2열 카드 그리드를 만들지 마라.

### 모바일

**세로 스크롤만 있는 앱이다. 가로 스크롤이 생기면 버그다.**

기준 폭은 **320px**이다. 이 폭에서 어떤 요소도 화면 밖으로 나가면 안 된다.
`max-w-*`는 상한일 뿐 하한을 보장하지 않는다 — 좁은 화면에서 무엇이 안 줄어드는지가 문제다.

- 좁힐 수 없는 폭을 만들지 마라. `flex`/`grid` 자식은 기본값이 `min-width: auto`라서
  **내용의 min-content보다 작아지지 않는다.** 긴 텍스트가 든 자식은 이 값 때문에 컨테이너를 밀어낸다.
- 가로줄에 `shrink-0`을 붙인 요소가 있으면, 나머지가 0까지 줄어든 뒤 그 요소가 화면 밖으로 밀려난다.
  `shrink-0`은 폭이 확정된 작은 요소(별 표시·배지)에만 쓴다.

### 터치 영역

누를 수 있는 모든 것(`a`, `button`)은 **최소 높이 44px**을 확보한다.
`px-4 py-2`만으로는 36~40px에 그친다. `inline-flex items-center min-h-[44px]`를 함께 쓴다.

카드처럼 이미 `p-5` 이상인 블록 링크는 예외다. 이미 충분히 크다.

## 타이포그래피

| 용도 | 스타일 |
|------|--------|
| 페이지 제목 | `text-2xl font-semibold text-neutral-50` |
| 주제 제목 | `text-lg font-medium text-neutral-100` |
| 개념 이름 | `text-base font-medium text-neutral-100` |
| 한 줄 요약 | `text-sm text-neutral-400` |
| 본문 | `text-[15px] text-neutral-300 leading-7` |
| 본문 속 강조 (ADR-051) | `<strong>`: `font-semibold text-neutral-100` — 강조색·배경 없이 굵기와 밝기만 올린다 |
| 본문 속 코드 표기 | `font-mono text-[0.9em]` — 색·배경 없이 본문 색을 물려받는다 |
| 본문 목록 | `<ul>`: `list-disc space-y-2 pl-5 text-[15px] leading-7 text-neutral-300 marker:text-neutral-500`, `<li>`: `break-keep` |
| 단계 목록 (ADR-050) | `<ol start>`: `list-decimal space-y-4 pl-7` + 본문 글자, 하위 `<ul>`: 1단 `list-disc`·2단 `list-[circle]` `mt-2 space-y-2 pl-5`, 항목 안 문단: `mt-2`. 번호·글머리 기호는 `marker:text-neutral-500` |
| 라벨·메타 | `text-xs text-neutral-500` |

**본문 속 강조(ADR-051)**: 개념 요약·본문의 `**…**`는 `<strong>`으로 그리고 표지는 지운다. 굵기는 600(`font-semibold`)이다 — 500이던 때는 본문(400)과
차이가 작아 강조로 읽히지 않았다. 강조색·밑줄·배경을 붙이지 마라. 이유: 색은 정답/오답/중요도에만 쓰고, 배경은 하이라이트다. 무엇을 감싸는지는
데이터의 일이다 — 시험에서 판단을 가르는 구절만 감싸고, 개념 하나에 셋 이하다(ADR-051 「기준 2」).

**본문 속 코드 표기(ADR-044)**: 개념 요약·본문에서 백틱 한 쌍으로 감싼 말(정책 요소·조건 키·예외 이름·경로처럼 그대로 치는 글자)은
`<code>`로 그리고 백틱 기호는 지운다. 배경 칩·테두리·색을 붙이지 마라. 이유: 색은 정답/오답/중요도에만 쓰고, 배경은 하이라이트다.
긴 식별자는 아래 `break-anywhere`가 끊는다.

**본문 목록(ADR-046)**: 개념 본문에서 `- `로 시작하는 문단은 목록 항목이고, 잇닿은 항목들이 글머리 기호 목록 하나가 된다. 글자는 본문과
같고 글머리 기호만 라벨 색(`neutral-500`)으로 낮춘다. 항목 사이(`space-y-2`, 8px)를 문단 사이(`space-y-3`, 12px)보다 좁혀 목록이 한 덩어리로
읽히게 한다. 번호 목록·중첩 목록·체크 표시를 만들지 마라. 이유: 이 표지는 한 대상의 종류를 나란히 세우는 데만 쓴다(ADR-046 「기준」).
예외는 아래 「단계 목록」 하나다.
항목은 굵은 이름으로 시작하고, 이름이 한국어면 바로 뒤에 영문 이름을 괄호로 붙인다(`**파일 게이트웨이**(S3 File Gateway)는`).

**단계 목록(ADR-050)**: 따라 하는 절차 하나(`identity-federation.iam-roles-anywhere`)에만 쓴다. `N. `로 시작하는 문단이 번호 항목이고, 두 칸·네 칸
들여쓴 문단이 그 아래 하위 항목(`- `)이나 항목 안 문단(표지 없음)이 된다. 번호 항목 사이(`space-y-4`, 16px)를 하위 항목 사이(8px)보다 넓혀 단계가
덩어리로 갈리게 한다. 두 자리 번호(19.)가 들어가도록 `pl-7`(28px)이다. 다른 개념으로 넓히지 마라 — 데이터 테스트가 막는다.

한글 본문에는 `break-keep`을 적용한다. 이유: 기본 줄바꿈은 한글 단어를 중간에서 끊는다.

**`break-keep`은 항상 `break-anywhere`와 함께 쓴다.**

`break-keep`(`word-break: keep-all`)만 쓰면 공백 없는 긴 문자열이 아예 줄바꿈되지 않는다.
이 앱의 주제 제목은 `EMR·Spark·Redshift·Athena·Kinesis·Glue·X-Ray·CloudWatch`처럼
가운뎃점으로 이어진 55자짜리 한 덩어리다. 가운뎃점은 줄바꿈 기회가 아니다.

`break-anywhere`는 `overflow-wrap: anywhere`이며 `src/index.css`에 정의돼 있다.
줄에 들어가지 않는 긴 덩어리만 강제로 끊고, 평소에는 공백에서 정상적으로 줄바꿈한다.
한글 단어는 `break-keep`이 계속 보호한다.

Tailwind의 `break-words`(`overflow-wrap: break-word`)로 대체하지 마라.
`break-word`는 **min-content 크기를 줄이지 않아** flex/grid 자식의 `min-width: auto`를 이기지 못한다.
390px 화면에서 실측했을 때 `break-words`는 오버플로를 전혀 해소하지 못했고, `anywhere`만 통했다.
`break-all`은 통하지만 영문·한글을 아무 데서나 끊어 가독성을 잃는다.

`overflow-wrap`은 상속되므로 화면 최상위 `section`에 한 번만 붙이면 하위 전체에 적용된다.

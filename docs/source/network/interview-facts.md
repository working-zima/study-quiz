## Q21 OSI 7계층 → protocols-encapsulation, ethernet

- **묻는 것**: OSI 참조 모델의 일곱 계층이 각각 무슨 일을 맡는가.
- **사실**
  - OSI 참조 모델은 통신을 일곱 계층으로 나누고 계층마다 맡을 일을 정한 모델이다. ITU-T X.200과 ISO/IEC 7498-1이 같은 본문이다.
  - 물리 계층: 비트(0과 1)를 전기 신호나 빛 같은 물리 신호로 바꿔 매체로 실어 나른다.
  - 데이터 링크 계층: 데이터를 프레임으로 묶어 보내고, 받는 쪽은 프레임을 풀어 안의 데이터를 꺼낸다. 물리 계층에서 생긴 오류를 검출하고, 프로토콜에 따라 고치기도 한다.
    이더넷은 FCS로 오류를 검출하면 그 프레임을 위 계층에 넘기지 않을 뿐 고치지 않는다. (수정 I1)
  - 네트워크 계층: 목적지까지의 경로를 정해 데이터를 전달한다. OSI 모델은 「네트워크 주소」라고만 하고, IP 주소는 TCP/IP 모델에서 이 자리에 대응하는 인터넷 계층의 주소다. (수정 I9)
  - 전송 계층: OSI 정의로는 위 계층이 전달 방식을 신경 쓰지 않도록 신뢰성 있는 전달을 맡는다. TCP/IP의 전송 계층에서는 TCP가 신뢰성을 더하고 UDP는 더하지 않는다. (수정 I10)
  - 세션 계층: 양쪽의 대화(세션)를 열고, 주고받는 순서를 맞추고, 질서 있게 닫는 일을 관리한다.
  - 표현 계층: 시스템마다 다른 데이터 표현 형식을 공통 형식으로 맞춰, 위 계층이 형식 차이를 신경 쓰지 않게 한다.
  - 응용 계층: 응용 프로그램(웹 브라우저, 메일, 파일 전송 등)이 네트워크 기능을 쓰는 유일한 창구다.
- **주제**: `protocols-encapsulation`(OSI·TCP/IP 모델과 계층 대응), `ethernet`(FCS로 오류 검출)
- **문항 형식 메모**: 예/아니요 감 — 「데이터 링크 계층은 검출한 오류를 늘 고친다」(아니요, I1), 「전송 계층 프로토콜은 모두 신뢰성을 보장한다」(아니요, I10).

## Q22 TCP와 UDP의 차이 → tcp-udp, tcp-retransmission

- **묻는 것**: TCP와 UDP는 무엇이 다른가.
- **사실**
  - TCP는 연결형이다. 데이터를 보내기 전에 연결을 맺고, 그 연결을 유지하며 주고받는다.
  - TCP는 순서 번호로 순서를 맞추고 빠진 세그먼트를 알아챈다. 손상은 세그먼트마다 붙는 체크섬으로 검출하고, 잃었거나 손상된 데이터는 다시 보내서(재전송) 복구한다.
    받은 데이터를 그 자리에서 고치는 것도, 네트워크에서 패킷이 사라지는 일 자체를 막는 것도 아니다. (수정 I2)
  - 그래서 데이터가 빠짐없이 순서대로 가야 하는 응용에 TCP가 맞는다. UDP 표준도 순서 있고 신뢰할 수 있는 전달이 필요한 응용은 TCP를 쓰라고 적는다.
  - UDP는 비연결형이라 연결을 맺지 않고 바로 보낸다. 순서를 맞추지 않고, 잃은 데이터그램을 다시 보내지도 않는다.
  - UDP도 체크섬으로 손상을 검출한다. 맞지 않는 데이터그램은 알리지 않고 버리며, 고치거나 다시 보내지는 않는다. IPv4에서는 체크섬을 생략할 수 있지만 IPv6에서는 기본적으로 붙여야 한다. (수정 I3)
  - UDP를 쓰는 예는 HTTP/3, NTP, RIP, DHCP이고 DNS도 주로 UDP를 쓴다([강의 p253], L11). 「UDP는 대용량 전송에 맞는다」는 쓰지 않는다. (수정 I4)
- **주제**: `tcp-udp`(두 프로토콜의 특성과 헤더), `tcp-retransmission`(재전송으로 복구)
- **문항 형식 메모**: 예/아니요 감 — 「UDP는 손상된 데이터그램을 알아채지 못한다」(아니요, I3), 「TCP는 손상된 세그먼트를 받은 쪽에서 고쳐 쓴다」(아니요, I2).

## Q23 ARP의 쓰임 → arp

- **묻는 것**: ARP가 무엇이고 왜 쓰는가.
- **사실**
  - ARP는 IP 주소(네트워크 계층이 쓰는 논리 주소)로 MAC 주소(데이터 링크 계층이 쓰는 물리 주소)를 찾아 둘을 짝지어 주는 프로토콜이다.
  - 상대의 IP 주소만 알고 MAC 주소는 모를 때 ARP로 그 MAC 주소를 알아낸다. 프레임을 실제로 보내려면 받는 쪽의 MAC 주소가 있어야 하기 때문이다.
- **주제**: `arp`

## Q24 TCP 연결 수립 과정 → tcp-connection

- **묻는 것**: TCP 연결은 어떤 순서로 맺어지는가.
- **사실**
  - 세 번 주고받는 3-way handshake로 맺는다.
  - ① 클라이언트가 SYN 플래그를 켠 세그먼트를 보내 연결을 청한다. ② 서버가 SYN과 ACK를 함께 켠 세그먼트로 답한다. ③ 클라이언트가 ACK를 켠 세그먼트를 보내면 연결이 맺어진다.
- **주제**: `tcp-connection`

## Q25 서브넷 마스크 → ip-addressing

- **묻는 것**: 서브넷 마스크가 무엇이고, 192.168.1.100의 마스크가 255.255.255.0이라는 것은 무슨 뜻인가.
- **사실**
  - 서브넷 마스크는 IP 주소에서 네트워크를 가리키는 부분과 호스트를 가리키는 부분의 경계를 정하는 32비트 값이다.
  - 비트로 펼치면 네트워크 쪽 자리가 1, 호스트 쪽 자리가 0이고, 1은 왼쪽부터 끊김 없이 이어진다.
  - 적을 때는 255.255.255.0처럼 8비트씩 끊은 10진수 넷으로 쓰거나, 이어진 1의 개수를 주소 뒤에 `/24`처럼 붙인다(CIDR 표기). 2진수는 계산할 때 비트를 펼쳐 보는 형식이다. (수정 I5)
  - 예시에서 255.255.255.0은 앞 24비트가 네트워크라는 뜻이다. 그래서 192.168.1까지가 네트워크, 마지막 100이 호스트를 가리키고,
    호스트 자리를 0으로 둔 네트워크 주소는 192.168.1.0이다([강의 p171, p175]).
- **주제**: `ip-addressing`
- **문항 형식 메모**: 예/아니요 감 — 「`/24`는 서브넷 마스크 255.255.255.0과 같은 경계를 가리킨다」(예, I5).

## Q26 쿠키의 정체와 쓰임 → http-cookie, http-basics

- **묻는 것**: 쿠키가 무엇이고 어디에, 왜 쓰는가.
- **사실**
  - HTTP는 요청과 요청 사이에 상태를 기억하지 않는다. 그래서 다른 장치가 없으면 서버는 요청을 보낸 클라이언트가 지금 어떤 상태(로그인했는지 등)인지 알 수 없다.
  - 쿠키는 서버가 만들어 클라이언트에 맡겨 두는 작은 정보다. 서버는 돌아온 쿠키로 클라이언트의 상태를 알아보고, 이렇게 상태가 있는 세션을 만든다.
  - 서버는 응답의 Set-Cookie 헤더로 쿠키를 주고, 클라이언트는 다음 요청부터 그 쿠키를 Cookie 헤더에 담아 보낸다.
- **주제**: `http-cookie`(쿠키와 두 헤더), `http-basics`(HTTP가 상태를 기억하지 않는다는 특성)

## Q27 www.example.com의 이름 풀이 과정 → dns

- **묻는 것**: 브라우저에 넣은 이름 www.example.com이 IP 주소로 풀리기까지 어떤 과정을 거치는가.
- **사실**
  - 먼저 캐시에 저장해 둔 답이 있는지 본다. 있으면 그 답을 쓴다.
  - 없으면 클라이언트가 로컬 DNS 서버(리졸버)에 묻는다.
  - 로컬 DNS 서버는 루트 DNS 서버에 묻고, 루트가 알려 준 TLD(.com) 서버에 묻고, TLD 서버가 알려 준 권한 있는(authoritative) 서버에 물어 www.example.com의 IP 주소를 얻는다.
    반복적 질의에서 루트·TLD 서버는 다음에 물을 서버를 알려 줄 뿐이고, 차례로 묻고 다니는 쪽은 로컬 DNS 서버다. (수정 I11)
  - 로컬 DNS 서버는 얻은 답을 캐시에 넣고 클라이언트에 돌려준다. (수정 I11)
  - 서버가 끝까지 대신 찾아 주는 재귀적 질의인지, 다음 서버만 알려 주는 반복적 질의인지에 따라 세부 흐름이 다르다. 재귀적 질의는 질의의 RD 비트로 청하고, 해 줄지는 네임 서버가 정한다. (수정 I11)
- **주제**: `dns`
- **문항 형식 메모**: 예/아니요 감 — 「반복적 질의에서는 루트 DNS 서버가 TLD 서버에 대신 물어 준다」(아니요, I11).

## Q28 리다이렉션의 정체와 쓰임 → http-messages, http-cache

- **묻는 것**: 리다이렉션이 무엇이고 왜 쓰는가.
- **사실**
  - 리다이렉션(3xx 응답)은 요청을 끝내려면 클라이언트가 한 단계 더 해야 한다고 알리는 응답이다. (수정 I6)
  - 그 가운데 자원을 다른 URI에서 찾으라고 알리는 것은 301·302·307·308이고, 새 URI는 응답의 Location 헤더에 담긴다. (수정 I6)
  - 사이트 구성을 바꾸거나 URL을 옮긴 뒤 옛 주소를 새 주소로 이어 줄 때 쓴다(영구 이동 301·308). 점검 중처럼 잠시 다른 URL로 보내야 할 때도 쓴다(임시 이동 302·307).
  - 304 Not Modified도 3xx다. 다른 곳으로 보내는 것이 아니라 클라이언트가 저장해 둔 사본을 그대로 쓰라고 보내는 응답이라 본문이 없다. (I6 — 확인 결과 답이 맞다)
  - 「URL 간소화」를 쓰임으로 든 부분은 근거가 없어 쓰지 않는다. (수정 I12)
- **주제**: `http-messages`(3xx 상태 코드와 Location), `http-cache`(304로 저장한 사본 쓰기)
- **문항 형식 메모**: 예/아니요 감 — 「304 Not Modified는 Location 헤더로 새 URI를 알려 준다」(아니요, I6).

## Q29 4xx 오류와 5xx 오류의 차이 → http-messages

- **묻는 것**: HTTP 400번대 오류와 500번대 오류는 어떻게 다른가.
- **사실**
  - 4xx는 클라이언트 오류다. 요청한 쪽이 잘못한 것으로 보일 때 쓴다(없는 자원, 인증 없음, 권한 없음 등).
  - 5xx는 서버 오류다. 서버가 스스로 잘못했거나 요청을 처리할 능력이 없다는 것을 알 때 쓴다.
  - 같은 요청을 다시 보냈을 때 결과가 바뀔지는 4xx·5xx라는 범위로 정해지지 않고 코드마다 다르다.
    408(요청 시간 초과)은 4xx지만 같은 요청을 다시 보내도 되고, 429(요청이 너무 많음)는 기다릴 시간을 Retry-After로 알릴 수 있다.
    501(구현되지 않음)은 5xx지만 서버가 그 기능을 지원하지 않는다는 뜻이라 다시 보내도 달라질 까닭이 없고, 503(서비스 이용 불가)은 일시적 과부하나 점검이라 시간이 지나면 될 수 있다. (수정 I7)
- **주제**: `http-messages`
- **문항 형식 메모**: 예/아니요 감 — 「4xx 응답을 받은 요청은 다시 보내도 결과가 바뀌지 않는다」(아니요, I7 — 408·429).

## Q30 포트와 웰 노운 포트 → ports

- **묻는 것**: 포트가 무엇이고, 그 가운데 웰 노운 포트는 무엇인가.
- **사실**
  - 포트 번호는 한 호스트 안에서 데이터를 받을 응용 프로그램을 가려내는 번호다.
  - 0~1023번이 웰 노운 포트로, 널리 쓰는 프로토콜의 서비스가 주로 쓰는 번호다(예: HTTP 80, HTTPS 443). 그 위로 등록된 포트(1024~49151)와 동적 포트(49152~65535)가 있다([강의 p223–p224]).
- **주제**: `ports`

## Q31 ICMP의 쓰임 → icmp

- **묻는 것**: ICMP는 어디에 쓰는 프로토콜인가.
- **사실**
  - ICMP는 IP 패킷이 전달되는 과정에서 생긴 오류를 알리고, 네트워크 상태를 진단할 정보를 얻는 데 쓴다.
  - ICMP를 쓰는 대표적인 명령이 ping이다. 에코 요청을 보내 에코 응답이 돌아오는지로 상대 호스트에 닿을 수 있는지 확인한다([강의 p154–p156]).
- **주제**: `icmp`

## Q32 TCP 혼잡 제어 → tcp-flow-congestion

- **묻는 것**: TCP의 혼잡 제어는 무엇인가.
- **사실**
  - 네트워크 안에 처리할 패킷이 몰려 패킷을 잃기 쉬운 상태를 혼잡이라 한다.
  - TCP는 혼잡을 다루는 알고리즘을 갖고 있다. 대표적인 것이 느린 시작과 혼잡 회피이고, 표준은 빠른 재전송·빠른 회복까지 넷을 함께 정한다.
  - 이 알고리즘들은 혼잡 윈도우라는 변수를 조절한다. 혼잡 윈도우는 확인 응답을 받기 전에 보내는 쪽이 내보낼 수 있는 데이터 양을 혼잡 쪽에서 제한하는 값이고,
    실제로 내보낼 수 있는 양은 혼잡 윈도우와 받는 쪽이 알린 수신 윈도우 가운데 작은 쪽이다. (수정 I13)
- **주제**: `tcp-flow-congestion`
- **문항 형식 메모**: 예/아니요 감 — 「보내는 쪽은 혼잡 윈도우 크기만큼은 언제나 한꺼번에 보낼 수 있다」(아니요, I13 — 수신 윈도우가 더 작으면 그쪽이 한도다).

## Q33 인터넷이 갑자기 안 될 때 → icmp, network-basics

- **묻는 것**: 잘 되던 인터넷이 갑자기 안 되면 무엇을 차례로 확인하는가.
- **사실**(답이 든 점검 항목)
  - 케이블이나 무선 같은 물리적 연결이 살아 있는지 본다.
  - 방화벽이나 보안 프로그램이 통신을 막고 있지 않은지 본다.
  - 장비를 다시 켜 볼 수 있는지 본다.
  - 바깥 연결: 인터넷 쪽 주소인 구글 공용 DNS 서버(8.8.8.8)에 ping을 보내 응답이 오는지 본다.
  - 안쪽 연결: 가까운 라우터(공유기)에 ping을 보내 응답이 오는지 본다.
- **주제**: `icmp`(ping이 쓰는 에코 요청·응답), `network-basics`(ping으로 패킷 손실을 보는 예, [강의 p47]). 강의도 ping 대상과 DNS 서버의 예로 8.8.8.8을 쓴다([강의 p47, p198]).
  물리 연결 점검·방화벽·재부팅은 강의 범위 밖이라 개념이나 문항으로 쓰지 않는다.

## Q34 트래픽이 몰릴 때의 웹 서버 구성 → network-basics, uri-web-server, http-basics, http-cache

- **묻는 것**: 트래픽이 지나치게 몰릴 때 웹 서버를 어떻게 꾸리면 좋은가.
- **사실**(답이 든 구성)
  - 로드 밸런서를 앞에 두어 요청을 여러 웹 서버로 나눠 보낸다.
  - 할 수 있으면 오토 스케일링으로 부하에 따라 서버 수를 자동으로 늘린다(스케일 아웃).
  - 이미지·CSS·JavaScript 같은 정적 콘텐츠는 캐시해 두고, 같은 콘텐츠를 매번 다시 만들어 보내는 대신 저장해 둔 사본을 내준다.
  - 데이터베이스를 쓴다면 그것도 이중화한다.
- **주제**: `network-basics`(트래픽을 분산한다는 말, [강의 p42]), `uri-web-server`(웹 서버와 WAS를 나누면 WAS를 여럿 붙이기 쉽다, [강의 p388–p392]),
  `http-basics`(서버가 상태를 기억하지 않아 서버를 늘리기 쉽다, [강의 p405]), `http-cache`(캐시).
  로드 밸런서·오토 스케일링·DB 이중화라는 장비와 구성은 강의 범위 밖이다. 개념·문항에는 강의가 다루는 「트래픽 분산」, 「서버를 늘리기 쉽다」, 「캐시」까지만 쓴다.

## Q35 HTTP 캐시를 검증하는 방법 → http-cache

- **묻는 것**: 캐시해 둔 자원이 아직 유효한지 HTTP로 어떻게 확인하는가.
- **사실**
  - 첫째 방법: 서버가 응답에 붙여 준 `ETag`(자원의 버전을 가리는 식별 문자열)를, 클라이언트가 다음 요청의 `If-None-Match` 헤더에 실어 아직 같은지 묻는다. (수정 I14)
  - 둘째 방법: 서버가 알려 준 `Last-Modified`(마지막으로 바뀐 시각)를 `If-Modified-Since` 헤더에 실어 그 뒤로 바뀌었는지 묻는다.
  - 바뀌지 않았으면 서버는 `304 Not Modified`로 답하고, 클라이언트는 저장해 둔 사본을 그대로 쓴다.
- **주제**: `http-cache`

## Q36 Connection: keep-alive의 뜻 → http-basics, http-headers

- **묻는 것**: 요청이나 응답에 실린 `Connection: keep-alive`는 무엇을 뜻하는가.
- **사실**
  - 지속 연결은 TCP 연결 하나를 닫지 않고 그 위에서 요청과 응답을 여러 번 주고받는 방식이다.
  - `Connection: keep-alive`는 연결을 이어 두자는 표시다. HTTP/1.0은 응답마다 연결을 닫는 것이 기본이라, 이 값을 보내고 상대가 받아들여야 연결이 이어졌다.
    HTTP/1.1부터는 지속 연결이 기본이라 이 헤더가 없어도 연결이 이어지고, 닫으려면 `Connection: close`를 보낸다. HTTP/2·HTTP/3에서는 Connection 같은 연결 전용 헤더를 쓰지 않는다. (수정 I15)
- **주제**: `http-basics`(지속 연결), `http-headers`(Connection 헤더)
- **문항 형식 메모**: 예/아니요 감 — 「HTTP/1.1에서 지속 연결을 쓰려면 `Connection: keep-alive`를 꼭 보내야 한다」(아니요, I15).

## Q37 IPv6가 생긴 까닭 → ip-protocol

- **묻는 것**: IPv4가 있는데 IPv6가 왜 나왔는가.
- **사실**
  - IPv4 주소는 32비트라 이론상 2^32 = 4,294,967,296개, 곧 약 43억 개다. (I8 — 확인 결과 답이 맞다)
  - 전 세계 호스트에 나눠 주기에 이 수가 넉넉하지 않아서 주소를 128비트로 늘린 IPv6가 나왔다. IPv6 주소는 이론상 2^128개다.
- **주제**: `ip-protocol`

## Q38 UDP가 TCP보다 빠른 까닭 → tcp-udp

- **묻는 것**: UDP는 왜 TCP보다 빠른가.
- **사실**
  - UDP는 TCP와 달리 보내기 전에 연결을 맺는 단계가 없다.
  - 순서를 맞추지 않고, 잃은 것을 다시 보내지 않고, 흐름 제어·혼잡 제어로 보내는 속도를 조절하지도 않는다. 연결 관리와 신뢰성 장치가 없는 만큼 절차가 적다.
  - 다만 체크섬으로 손상을 검출하는 일은 UDP도 한다(Q22, 수정 I3).
- **주제**: `tcp-udp`
- **문항 형식 메모**: 예/아니요 감 — 「UDP가 빠른 까닭 가운데 하나는 손상 검사(체크섬)를 하지 않기 때문이다」(아니요, I3).

## Q39 쿠키의 보안 → http-cookie

- **묻는 것**: 쿠키는 보안에 민감한가. 그렇다면 보안을 높이는 방법은 무엇인가.
- **사실**
  - 민감하다. 그래서 중요한 개인정보는 쿠키에 담지 않는 편이 좋다.
  - `Secure` 속성을 붙이면 HTTPS 같은 안전한 채널로 보낼 때만 쿠키를 싣는다.
  - `HttpOnly` 속성을 붙이면 JavaScript(`document.cookie` 등)로 쿠키를 읽을 수 없다. 다만 스크립트가 보낸 요청에도 쿠키는 실리므로,
    XSS 자체를 막는 것이 아니라 쿠키를 빼앗기는 피해를 줄인다(강의 수정 이력 L23).
- **주제**: `http-cookie`
- **문항 형식 메모**: 예/아니요 감 — 「`HttpOnly`를 붙이면 XSS 공격 자체가 막힌다」(아니요, L23).

## Q40 PUT과 PATCH의 차이 → http-messages

- **묻는 것**: HTTP 메서드 PUT과 PATCH는 어떻게 다른가.
- **사실**
  - PUT은 대상 자원을 요청 본문의 내용으로 통째로 바꾸라는 요청이다. 본문으로 덮어쓰는 것과 같고, 자원이 없으면 그 내용으로 새로 만든다([강의 p422]).
  - PATCH는 자원의 일부만 바꾸라는 요청이다. 바꿀 부분만 보낸다(강의 예: email 하나만 보내면 그 값만 바뀐다, [강의 p425–p426]).
- **주제**: `http-messages`

### I1 — 데이터 링크 계층이 오류를 「검출하고 수정」 (Q21) [후보 1]

- 답: 데이터 링크 계층을 데이터의 오류를 검출하고 고치는 계층으로 소개한다.
- 표준: OSI 참조 모델은 데이터 링크 계층이 물리 계층에서 생긴 오류를 검출하고 **경우에 따라** 고친다고 정의한다 — 고치는 것은 필수가 아니다.
  이더넷(IEEE 802.3)은 FCS 필드에 32비트 CRC 값을 담고, 받은 프레임에서 다시 계산한 CRC가 FCS와 다르면 그 프레임을 잘못된 MAC 프레임으로 본다.
  잘못된 프레임의 내용은 위 부계층(LLC·MAC Control)으로 넘기지 않는다. 오류를 고치는 절차는 없다.
- 근거: ITU-T X.200 §7.6.2.2 — https://www.itu.int/rec/T-REC-X.200-199407-I/en ,
  IEEE 802.3 §3.2.9, §3.4 — https://www.ieee802.org/3/as/public/0503/3d0_1_CMP.pdf (IEEE 802.3 작업 그룹의 802.3-2005 개정 초안 P802.3as D0.1이 3.2.9·3.4 본문을 싣고 있다)
- 처리: 한정해 쓴다 — 「데이터 링크 계층은 오류를 검출하고, 프로토콜에 따라 고치기도 한다. 이더넷은 오류가 있는 프레임을 위로 넘기지 않을 뿐 고치지 않는다」.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다. 강의는 FCS를 오류 검출용 CRC 필드로 설명해 표준과 맞다(Ch2-1 p69–p70).

### I2 — TCP가 손상된 데이터를 「감지하고 수정」, 패킷이 「손실되지 않도록 보장」 (Q22) [후보 2]

- 답: TCP는 손상된 데이터를 감지해 고치고, 패킷을 잃지 않도록 보장한다.
- 표준: TCP의 신뢰성은 잃은 패킷을 순서 번호로, 오류를 세그먼트마다 붙는 체크섬으로 검출하고, 그것을 재전송으로 바로잡는 것이다. 체크섬은 보내는 쪽이 만들고 받는 쪽이 반드시 검사한다.
  세그먼트는 오류(체크섬 검사 실패)나 혼잡으로 사라질 수 있고, TCP는 재전송으로 모든 세그먼트가 결국 전달되게 한다. 곧 받은 데이터를 그 자리에서 고치는 것이 아니고,
  네트워크에서 패킷이 사라지는 일 자체를 막는 것도 아니다.
- 근거: RFC 9293 §2.2, §3.1, §3.8 — https://www.rfc-editor.org/rfc/rfc9293
- 처리: 고쳐 쓴다 — 「TCP는 손상을 체크섬으로 검출하고, 잃었거나 손상된 데이터는 다시 보내서 복구한다」.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다. 강의는 TCP의 오류 제어를 재전송 기반으로 설명해 이 수정과 맞다(Ch4-7 p283–p289). 관련 — L13(TCP와 ARQ 세 방식).

### I3 — UDP는 손상된 데이터를 「감지하거나 수정하지 않는다」 (Q22) [후보 3]

- 답: UDP는 손상된 데이터를 감지하지도 고치지도 않는다.
- 표준: UDP 체크섬은 의사 헤더(IP 헤더에서 가져온 정보)·UDP 헤더·데이터에 대해 계산한다. 호스트는 체크섬을 만들고 검사할 수 있어야 하고 기본값은 켜짐이다.
  0이 아닌 체크섬이 맞지 않는 데이터그램은 알리지 않고 버린다 — 손상은 검출한다. 다만 전달과 중복 방지를 보장하지 않으므로 고치거나 다시 보내지는 않는다.
  체크섬 값 0은 보낸 쪽이 체크섬을 만들지 않았다는 뜻이라 IPv4에서는 생략할 수 있지만, IPv6에서는 UDP 체크섬이 선택이 아니다(UDP를 터널 캡슐화에 쓰는 경우만 예외).
- 근거: RFC 768 Introduction, Fields — https://www.rfc-editor.org/rfc/rfc768 , RFC 1122 §4.1.3.4 — https://www.rfc-editor.org/rfc/rfc1122 ,
  RFC 8200 §8.1 — https://www.rfc-editor.org/rfc/rfc8200
- 처리: 고쳐 쓴다 — 「UDP는 체크섬으로 손상을 검출해 그 데이터그램을 버리지만, 고치거나 다시 보내지는 않는다」. 「고치지 않는다」는 맞으므로 그대로 쓴다.
- 강의: 같은 문제 — L10(강의는 UDP 체크섬을 신뢰성과 관계없는 필드로 설명한다).

### I4 — UDP가 「대용량 데이터 전송」에 적합 (Q22) [후보 4]

- 답: TCP를 설명하며 대용량 전송에 맞는다고 하고, UDP를 설명하면서도 대용량 전송이나 신뢰성이 중요하지 않은 응용에 맞는다고 한다.
- 표준: UDP 표준은 UDP를 트랜잭션 지향 프로토콜로 소개하고, 순서 있고 신뢰할 수 있는 스트림 전달이 필요한 응용은 TCP를 쓰라고 한다.
  UDP 사용 지침(BCP 145)은 UDP로 대량 데이터를 보내는 응용이라면 TCP와 비슷한 혼잡 제어를 스스로 갖추라고 하고, UDP 대신 권하는 길로 TCP 같은 IETF 전송 프로토콜을 든다.
  UDP가 대용량 전송에 맞는다는 근거는 허용한 출처에서 찾지 못했다.
- 근거: RFC 768 Introduction — https://www.rfc-editor.org/rfc/rfc768 , RFC 8085 §3, §3.1.2 — https://www.rfc-editor.org/rfc/rfc8085
- 처리: 쓰지 않는다 — UDP를 쓰는 예는 강의 정리의 것(HTTP/3, NTP, RIP, DHCP, 그리고 주로 UDP를 쓰는 DNS — Ch4-3 p253)을 쓴다.
- 강의: 관련 — L11(강의가 든 UDP 예 가운데 DNS는 TCP도 쓴다).

### I5 — 서브넷 마스크는 「2진수로 표시」 (Q25) [후보 5]

- 답: 서브넷 마스크는 2진수로 표시되고, 1이 네트워크 부분·0이 호스트 부분이라고 한다.
- 표준: 서브넷 마스크는 32비트 값이고, 네트워크(와 서브넷) 자리의 비트가 1이다. 표준의 예시는 255.255.0.0, 255.255.252.0처럼 8비트씩 끊은 10진수(점 10진 표기)로 적는다.
  CIDR은 같은 경계를 주소 뒤의 `/`와 접두사 길이(앞에서부터 이어진 1의 개수)로 적는다 — 172.16.0.0/16의 마스크는 앞 16비트가 1, 뒤 16비트가 0인 255.255.0.0이다.
  마스크의 1은 왼쪽부터 끊김 없이 이어져야 한다. 1과 0으로 나눠 보는 것은 비트의 뜻이지 적는 형식이 아니다.
- 근거: RFC 950 §2.2, Appendix I, Appendix II — https://www.rfc-editor.org/rfc/rfc950 , RFC 4632 §3.1, §5.1 — https://www.rfc-editor.org/rfc/rfc4632
- 처리: 고쳐 쓴다 — 「서브넷 마스크는 보통 255.255.255.0처럼 점 10진수로, 또는 `/24`처럼 접두사 길이로 적는다. 비트로 펼치면 네트워크 쪽이 1, 호스트 쪽이 0이다」.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다. 강의는 마스크를 점 10진수와 2진수로 함께 보이고 CIDR 표기도 다룬다(Ch3-5 p174, p178).

### I6 — 리다이렉션을 「자원이 다른 곳에 있음을 알리는 응답」으로 정의하고 304를 함께 듦 (Q28) [후보 6]

- 답: 리다이렉션을 요청한 자원이 다른 곳에 있다고 알리는 응답으로 정의하고, 캐시된 데이터를 써도 되는지 알려 주기도 한다며 304를 든다.
- 표준: **304를 리다이렉션으로 묶은 것은 확인 결과 답이 맞다.** 3xx는 요청을 끝내려면 사용자 에이전트가 더 할 일이 있다는 뜻이고, 표준은 그 종류로
  자원이 다른 URI에 있을 수 있다고 알리는 것(301·302·307·308), 여러 후보 가운데 고르게 하는 것(300), 다른 자원으로 간접 응답을 주는 것(303),
  이전에 저장해 둔 결과로 보내는 것(304)을 든다. 304는 조건부 요청의 조건이 거짓이어서 보내는 응답으로, 클라이언트가 저장해 둔 표현을 쓰도록 보낸다 — 다른 URI로 보내지 않고 본문도 없다.
  MDN도 304를 특수한 리다이렉션으로 분류한다. 그러니 「자원이 다른 곳에 있다」는 정의는 301·302·307·308에만 맞는다. 301·308은 새 영구 URI를, 302·307은 잠시 머무는 다른 URI를 알린다.
- 근거: RFC 9110 §15.4, §15.4.2, §15.4.3, §15.4.5, §15.4.8, §15.4.9 — https://www.rfc-editor.org/rfc/rfc9110 ,
  MDN 「Redirections in HTTP」 Special redirections — https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections
- 처리: 304는 답대로 쓴다. 정의는 한정해 쓴다 — 「3xx는 요청을 끝내려면 클라이언트가 한 단계 더 해야 한다는 응답이고, 그 가운데 301·302·307·308이 Location으로 다른 URI를 알린다」.
- 강의: 같은 문제 — L22(강의도 304를 「캐시로 리다이렉트」로 맞게 설명하고, p435의 3XX 일반화만 한정했다).

### I7 — 4xx는 「다시 보내도 성공하지 않을 가능성이 높고」, 5xx는 「다시 보내면 결과가 달라질 수 있다」 (Q29) [후보 7]

- 답: 4xx는 원인이 클라이언트에 있어 같은 요청을 거듭 보내도 성공하기 어렵고, 5xx는 원인이 서버에 있어 거듭 보내면 결과가 바뀔 수 있다고 한다.
- 표준: 표준이 범위로 정하는 것은 원인 쪽이다 — 4xx는 클라이언트가 잘못한 것으로 보이는 경우, 5xx는 서버가 잘못했거나 요청한 메서드를 수행할 능력이 없음을 서버가 아는 경우다.
  다시 보냈을 때의 결과는 범위가 아니라 코드마다 다르다. 408(요청 시간 초과)은 클라이언트가 같은 요청을 다시 보내도 된다고 하고(MAY), 429(요청이 너무 많음)는 Retry-After 헤더로
  다시 보내기 전에 기다릴 시간을 알릴 수 있다. 501(구현되지 않음)은 서버가 그 기능을 지원하지 않는다는 뜻이고, 503(서비스 이용 불가)은 일시적 과부하나 예정된 점검이라
  Retry-After로 기다릴 시간을 알릴 수 있다. 4xx 응답에는 오류 상황과 그것이 일시적인지 영구적인지를 설명해 담는 것이 좋다(SHOULD).
- 근거: RFC 9110 §10.2.3, §15.5, §15.5.9, §15.6, §15.6.2, §15.6.4 — https://www.rfc-editor.org/rfc/rfc9110 , RFC 6585 §4 — https://www.rfc-editor.org/rfc/rfc6585
- 처리: 한정해 쓴다 — 「4xx는 원인이 클라이언트 쪽, 5xx는 서버 쪽이다」만 범위의 뜻으로 쓰고, 다시 보냈을 때의 결과는 「코드마다 다르다」로 쓴다. 408·429·501·503은 그 예로만 쓴다.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다(Ch5-5 p433, p436–p437).

### I8 — IPv4 주소는 「약 43억 개」 (Q37) [후보 8]

- 답: IPv4 주소는 32비트라 약 43억 개를 줄 수 있다.
- 표준: IPv4 주소는 4옥텟(32비트) 고정 길이다. 2^32 = 4,294,967,296이므로 약 43억 개가 맞다. IPv6는 주소 크기를 32비트에서 128비트로 늘렸다.
- 근거: RFC 791 §2.3 — https://www.rfc-editor.org/rfc/rfc791 , RFC 8200 §1 — https://www.rfc-editor.org/rfc/rfc8200
- 처리: **확인 결과 답이 맞다** — 그대로 쓴다.
- 강의: 관련 — L5(강의가 2^128의 주어를 IPv4로 잘못 적었다).

### I9 — OSI 네트워크 계층이 「IP 주소를 사용」 (Q21) [새로 찾음]

- 답: OSI 7계층을 설명하며 네트워크 계층을 IP 주소로 목적지까지의 경로를 정하는 계층이라고 한다.
- 표준: OSI 참조 모델의 네트워크 계층은 전송 계층이 경로 선택과 중계를 신경 쓰지 않게 하고, 네트워크 주소로 상대를 가린다 — 특정 프로토콜의 주소를 정하지 않는다.
  IP는 TCP/IP(인터넷 프로토콜 묶음)의 인터넷 계층 프로토콜로, 인터넷의 전송 프로토콜이 모두 출발지 호스트에서 목적지 호스트까지 데이터를 나르는 데 쓴다.
  인터넷 프로토콜 묶음은 4계층이라 OSI 7계층과 일대일로 맞지 않는다.
- 근거: ITU-T X.200 §7.5.2.1, §7.5.3.1.6 — https://www.itu.int/rec/T-REC-X.200-199407-I/en , RFC 1122 §1.1.3 — https://www.rfc-editor.org/rfc/rfc1122
- 처리: 한정해 쓴다 — 「OSI 네트워크 계층은 주소로 경로를 정해 전달한다. TCP/IP에서 이 자리는 인터넷 계층이고 IP 주소를 쓴다」. 계층 대응은 강의 그림(OSI 네트워크 ↔ TCP/IP 인터넷, p29–p31)을 쓴다.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다.

### I10 — 전송 계층은 「데이터를 신뢰성 있게 전달」 (Q21) [새로 찾음]

- 답: 전송 계층을 데이터를 신뢰성 있게 전달하는 계층으로 소개한다.
- 표준: OSI 정의로는 맞다 — 전송 서비스는 세션 계층이 신뢰성 있고 비용 효율적인 전달이 어떻게 이뤄지는지 신경 쓰지 않도록 투명한 전달을 제공한다.
  그러나 TCP/IP의 전송 계층에는 신뢰성 있는 연결형 서비스인 TCP와 비연결형 데이터그램 서비스인 UDP가 함께 있고, UDP는 전달을 보장하지 않는다.
- 근거: ITU-T X.200 §7.4.2.1 — https://www.itu.int/rec/T-REC-X.200-199407-I/en , RFC 1122 §1.1.3 — https://www.rfc-editor.org/rfc/rfc1122 ,
  RFC 768 Introduction — https://www.rfc-editor.org/rfc/rfc768
- 처리: 한정해 쓴다 — 「전송 계층은 신뢰성을 더할 수 있는 자리이고, TCP는 더하고 UDP는 더하지 않는다」.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다. 강의도 전송 계층의 역할로 신뢰성을 들고(p28, p219–p220) UDP는 비신뢰성이라고 따로 적는다(p250).

### I11 — DNS 질의가 서버에서 서버로 넘어가는 것처럼 적은 흐름 (Q27) [새로 찾음]

- 답: 캐시를 먼저 보고, 로컬 DNS 서버 → 루트, 루트 → TLD, TLD → authoritative 순으로 화살표를 이은 뒤, authoritative 서버로 알아낸 IP 주소를 로컬 DNS 서버에 넘긴다고 적는다.
  세부는 재귀적·반복적 질의에 따라 다르다고 덧붙인다.
- 표준: 반복적 질의에서는 질의를 받은 서버가 다른 서버를 알려 주고, 그 뒤 질의는 묻는 쪽이 이어 간다 — 루트·TLD 서버가 다음 서버에 대신 묻는 것이 아니다.
  재귀적 질의는 묻는 쪽이 질의에 RD(재귀 요청) 비트를 켜서 청하고, 네임 서버가 해 줄지는 선택이다. 리졸버는 먼저 자기 정보(캐시 포함)에서 답을 찾고, 없으면 아는 네임 서버 가운데
  가장 가까운 것부터 묻고, 받은 답은 캐시에 넣은 뒤 클라이언트에 돌려준다.
- 근거: RFC 1034 §4.3.1, §5.3.3 — https://www.rfc-editor.org/rfc/rfc1034
- 처리: 한정해 쓴다 — 단계 2~4를 「로컬 DNS 서버가 루트에 묻는다 → 루트가 TLD 서버를 알려 준다 → TLD 서버에 묻는다 → TLD 서버가 권한 있는 서버를 알려 준다 → 그 서버에 물어 IP 주소를 얻는다」로 쓰고,
  끝에 「캐시에 넣고 클라이언트에 돌려준다」를 더한다. 서버에서 서버로 화살표만 이은 순서는 쓰지 않는다.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다. 강의는 반복적 질의(p346)와 재귀적 질의(p347)를 그림으로 함께 다룬다.

### I12 — 리다이렉션의 쓰임에 「URL 간소화」 (Q28) [새로 찾음]

- 답: 리다이렉션을 쓰는 때로 사이트 재구성이나 URL 변경, URL 간소화, 임시 URL로 보낼 때를 든다.
- 표준: MDN이 드는 리다이렉션의 쓰임은 도메인 별칭(다른 이름이나 오타 도메인을 한 사이트로 잇기, http에서 https로 옮기기), 사이트를 다시 짠 뒤 옛 링크를 살리기,
  안전하지 않은 요청 뒤의 임시 응답, 오래 걸리는 요청의 임시 응답이다. 점검·장애 중 잠시 다른 곳으로 보낼 때는 임시 리다이렉션(302·307)을 쓴다.
  재구성·URL 변경과 임시 이동은 여기에 맞는다. 「URL 간소화」는 MDN에도 RFC 9110에도 없다.
- 근거: MDN 「Redirections in HTTP」 Temporary redirections, Use cases — https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections , RFC 9110 §15.4 — https://www.rfc-editor.org/rfc/rfc9110
- 처리: 쓰지 않는다 — 「URL 간소화」만 뺀다. 재구성·URL 변경(영구 이동)과 임시 이동은 쓴다.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다.

### I13 — 혼잡 윈도우를 「송신자가 네트워크로 보낼 수 있는 최대 양」으로 설명 (Q32) [새로 찾음]

- 답: 혼잡 윈도우를, 보내는 쪽이 네트워크에 내보낼 수 있는 데이터의 최대치를 뜻하는 변수로 설명한다.
- 표준: 혼잡 윈도우(cwnd)는 TCP가 보낼 수 있는 데이터 양을 제한하는 상태 변수다. 어느 때든 TCP는 확인된 가장 큰 순서 번호에 cwnd와 수신 윈도우(rwnd) 가운데 작은 값을 더한 번호를
  넘는 데이터를 보내면 안 된다 — 실제 한도는 둘 중 작은 쪽이다. 표준이 정한 혼잡 제어 알고리즘은 느린 시작, 혼잡 회피, 빠른 재전송, 빠른 회복 넷이다.
- 근거: RFC 5681 §2, §3, §3.1 — https://www.rfc-editor.org/rfc/rfc5681
- 처리: 한정해 쓴다 — 「혼잡 윈도우는 확인 응답을 받지 않은 채 내보낼 수 있는 양을 혼잡 쪽에서 제한하는 값이고, 실제로 내보내는 양은 혼잡 윈도우와 수신 윈도우 가운데 작은 쪽을 넘지 않는다」.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다. 강의는 min(수신 윈도우, 혼잡 윈도우) 식을 맞게 보인다(Ch4-8 p317). 관련 — L14(혼잡 제어의 이름과 조건).

### I14 — 「Etag」 표기 (Q35) [새로 찾음]

- 답: If-None-Match로 검사하는 값을 「Etag」로 적는다.
- 표준: 헤더 필드 이름은 `ETag`이고, 같은 자원의 여러 표현을 가려내는 검증자(엔터티 태그)를 담는다. 캐시는 저장한 응답의 엔터티 태그를 `If-None-Match`에 실어 검증한다.
- 근거: RFC 9110 §8.8.3, §13.1.2 — https://www.rfc-editor.org/rfc/rfc9110 , RFC 9111 §4.3.1 — https://www.rfc-editor.org/rfc/rfc9111
- 처리: 고쳐 쓴다(표기만) — `ETag`.
- 강의: 같은 문제를 다룬 강의 수정 이력은 없다. 강의는 `ETag`로 맞게 적는다(Ch5-8 p474–p475).

### I15 — `Connection: keep-alive`가 「HTTP의 지속 연결을 나타낸다」 (Q36) [새로 찾음]

- 답: 이 헤더가 지속 연결을 나타낸다고 하고, 지속 연결을 TCP 연결 하나로 여러 요청·응답을 주고받는 기능으로 설명한다.
- 표준: 지속 연결의 설명은 맞다. 다만 헤더와 지속 연결의 관계는 버전마다 다르다. HTTP/1.1은 지속 연결이 기본이라 이 헤더 없이도 연결이 이어지고, `close` 연결 옵션이 있을 때 그 응답 뒤에 닫는다.
  HTTP/1.0은 `keep-alive` 연결 옵션이 있고 받는 쪽이 받아들일 때만 연결을 이었다. 브라우저는 호환을 위해 HTTP/1.1에서도 `Connection: keep-alive`를 보내곤 한다.
  Connection은 지금 연결에만 쓰는 제어 옵션을 나열하는 필드이고, HTTP/2·HTTP/3에서는 Connection·Keep-Alive 같은 연결 전용 헤더를 쓰지 못한다.
- 근거: RFC 9112 §9.3 — https://www.rfc-editor.org/rfc/rfc9112 , RFC 9110 §7.6.1 — https://www.rfc-editor.org/rfc/rfc9110 ,
  MDN 「Connection」 — https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Connection
- 처리: 한정해 쓴다 — 「`Connection: keep-alive`는 연결을 이어 두자는 표시다. HTTP/1.0에서는 이것이 있어야 연결이 이어졌고, HTTP/1.1부터는 지속 연결이 기본이다」.
- 강의: 같은 문제 — L17(강의도 비연결성과 지속 연결을 섞고 Connection 헤더를 keep-alive로 설명한다).

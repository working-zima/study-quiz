# Azure 과목 — 덤프·용어집 수정 이력

덤프와 용어집이 **공식 문서와 다르거나 공식 문서에 없는** 곳과 그 처리를 모은다(`docs/source/azure/CLAUDE.md` 「충돌하면 공식 문서를 따른다」, ADR-060).
덤프와 용어집은 범위·강조의 근거이자 사실 **후보**일 뿐이다. 사실은 공식 문서에서만 가져오고, 공식 문서 쪽 근거와 URL은 `official.md`에 있다.

규칙:

- **덤프·용어집 문장을 옮기지 않는다**(ADR-009). 무엇을 주장하는지만 직접 쓴 말로 적는다.
- 표기는 `[덤프 NO.34]`(덤프 문항 번호)와 `[용어집 1-12]`(쪽 번호 — 1 클라우드 개념, 2 아키텍처와 서비스, 3 ID와 보안, 4 관리와 거버넌스 — 와 그 쪽의 `NO.`)다.
- 덤프의 정답은 그림으로만 표시된 것이 많다. 그런 문항은 OCR 글자나 `index.json`의 `answer`가 아니라 **답 그림을 직접 보고** 적는다(`raw/dump/img/`).
- 처리는 셋 가운데 하나다 — **고쳐 쓴다**(공식 문서대로 바꿔 쓴다), **한정해 쓴다**(조건을 붙이거나 범위를 좁혀 공식 문서가 말하는 만큼만 쓴다), **쓰지 않는다**(그 주장을 개념·문항·도식에 옮기지 않는다).
- **「자격시험은 ~로 본다」 줄을 쓰지 않는다.** 덤프는 시험을 주관하는 곳이 낸 문항이 아니라, 덤프의 답을 시험의 답으로 단정할 근거가 없다(네트워크 과목의 그 줄은 ADR-057).
- 덤프의 답이 공식 문서와 **맞는** 문항은 항목을 만들지 않는다. 확인 결과는 그 phase의 step summary에 적는다.

「(phase 100)」이 붙은 항목은 phase 100 step 4가 `azure-cloud-computing` 주제(클라우드 컴퓨팅과 비용 모델)에 걸린 덤프 문항과 용어집 항목을 공식 문서와 대조하며 더했다(확인한 날 2026-10-30).
본 덤프 문항은 `dump-topics.tsv`에서 `primary`나 `secondary`가 `cloud-computing`인 22문항이다(NO.283·370은 `cloud-models` 주제의 문항이라 phase 100 step 7이 본다).

「D11」부터와 「G9」부터는 phase 100 step 7이 `azure-cloud-models` 주제(클라우드 배포 모델)에 걸린 덤프 문항과 용어집 항목을 공식 문서와 대조하며 더했다(확인한 날 2026-10-30).
본 덤프 문항은 `dump-topics.tsv`에서 `primary`나 `secondary`가 `cloud-models`인 17문항이다. 덤프 항목은 D10 뒤에, 용어집 항목은 G8 뒤에 이어 붙였다.

「D16」부터와 「G10」부터는 phase 101 step 0이 `azure-cloud-benefits` 주제(클라우드의 이점)에 걸린 덤프 문항과 용어집 항목을 공식 문서와 대조하며 더했다(확인한 날 2026-10-30).
본 덤프 문항은 `dump-topics.tsv`에서 `primary`나 `secondary`가 `cloud-benefits`인 27문항이다(그 가운데 NO.61·336·356은 phase 100의 D3·D9가 이미 다뤘다). 덤프 항목은 D15 뒤에, 용어집 항목은 G9 뒤에 이어 붙였다.

「D22」부터와 「G15」부터는 phase 101 step 3이 `azure-sla-lifecycle` 주제(SLA와 서비스 수명 주기)에 걸린 덤프 문항과 용어집 항목을 공식 문서와 대조하며 더했다(확인한 날 2026-10-30).
본 덤프 문항은 `dump-topics.tsv`에서 `primary`가 `sla-lifecycle`인 23문항이다(같은 문항으로 분류된 NO.343·344·421·426·430은 원 문항으로 봤고, NO.493은 `azure-regions-zones` 주제의 문항이라 보지 않았다). 덤프 항목은 D21 뒤에, 용어집 항목은 G14 뒤에 이어 붙였다.

본 덤프 문항은 `dump-topics.tsv`에서 `primary`나 `secondary`가 `service-types`·`shared-responsibility`인 34문항이다(NO.188은 첫 칸을 D16이 다뤘고 둘째 칸을 D37이 다룬다). 덤프 항목은 D29 뒤에, 용어집 항목은 G16 뒤에 이어 붙였다.

「D38」부터와 「G20」부터는 phase 102 step 0이 `azure-regions-zones` 주제(지역과 가용성 영역)에 걸린 덤프 문항과 용어집 항목을 공식 문서와 대조하며 더했다(확인한 날 2026-10-31).

## D1 — 서버리스의 예 (phase 100)

- **덤프**: 서버리스 컴퓨팅의 예를 고르는 문항이 정답을 Azure Virtual Machines로 적는다. 보기에는 Azure Functions도 있다 — [덤프 NO.126]
- **공식 문서**: Learn 「Describe Azure Functions」는 Azure Functions를 이벤트에 따라 실행되는 서버리스 컴퓨팅 방식이라고 하고, VM이나 컨테이너로 만든 앱은 리소스가 계속 실행 중이어야 한다고 대비한다.
  Learn 「Describe Azure virtual machines」는 VM을 IaaS로 두고, VM 안의 패치·업데이트·구성은 쓰는 쪽이 계속 관리한다고 한다. Azure Functions 문서도 Functions를 서버리스 솔루션이라고 한다.
- **처리**: 고쳐 쓴다. 서버리스의 예는 Azure Functions이고, VM은 쓰는 쪽이 운영 체제를 관리하며 실행되는 동안 요금이 붙는 방식이라 서버리스의 예가 아니다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.serverless`

## D2 — 클라우드 공급자에게 내는 돈의 분류 (phase 100)

- **덤프**: 「클라우드 공급자에게 내는 돈은 자본 지출이다」를 맞다고, 「소비 기반 모델로 받는 서비스는 운영 지출이다」를 틀리다고 표시한다 — [덤프 NO.124]
  (같은 세 진술을 묻는 [덤프 NO.338]은 반대로 — 앞의 것을 틀리다고, 뒤의 것을 맞다고 — 표시한다)
- **공식 문서**: Learn 「Describe the consumption-based model」은 클라우드 서비스를 쓰는 대로 내므로 클라우드 컴퓨팅이 운영 지출로 분류된다고 한다.
  Cloud Adoption Framework 「Cost efficiency」는 Azure 같은 서비스에 주기적으로 내는 돈을 운영 지출의 예로 든다.
- **처리**: 고쳐 쓴다. 클라우드 공급자에게 쓰는 만큼 내는 돈은 운영 지출이고, 사용량 기반 모델로 받는 서비스의 비용도 운영 지출이다. NO.124의 표시는 따르지 않는다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.capex-opex`

## D3 — 퍼블릭 클라우드로 자본 지출을 줄일 수 있나 (phase 100)

- **덤프**: 「퍼블릭 클라우드를 쓰면 자본 지출을 최소로 줄일 수 있다」를 틀리다고 표시한다 — [덤프 NO.61] 둘째 진술
  (같은 덤프의 [덤프 NO.336]·[덤프 NO.356]은 「클라우드 컴퓨팅은 온-프레미스보다 자본 지출이 적다」를 맞다고 표시한다)
- **공식 문서**: Learn 「Describe the consumption-based model」은 사용량 기반 모델의 이점으로 하드웨어·데이터 센터 인프라에 미리 내는 돈이 없다는 것을 든다.
  Learn 「Define cloud models」의 비교표는 퍼블릭 클라우드에서 규모를 키우는 데 자본 지출이 들지 않는다고 적는다.
- **처리**: 고쳐 쓴다. 클라우드(퍼블릭 클라우드 포함)를 쓰면 하드웨어·데이터 센터에 미리 쓰는 돈, 곧 자본 지출이 줄어든다. NO.61 둘째 진술의 표시는 따르지 않는다.
  퍼블릭 클라우드의 내용은 `azure-cloud-models` 주제가 쓴다 — 이 주제에서는 자본 지출 쪽 사실만 쓴다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.capex-opex`

## D4 — 전기료·직원 월급·소프트웨어 임대의 분류 (phase 100)

- **덤프**: 기술 인력의 월급과 소프트웨어 임대를 운영 지출로 본다 — [덤프 NO.6]. 「자기 데이터 센터의 전기료는 운영 지출이다」를 틀리다고 표시한다 — [덤프 NO.350].
  [덤프 NO.400]의 해설은 자기 데이터 센터의 전기료를 자본 지출이라고 한다(그 해설은 NO.400의 진술과 맞지 않는다 — D5).
- **공식 문서**: Learn 「Describe the consumption-based model」은 자본 지출을 서버·네트워크 하드웨어·데이터 센터 공간 같은 물리 인프라에 미리 쓰는 돈으로, 운영 지출을 서비스에 시간에 걸쳐 계속 쓰는 돈으로 정의할 뿐
  전기료·월급·소프트웨어 임대를 어느 쪽에도 넣지 않는다. Cloud Adoption Framework 「Cost efficiency」도 하드웨어·장비 대 서비스에 주기적으로 내는 돈만 든다.
  Azure 클라우드 컴퓨팅 사전 「What is cloud computing?」은 서버 랙·상시 전기·인프라를 관리하는 IT 전문가를 한데 묶어 클라우드가 없애 주는 「capital expense」라고 부른다 — 덤프와 반대 방향이고, 분류의 정의가 아니라 소개 글이다.
- **처리**: 쓰지 않는다. 전기료·월급·소프트웨어 임대를 자본 지출이나 운영 지출의 예로 개념·문항·도식에 쓰지 않는다. 공식 문서가 직접 드는 예(서버·네트워크 하드웨어·데이터 센터 공간, Azure 같은 서비스에 주기적으로 내는 돈)만 쓴다.
  「데이터 센터를 짓는 데 드는 돈은 자본 지출이다」([덤프 NO.6] 첫 진술, [덤프 NO.350]·[덤프 NO.400] 셋째 진술)는 위 정의와 맞으므로 써도 된다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.capex-opex`, G6

## D5 — 예약 VM 인스턴스는 운영 지출인가 (phase 100)

- **덤프**: 「Azure 예약 VM 인스턴스는 운영 지출의 예다」를 틀리다고 표시한다 — [덤프 NO.400] 둘째 진술. 그 진술의 해설(Box 2)은 예약이 아니라 데이터 센터 전기료 이야기라, [덤프 NO.350]의 해설을 옮겨 온 것으로 보인다.
- **공식 문서**: 「What are Azure Reservations?」는 예약을 1년이나 3년 약정으로 받는 청구 할인이라고 하고, 미리 한꺼번에 내거나 달마다 낼 수 있으며 총액이 같다고 한다.
  자본 지출·운영 지출 가운데 어느 쪽인지는 어느 공식 문서도 말하지 않는다.
- **처리**: 쓰지 않는다. 예약을 자본 지출이나 운영 지출로 분류하지 않는다. 예약은 약정·할인·결제 방식으로만 설명한다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.reservations`, `azure-cloud-computing.capex-opex`

## D6 — Azure는 자본 지출과 운영 지출 사이의 유연성을 주는가 (phase 100)

- **덤프**: 「Azure는 자본 지출과 운영 지출 사이에서 유연성을 준다」를 맞다고 표시한다 — [덤프 NO.92] 첫 진술
- **공식 문서**: 그런 말을 하는 문서를 찾지 못했다. Learn은 클라우드가 IT 지출을 자본 지출에서 운영 지출로 옮긴다고만 한다(「Describe cloud computing」 요약 단원, 단원 6).
- **처리**: 쓰지 않는다. (NO.92의 둘째·셋째 진술 — 같은 크기의 VM 둘이 늘 같은 달 비용을 내지는 않는다, 멈춘 VM에도 스토리지 요금이 붙는다 — 은 공식 문서와 맞고, 비용 관리 주제가 볼 문항이다.)
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.capex-opex`

## D7 — 클라우드를 쓰려면 인터넷 연결이 꼭 있어야 하나 (phase 100)

- **덤프**: 「클라우드 컴퓨팅을 쓰려면 인터넷 연결이 있어야 한다」를 맞다고 표시한다 — [덤프 NO.410] 둘째 진술
- **공식 문서**: Learn 「What is cloud computing」은 클라우드 컴퓨팅을 컴퓨팅 서비스를 인터넷으로 내주는 것이라고 정의한다. 「반드시 있어야 한다」고는 말하지 않는다.
  「What is Azure ExpressRoute?」는 회사 네트워크를 공용 인터넷을 지나지 않는 사설 연결로 Microsoft 클라우드에 잇는 방법을 설명한다.
- **처리**: 한정해 쓴다. 정의대로 「클라우드 컴퓨팅은 컴퓨팅 서비스를 인터넷으로 내준다」를 쓰고, 「인터넷 연결이 없으면 클라우드를 쓸 수 없다」 같은 단정은 쓰지 않는다. ExpressRoute는 이 주제에서 쓰지 않는다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.cloud-computing`

## D8 — 클라우드 용량을 늘리는 비용이 더 적은가 (phase 100)

- **덤프**: 「클라우드의 용량을 늘리는 비용이 온-프레미스 데이터 센터의 용량을 늘리는 비용보다 적다」를 맞다고 표시한다 — [덤프 NO.410] 셋째 진술
- **공식 문서**: 두 비용을 견주는 문장은 찾지 못했다. 공식 문서가 말하는 것은 차이의 내용이다 — 데이터 센터를 새로 지을 때까지 기다리지 않고 클라우드로 늘린다(Learn 단원 3),
  기존 데이터 센터에서 모자란 용량을 채우려면 하드웨어·전원·냉각을 주문하고 설치해야 하지만 클라우드에서는 가상 머신을 더한다(Learn 단원 6).
- **처리**: 한정해 쓴다. 「더 싸다」는 비교를 쓰지 않고, 늘리는 방법과 기다림이 어떻게 다른지만 쓴다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.cloud-computing`, `azure-cloud-computing.consumption-based-model`

## D9 — 클라우드의 구성 옵션은 온-프레미스와 같은가 (phase 100)

- **덤프**: 「클라우드 컴퓨팅은 온-프레미스와 같은 구성 옵션을 준다」를 틀리다고 표시한다 — [덤프 NO.336]·[덤프 NO.356] 둘째 진술
- **공식 문서**: 클라우드와 온-프레미스의 구성 옵션을 견주는 문장은 찾지 못했다.
- **처리**: 쓰지 않는다.
- **쓰인 곳**: 없음(이 주제의 어느 개념도 이 주장을 쓰지 않는다)

## D10 — 웹사이트를 옮기면 「달마다」 사용료를 내나 (phase 100)

## D11 — 어느 모델에 인프라를 두면 자기 데이터 센터가 필요 없나 (phase 100)

- **덤프**: 「인프라를 ___에 둔 조직은 더는 데이터 센터가 필요 없다(데이터 센터를 닫을 수 있다)」의 빈칸을 두고 덤프끼리 답이 갈린다.
  - [덤프 NO.30](밑줄 친 말 고치기): 「프라이빗 클라우드」를 틀렸다고 보고 「퍼블릭 클라우드」로 고치게 한다. 해설은 프라이빗 클라우드가 자기 데이터 센터에 있으므로 데이터 센터를 닫을 수 없다고 한다.
  - [덤프 NO.238](빈칸 고르기, 답 그림 p141): 「퍼블릭 클라우드」를 고른다.
  - [덤프 NO.272](빈칸 고르기, 답·해설 그림 p160): 문장이 「자기 인프라를」로 조금 다르고, 「프라이빗 클라우드」를 고른다.
- **공식 문서**:
  - 퍼블릭 — Learn 「Define cloud models」은 제3자 공급자가 짓고 통제하고 유지 관리하며 규모를 키우는 데 자본 지출이 없다고 한다. 클라우드 컴퓨팅 사전 「What is a public cloud?」는 리소스가 공급자의 데이터 센터에 있고 온-프레미스 하드웨어 없이 쓴다고 한다.
    Learn 「Describe the shared responsibility model」은 물리 데이터 센터·네트워크·호스트를 늘 공급자 몫으로 든다.
  - 프라이빗 — Learn 「Define cloud models」은 사업장 안의 데이터 센터에도, 사업장 밖의 전용 데이터 센터에도 둘 수 있고 제3자가 운영할 수도 있다고 한다. 같은 단원의 비교표는 하드웨어를 사야 하고 유지 관리·업데이트를 조직이 맡는다고 적는다.
    사전 「What is a private cloud?」도 사업장 안이나 제3자 공급자가 호스트한다고 한다.
  - 「데이터 센터가 필요 없다」·「데이터 센터를 닫을 수 있다」를 모델과 짝지어 말하는 문장은 어느 공식 문서에도 없다.
- **처리**: NO.272는 고쳐 쓰고, NO.30·238은 한정해 쓴다.
  - 프라이빗 클라우드에는 그 조직만 쓰는 하드웨어와 그것을 둔 데이터 센터가 사업장 안이든 밖이든 있다. 그러니 「프라이빗 클라우드로 옮기면 데이터 센터가 필요 없다」(NO.272의 답)는 쓰지 않는다.
  - 프라이빗은 사업장 밖 제3자의 데이터 센터에도 둘 수 있으므로, 「프라이빗이면 자기 데이터 센터를 닫을 수 없다」(NO.30의 해설)도 단정하지 않는다.
  - 본문은 「하드웨어와 그것을 둔 데이터 센터를 누가 갖추고 관리하나」로 쓴다. 퍼블릭은 공급자가 짓고 관리하므로 조직이 그 인프라를 위한 자기 하드웨어를 사서 둘 필요가 없고, 프라이빗은 조직 전용 하드웨어를 조직이 사서 유지 관리한다.
    NO.30·238의 답(퍼블릭)은 이 방향과 맞지만, 「데이터 센터를 없앤다」는 결과 문장으로는 쓰지 않는다.
  - 문항은 「자기 데이터 센터가 필요 없다」나 「제3자가 운영한다」를 퍼블릭과 프라이빗을 가르는 단서로 쓰지 않는다 — 사업장 밖 제3자에게 맡긴 프라이빗과 퍼블릭이 둘 다 맞게 읽힌다. 가르는 단서는 「한 조직 전용인가, 사려는 누구나 쓰는가」다.

## D14 — 하이브리드가 자본 지출과 운영 지출을 가장 줄이는가 (phase 100)

## D15 — 퍼블릭 클라우드의 「셀프서비스 관리」 (phase 100)

- **덤프**: 퍼블릭 클라우드의 특징 둘로 사용량에 따른 요금(metered pricing)과 셀프서비스 관리를 고른다. 해설은 셀프서비스 관리를, 쓰는 쪽이 VM·웹 사이트 같은 리소스를 직접 배포하고 구성하며 밑바탕 하드웨어는 공급자가 관리하는 것이라고 푼다 — [덤프 NO.195]
- **공식 문서**: 쓴 만큼 낸다는 것은 Learn 「Define cloud models」 비교표(퍼블릭)와 사전 「What is a public cloud?」에 있다. 「셀프서비스 관리」라는 말은 받은 공식 문서에 없다.
  가장 가까운 것은 사전 「What is a public cloud?」의 필요할 때 쓰는 접근(웹 화면·API·명령줄 도구로 서비스에 접근하고 리소스를 빨리 늘리고 줄인다)과, Learn 「Define cloud models」의 앱을 빨리 갖추고 없앨 수 있다는 칸이다.
  밑바탕 하드웨어가 공급자 몫이라는 것은 Learn 「Describe the shared responsibility model」(물리 호스트는 늘 공급자 몫)에 있다.
- **처리**: 한정해 쓴다. 「쓴 만큼 낸다」는 쓴다. 「셀프서비스 관리」라는 이름은 쓰지 않고, 같은 내용이 필요하면 「쓰는 쪽이 웹 화면이나 명령으로 필요할 때 리소스를 만들고 늘리고 줄이며, 밑바탕 하드웨어는 공급자가 관리한다」로 쓴다.

## D16 — Azure Site Recovery가 가상 머신에 주는 것 (phase 101)

- **덤프**: Site Recovery가 VM에 주는 것을 고르는 세 문항이 모두 「내결함성(fault tolerance)」을 답으로 표시한다 — [덤프 NO.103](밑줄 친 「내결함성」을 「바꿀 필요 없음」으로 답한다), [덤프 NO.188] 첫 칸, [덤프 NO.405](세 문항 모두 답 그림으로 확인).

- **공식 문서**: 「Reliability in Azure」는 Azure Site Recovery가 VM 워크로드의 **재해 복구**를 조율한다(복제와 장애 조치 순서를 자동화한다)고 한다.

- **쓰인 곳**: `azure-cloud-benefits.reliability`

## D17 — 수직·수평 크기 조정의 예 (phase 101)

- **덤프**: 세 진술 — VM에 RAM을 더하는 것은 수평 크기 조정이다, 수요에 따라 VM을 하나 더 두는 것은 수직 크기 조정이다, 수평 크기 조정은 자동이나 수동으로 할 수 있다 — 에 모두 「예」를 표시한다 — [덤프 NO.371](답 그림)
- **공식 문서**: Learn 「Describe the benefits of high availability and scalability in the cloud」는 VM에 CPU·RAM을 더하는 것을 수직(스케일 업), VM·컨테이너를 더하는 것을 수평(스케일 아웃)으로 들고, 수평은 자동이나 수동으로 한다고 한다. 「Overview of autoscale in Azure Monitor」도 같다.
  같은 덤프의 [덤프 NO.147]·[덤프 NO.355]는 CPU·메모리를 더하는 것을 수직으로 맞게 답한다.
- **처리**: 고쳐 쓴다. 앞의 두 진술은 틀리다 — RAM을 더하는 것은 수직, VM을 더 두는 것은 수평이다. 셋째 진술은 맞다.
- **쓰인 곳**: `azure-cloud-benefits.scalability`, `CloudScalingDiagram`

## D18 — 클라우드 서비스 비용을 셈할 수 있게 하는 이점 (phase 101)

- **덤프**: 클라우드 서비스가 얼마 들지 계산할 수 있게 하는 이점으로 답 그림이 「민첩성」을 표시한다. 보기는 민첩성·탄력성·고가용성·예측 가능성이다 — [덤프 NO.179](p110의 답 그림)
- **공식 문서**: Learn 「Describe the benefits of reliability and predictability in the cloud」는 비용 예측 가능성을 클라우드에 쓸 돈을 내다보는 것이라 하고, 리소스 사용의 실시간 추적·모니터링·분석과 Azure 가격 계산기로 앞으로 쓸 돈을 어림한다고 한다.
- **처리**: 고쳐 쓴다. 비용을 셈하고 내다보게 하는 이점은 예측 가능성(비용 예측 가능성)이다. 민첩성은 비용 계산과 관계없다(D19).

## D19 — 민첩성과 탄력성 (phase 101)

- **덤프**: 짝짓기 [덤프 NO.145]의 답 그림은 「클라우드 앱이 쓸 리소스를 동적으로 늘리고 줄이는 능력」에 민첩성을, 「앱의 요구가 바뀔 때 클라우드 리소스를 빨리 배포하고 구성하는 능력」에 탄력성을 짝짓는다.
  같은 덤프의 [덤프 NO.160](보기에 탄력성이 없다) 답 그림은 수요에 맞춰 리소스를 동적으로 마련하는 쪽을 확장성에, 앱을 빨리 개발·테스트·출시하는 쪽을 민첩성에 짝짓고, [덤프 NO.434]는 바뀌는 요구에 빨리 맞추는 것을 민첩성이라 답한다.
  [덤프 NO.115]·[덤프 NO.140]·[덤프 NO.227]은 자동 크기 조정, 월말에 몰리는 사용량 대응, 리소스 할당과 해제를 탄력성으로 답한다. 리소스를 수요에 맞춰 늘리고 줄이는 것을 덤프가 민첩성·확장성·탄력성으로 서로 다르게 답한다.
- **공식 문서**: 사전 「What is elasticity in cloud computing?」은 탄력성을 실시간 수요에 따라 리소스를 자동으로 조정하는 능력이라 정의한다. 민첩성은 Learn 「Describe the benefits of using cloud services」 단원(2~5)에 없다.
  같은 사전이 탄력성이 주는 사업상 이점 셋(비용·성능·민첩성) 가운데 하나로 「긴 조달 과정 없이 새 서비스를 빨리 내놓고 시장·고객의 요구를 따라잡는다」고 말할 뿐, 민첩성을 따로 정의하지 않는다.
  사전 「What is cloud computing?」의 「Speed」(주문형이라 몇 분 만에 리소스를 마련한다)는 이름이 다르다.
- **처리**: 한정해 쓴다. 수요에 따라 리소스를 자동으로 늘리고 줄이는 것은 탄력성이다 — NO.145의 짝은 따르지 않는다. 민첩성은 이 주제의 이점 이름으로 따로 세우지 않고 정의도 쓰지 않는다.
  쓴다면 탄력성 개념 안에서 「탄력성 덕분에 장비 조달을 오래 기다리지 않고 새 서비스를 빨리 내놓을 수 있다」처럼 사전이 말하는 만큼만 한 줄로 쓴다. 민첩성을 문항의 정답으로 삼지 않는다.
- **쓰인 곳**: `azure-cloud-benefits.elasticity`

## D22 — 서비스마다의 SLA 수치와 Azure AD라는 옛 이름 (phase 101)

## D23 — SLA를 높이는 법: 여러 지역에 두기, 구독 늘리기 (phase 101)

- **덤프**: [덤프 NO.58]·[덤프 NO.237]은 「여러 지역에 Azure 리소스를 더하면 SLA가 보장하는 가동 시간을 높일 수 있다」에 예를, 「구독을 여러 개 사면 높일 수 있다」에 아니요를 표시한다(답 그림). NO.58 해설은 여러 지역에 두면 보통 99.95%로 오른다고 적는다.
- **공식 문서**: Well-Architected 「Implement multiregion targets」는 여러 지역 배포가 중복성 원칙의 구현이고 장애 조치용 두 번째 지역이 생겨 목표를 높일 수 있다고 하며, Azure Cosmos DB는 여러 지역에 배포하면 Microsoft가 더 높은 SLA를 약속한다고 든다.
  Cloud Adoption Framework 「Protect your cloud estate」는 복합 SLA 어림이 목표에 못 미치면 더 높은 등급의 SLA를 고르거나 중복(여러 가용성 영역·여러 지역)을 더하라고 하고, 여러 지역 배포를 「1 − (1 − 한 지역의 값)^지역 수」로 어림한다.
  「How to read a service-level agreement (SLA)」는 같은 서비스라도 인스턴스 하나만 둔 배포가 중복을 둔 배포보다 SLA가 낮을 수 있다고 한다. 「보통 99.95%로」라는 수치와 구독 수가 SLA와 어떤 관계인지는 받은 문서에 없다.
- **처리**: 한정해 쓴다. 중복(여러 지역, 여러 인스턴스)을 두면 앱 전체의 어림 가용성이 올라가고, 일부 서비스는 중복을 둔 배포에 더 높은 SLA를 약속한다(배포 방식에 따라 SLA가 다르다)고 쓴다.
  「여러 지역에 두면 SLA가 99.95%가 된다」 같은 수치와 「모든 서비스의 SLA가 오른다」는 쓰지 않는다. 구독 수에 관한 진술도 쓰지 않는다.
- **쓰인 곳**: `azure-sla-lifecycle.sla`, `azure-sla-lifecycle.composite-sla`

## D24 — 서비스 크레딧은 저절로 들어오나 — 덤프끼리 갈림 (phase 101)

- **덤프**: [덤프 NO.71]은 리소스가 장애로 오래 멈췄을 때 Microsoft가 「자동으로 계정에 크레딧을 준다」(보기 C)를 답으로 하고, 밑줄 친 「은행 계좌로 환불한다」를 고칠 말로 둔다. [덤프 NO.397]은 같은 상황에서 「Azure 계정에 크레딧을 준다」를 답으로 한다(답 그림).
  반면 [덤프 NO.175]는 「유료 고객은 월간 가동률이 보장값에 못 미치면 크레딧을 받는다」에 아니요를, [덤프 NO.196]은 「유료 고객은 크레딧을 청구할 수 있다」에 예를 표시한다(둘 다 답 그림) — 크레딧이 저절로 오는지를 덤프가 서로 다르게 답한다.
- **공식 문서**: Well-Architected 「Azure facilitation」은 Azure SLA에 SLA에 못 미쳤을 때 서비스 크레딧을 받는 절차가 들어 있다고 한다.
  「How to read a service-level agreement (SLA)」는 서비스 크레딧이 중단에 대한 보상이지만 공급자가 보통 알아서 주지 않으므로, 고객이 SLA를 어긴 중단을 찾아 기록하고 기한 안에 청구해야 한다고 하고, 크레딧은 대개 영향을 받은 서비스의 한 달 요금에 대한 백분율이라고 한다.
  이 문서는 Microsoft SLA에만 해당하는 글이 아니라고 스스로 밝힌다. 「은행 계좌로 환불」이라는 말은 받은 문서에 없다.
- **처리**: 고쳐 쓴다. 「자동으로」는 따르지 않는다 — NO.175·196 쪽을 따른다. 서비스 크레딧은 SLA에 못 미쳤을 때의 보상이고, 보통 서비스 요금(한 달 요금)에 대한 백분율로 정해지며, 받으려면 고객이 청구해야 한다고 쓴다.
  「청구해야 한다」는 SLA 일반에 대한 문서의 말이므로 「보통」을 붙이거나 「Azure SLA에는 크레딧을 받는 절차가 들어 있다」와 함께 쓴다. 「은행 계좌 환불」·크레딧 비율(10% 등)·청구 기한(30~60일)은 쓰지 않는다.
- **쓰인 곳**: `azure-sla-lifecycle.service-credit`

## D25 — 월간 가동률 계산식 (phase 101)

- **덤프**: [덤프 NO.447]은 월간 가동률을 「(최대 가용 분 − 중단 분) ÷ 최대 가용 분 × 100」으로 셈한다고 답하고(답 그림·해설), 근거로 옛 Cloud Services SLA 쪽 주소를 든다.
- **공식 문서**: 「How to read a service-level agreement (SLA)」는 가상의 서비스를 든 예에서 「(청구 대상 분 − 중단 분) ÷ 청구 대상 분 × 100」을 들고, 이 짜임이 실제 SLA 여럿을 닮았다고 한다. 같은 문서는 SLA가 보통 청구 기간 단위로 가동 시간을 잰다고 한다.
  「최대 가용 분」이라는 이름과 Azure 서비스마다의 실제 정의는 SLA 약관에 있어 이 과목은 확인할 수 없다.
- **처리**: 한정해 쓴다. 「한 달(청구 기간) 동안 셀 수 있는 시간에서 멈춘 시간을 빼고, 그 값을 셀 수 있는 시간으로 나눈 백분율」 꼴은 SLA 일반의 예로 쓸 수 있다. Azure SLA의 식이라고 단정하거나 「최대 가용 분」이라는 이름을 쓰지 않는다.
- **쓰인 곳**: `azure-sla-lifecycle.sla`

## D27 — 공개 미리 보기를 운영 환경에 쓸 수 있나 (phase 101)

- **덤프**: [덤프 NO.4]·[덤프 NO.210]은 「공개 미리 보기의 Azure 서비스는 운영 환경에 쓸 수 있다」에 예를 표시한다(답 그림). 같은 문항의 첫째 진술 「비공개 미리 보기 서비스는 모두 별도의 Azure 포털로 접근해야 한다」에는 아니요를 표시한다.
- **공식 문서**: 「Infrastructure Lifecycle FAQ - Microsoft Azure」는 공개 미리 보기 기능이 따로 밝히지 않는 한 운영(프로덕션) 워크로드용이 아니고, 비공개 미리 보기 기능은 운영 워크로드용이 아니라고 한다. Azure AI Search 문서의 미리 보기 안내는 미리 보기 기능을 운영 워크로드에 권하지 않는다고 한다.
  미리 보기 약관은 조기 액세스 미리 보기(비공개 미리 보기를 포함한다)를 운영 환경에 쓸 수 없다고 정한다. 「Set up preview features in Azure subscription」은 미리 보기 기능을 Azure 포털·Azure CLI·Azure PowerShell로 구독에 등록한다고 할 뿐, 별도 포털은 말하지 않는다.
- **처리**: 고쳐 쓴다. 공개 미리 보기는 따로 밝히지 않는 한 운영 환경에 쓰라고 내놓은 것이 아니다(운영 작업에 권하지 않는다)고 쓴다. 쓰는 것을 막는 문장은 비공개 미리 보기(조기 액세스 미리 보기) 약관에만 있으므로, 공개 미리 보기를 「운영 환경에 쓸 수 없다」고 단정하지도 않는다.
  「별도 포털」 진술은 쓰지 않는다.
- **쓰인 곳**: `azure-sla-lifecycle.preview`

## D28 — 비공개·공개 미리 보기와 GA는 누구에게 열리나 — 덤프끼리 갈림 (phase 101)

- **덤프**: [덤프 NO.57]은 「비공개 미리 보기의 Azure 서비스는 모든 Azure 고객에게 공개된다」에 예를, 「공개 미리 보기는 모든 Azure 고객에게」에 예를, 「GA는 일부 고객에게만」에 아니요를 표시한다(답 그림·해설 그림 둘 다).
  [덤프 NO.132](NO.344·421이 같은 문항으로 분류되어 있다)는 같은 세 진술에 아니요·예·아니요를 표시한다(답 그림).
  [덤프 NO.172]는 「공개 미리 보기일 때 모든 Azure 고객이 쓸 수 있다」를 바꿀 필요 없음으로 답하고, 해설은 뉴스 사이트를 인용하며 공개 미리 보기가 흔히 할인된 값에 나온다고 적는다.
- **공식 문서**: 「Infrastructure Lifecycle FAQ - Microsoft Azure」는 비공개 미리 보기를 초대받은 일부 고객만 들어오는 단계로, 공개 미리 보기를 Azure 구독이 있는 모든 Azure 고객이 평가할 수 있는 단계로(지역·구독 유형·용량으로 범위가 좁을 수 있다), GA를 모든 Azure 고객이 운영에 쓰도록 정식으로 내놓은 단계로 정의한다.
  미리 보기 약관은 조기 액세스 미리 보기(비공개 미리 보기를 포함한다)를 제3자에게 줄 수 없고 기밀이라고 한다. 미리 보기의 값(할인)은 받은 문서에 없다.
- **처리**: 고쳐 쓴다. NO.132를 따른다 — 비공개 미리 보기는 모든 고객에게 열리지 않는다. 공개 미리 보기의 「할인된 값」은 쓰지 않는다. 공개 미리 보기를 「누구나」로 쓸 때는 「Azure 구독이 있는 모든 고객」으로 쓰고, 지역 등에 따라 범위가 좁을 수 있다는 것을 함께 둔다.
- **쓰인 곳**: `azure-sla-lifecycle.preview`, `azure-sla-lifecycle.general-availability`, `ServiceLifecycleDiagram`

## D29 — 출시 단계의 차례, 미리 보기의 값·관리 도구, GA 뒤의 변화 (phase 101)

- **덤프**: [덤프 NO.358](NO.430이 같은 문항으로 분류되어 있다)은 「대부분의 Azure 서비스는 비공개 미리 보기 → 공개 미리 보기 → GA 차례로 나온다」에 예를, 「공개 미리 보기 서비스는 Azure CLI로만 관리할 수 있다」에 아니요를, 「비공개 미리 보기 서비스의 값은 GA가 되면 내려간다」에 아니요를 표시한다(답 그림).
  [덤프 NO.150]은 「Azure 포털에서 GA 서비스와 공개 미리 보기 서비스를 구분할 수 있다」에 예를, 「GA가 된 뒤에는 새 기능 업데이트가 없다」에 아니요를, 「공개 미리 보기로 만든 리소스는 GA가 되면 다시 만들어야 한다」에 아니요를 표시한다(답 그림).
- **공식 문서**: 「Infrastructure Lifecycle FAQ - Microsoft Azure」는 단계를 비공개 미리 보기 → 공개 미리 보기 → GA → 사용 중단 → 사용 중지 차례로 들고, 비공개는 더 넓게 내놓기 전, 공개는 GA 전이라고 한다. 다만 대상을 Azure 인프라 제품과 기능이라 밝히고, 대부분(또는 모든) 서비스가 세 단계를 다 거친다고는 하지 않는다.
  「Modern Lifecycle Policy」는 이 정책의 제품이 계속 서비스되고 바뀌는 일이 잦을 수 있다고 한다(GA 뒤에도 바뀐다). 「Set up preview features in Azure subscription」은 미리 보기 기능을 Azure 포털·Azure CLI·Azure PowerShell로 나열·등록한다고 한다.
  미리 보기·GA의 값, 포털이 GA와 미리 보기를 구분해 보여 주는지, GA 뒤에 리소스를 다시 만드는지는 받은 문서에 없다(미리 보기 약관은 컨테이너로 쓰는 AI 서비스의 미리 보기를 GA 버전으로 바꿔야 한다는 한 서비스의 예만 든다).
- **처리**: 한정해 쓴다. 단계의 차례(비공개 미리 보기 → 공개 미리 보기 → GA)는 인프라 수명 주기 FAQ대로 쓰되, 「모든(대부분의) 서비스가 세 단계를 다 거친다」고는 쓰지 않는다. GA 뒤에도 서비스가 바뀐다는 것은 최신 수명 주기 정책대로 쓸 수 있다.
  값의 변화, 포털에서의 구분, GA 뒤 리소스 다시 만들기는 쓰지 않는다. 「CLI로만」은 미리 보기 기능 문서와 어긋나 쓰지 않는다.
- **쓰인 곳**: `azure-sla-lifecycle.preview`, `azure-sla-lifecycle.general-availability`, `ServiceLifecycleDiagram`

## D30 — SaaS에서 고객과 Microsoft가 함께 맡는 책임 (phase 101)

- **덤프**: [덤프 NO.15]는 SaaS에서 Microsoft와 고객이 함께 맡는 책임으로 「정보와 데이터 관리」를 답으로 표시한다(보기에는 ID와 디렉터리 인프라 관리, 애플리케이션 관리, 운영 체제 업데이트도 있다).
- **공식 문서**: 「Shared responsibility in the cloud」의 책임 표에서 고객 데이터는 온-프레미스·IaaS·PaaS·SaaS 모두 고객 몫이고, SaaS에서 함께 맡는 것은 클라이언트 장치와 애플리케이션이다.

- **처리**: 고쳐 쓴다. 정보와 데이터는 어느 유형에서나 고객이 맡는다. SaaS에서 함께 맡는 것은 공식 문서대로(애플리케이션·클라이언트 장치·ID와 액세스) 쓴다. 덤프 보기 가운데 공식 문서와 맞는 쪽은 「ID와 디렉터리 인프라 관리」다.
- **쓰인 곳**: `azure-service-types.shared-responsibility-model`, `SharedResponsibilityDiagram`

## D31 — 관리 부담을 가장 줄이는 웹앱 이전 (phase 101)

- **덤프**: [덤프 NO.135]는 외부 사용자가 쓰는 웹앱을 Azure로 옮기면서 그 웹앱을 관리하는 수고를 가장 줄이려면 무엇을 권할지 묻고 「IaaS」를 답으로 표시한다.
- **공식 문서**: Learn 「Describe cloud service types」 단원 2는 IaaS를 고객의 운영 책임이 가장 큰 유형(운영 체제·패치·구성·많은 보안 통제를 고객이 관리)이라 한다. 단원 3은 PaaS에서 공급자가 운영 체제·미들웨어·런타임을 관리하고 고객은 앱 코드·데이터·액세스 제어에 집중한다고 하고,

## D33 — 코드를 고칠 앱과 운영 체제를 직접 다룰 앱의 유형 (phase 101)

## D34 — PaaS만 쓰는 이전 계획에 맞는 구성 — 덤프끼리 갈림 (phase 101)

- **덤프**: 「PaaS만 쓴다」는 같은 계획을 두고 구성마다 답을 묻는 문항들이다.
  - [덤프 NO.463]·[덤프 NO.189] 보기 A: App Service와 Azure SQL Database → 맞는다
  - [덤프 NO.166]·[덤프 NO.189] 보기 D: App Service와 SQL Server를 설치한 VM → 맞지 않는다
  - [덤프 NO.189] 보기 C: VM과 Azure SQL Database와 스토리지 계정 → 정답이 아니다. 그런데 [덤프 NO.290]은 **같은 구성**에 「맞는다」를 답으로 표시한다
  - [덤프 NO.191]: App Service와 스토리지 계정 → 맞지 않는다
- **공식 문서**: 「Shared responsibility in the cloud」는 VM을 IaaS의 예로, App Service·Azure Functions·Azure SQL Database·**Azure Storage**를 PaaS의 예로 든다. Learn 「Describe cloud computing」 단원 4는 VM에 SQL 데이터베이스를 직접 설치하면 그 패치·업데이트까지 고객이 맡는다고 한다.

  NO.191의 스토리지 계정은 공식 문서가 Azure Storage를 PaaS의 예로 들므로 덤프의 답(맞지 않는다)과 어긋난다 — 문항에서 Azure Storage의 유형은 묻지 않는다(근거가 문서 한 줄의 예뿐이다).
- **쓰인 곳**: `azure-service-types.paas`

## D35 — PaaS 웹앱의 운영 체제 통제·메모리·자동 확장·개발 서비스 — 덤프끼리 갈림 (phase 101)

- **덤프**: Azure에서 웹앱을 호스트하는 PaaS를 두고 진술마다 예/아니요를 묻는 네 문항이다(모두 답 그림으로 확인).
  - 앱을 호스트하는 운영 체제를 완전히 통제한다 → 넷 모두 아니요([덤프 NO.155]·[덤프 NO.201]·[덤프 NO.301]·[덤프 NO.348])
  - 자동으로 확장한다(인스턴스 수를 자동으로 늘린다) → 넷 모두 예
  - 가격 계층을 바꿔 메모리를 더 줄 수 있다 → [덤프 NO.201]은 **예**, [덤프 NO.301]·[덤프 NO.348]은 **아니요**
  - 전문 개발 서비스가 사용자 지정 앱에 기능을 계속 더해 준다 → [덤프 NO.155]는 예
- **공식 문서**: Learn 단원 3은 PaaS에서 공급자가 운영 체제를 유지 관리한다고 하고, PaaS 사전은 수요에 따라 리소스를 자동으로 늘리고 줄인다고 한다. App Service 개요도 수요에 따라 자동으로 확장한다고 한다.
  「Scale up an app in Azure App Service」는 앱이 속한 App Service 플랜의 **가격 책정 계층을 바꿔 CPU·메모리·디스크 공간을 더 얻는 것**을 스케일 업이라 한다.
  PaaS가 「전문 개발 서비스」로 앱에 기능을 더해 준다는 말은 받은 문서 어디에도 없다 — 공식 문서가 PaaS에 들어 있다고 하는 것은 개발 도구·미들웨어·런타임 같은 플랫폼 구성 요소다.
- **처리**: 운영 체제 통제(아니요)와 자동 확장(예)은 덤프가 맞다. 가격 계층과 메모리는 고쳐 쓴다 — NO.201이 맞고 NO.301·348이 틀렸다. 다만 근거가 App Service 한 서비스의 문서라, 쓸 때는 「PaaS 일반」이 아니라 App Service의 예로 한정한다.
  「전문 개발 서비스」는 쓰지 않는다.
- **쓰인 곳**: `azure-service-types.paas`

## D36 — Azure Cosmos DB의 서비스 유형 (phase 101)

- **덤프**: Cosmos DB를 PaaS로 답하는 문항 셋([덤프 NO.65]은 문제문 글자로, [덤프 NO.70]·[덤프 NO.104]는 OCR 글자로)과 SaaS가 아니라고 답하는 [덤프 NO.118] 셋째 진술(답 그림)이 있다.
- **공식 문서**: Cosmos DB 소개 문서는 Cosmos DB를 완전 관리형 NoSQL·벡터 데이터베이스라고만 하고 IaaS·PaaS·SaaS 어느 것이라고도 하지 않는다. 「Shared responsibility in the cloud」의 유형별 예에도 없다.
- **처리**: 쓰지 않는다. 「완전 관리형」이라는 말만으로 PaaS라고 옮겨 적지 않는다. Cosmos DB를 서비스 유형의 예로 들지 않는다. NO.118의 나머지 두 진술(VM에 설치한 SQL Server는 PaaS가 아니다, Azure SQL Database는 PaaS다)은 공식 문서와 맞다.
- **쓰인 곳**: (쓰일 곳) 개념 글에 쓰지 않는다 — 근거 기록

## D37 — 공식 문서가 유형을 말하지 않는 서비스 — Azure Backup·Azure Files·Microsoft Intune·Site Recovery (phase 101)

- **덤프**: [덤프 NO.16] 셋째 진술 「Azure Backup은 PaaS의 예다」에 예(답 그림). [덤프 NO.262] 「Azure Files는 IaaS의 예다」에 예, 「Microsoft Intune은 SaaS의 예다」에 예(답 그림). [덤프 NO.188] 둘째 칸은 Site Recovery를 「재해 복구 서비스(DRaaS)」의 예로 고른다(답 그림, 첫 칸은 D16).
- **공식 문서**: 받은 문서 가운데 Azure Backup·Azure Files·Intune·Site Recovery의 서비스 유형을 직접 말하는 곳이 없다. 「Shared responsibility in the cloud」는 Azure Storage를 PaaS의 예로, Azure Disk Storage를 IaaS의 예로 들 뿐이다 — Azure Files가 IaaS라는 덤프의 답과 맞는지 공식 문서로 가를 수 없다. DRaaS는 이 과목이 다루는 세 유형이 아니다.
- **처리**: 쓰지 않는다. 이 넷을 서비스 유형의 예로 들지 않는다. NO.16의 앞 두 진술(SaaS는 고객이 소프트웨어 업데이트를 적용하지 않는다 — 아니요, IaaS는 쓸 소프트웨어를 고객이 설치한다 — 예)과 NO.262 둘째 진술(VM에서 실행하는 DNS 서버는 PaaS가 아니다)은 공식 문서와 맞다.

- **용어집**: 「스팟 인스턴스」라는 이름으로, 공급자가 자원을 회수할 수 있어 SLA를 「보장하기 어렵다」고 한다 — [용어집 1-12]

  (용어집이 드는 할인 폭의 수치는 Azure 제품 페이지와 맞지만, 이 과목은 할인 폭의 수치를 쓰지 않는다 — phase 100 guide 「예시 값」.)
- **처리**: 고쳐 쓴다. 개념 이름은 「Azure 스폿 가상 머신」이고, SLA는 「어렵다」가 아니라 「없다」로 쓴다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.spot-vm`, `PricingModelsTable`

## G5 — 서버리스는 오래 실행하면 비싸지는가 (phase 100)

- **용어집**: 서버리스는 장시간 실행하면 비용이 커질 수 있다고 한다 — [용어집 1-13]
- **공식 문서**: Learn 「Describe Azure Functions」는 몇 초 안에 끝나는 일에 주로 쓴다고 하고, 함수가 실행되는 동안 쓴 CPU 시간에만 요금을 매긴다고 한다. 오래 실행하면 비싸진다는 비교는 찾지 못했다.
- **처리**: 쓰지 않는다. 서버리스가 맞는 일은 공식 문서가 드는 것(이벤트에 반응해 짧게 끝나는 일, 수요가 들쭉날쭉한 일)으로만 쓴다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.serverless`

## G6 — 전력·인건비를 운영 지출의 예로 드는 것 (phase 100)

- **용어집**: 운영 지출의 예로 클라우드 사용료·유지 보수와 함께 전력·인건비를 든다 — [용어집 1-33]
- **공식 문서**: D4와 같다 — Learn과 Cloud Adoption Framework는 전력·인건비를 어느 쪽에도 넣지 않고, Azure 클라우드 컴퓨팅 사전은 오히려 이 둘을 클라우드가 없애 주는 「capital expense」에 묶는다.
- **처리**: 쓰지 않는다(D4). 클라우드 사용료가 운영 지출이라는 것은 공식 문서와 맞아 쓴다(D2).
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.capex-opex`

## G7 — 자본 지출의 「가치가 시간이 지나며 줄어든다」 (phase 100)

- **용어집**: 자본 지출로 산 장비는 투자 가치가 시간이 지나며 줄어든다고 한다 — [용어집 1-49]
- **공식 문서**: Cloud Adoption Framework 「Cost efficiency」는 운영 지출로 옮길 때 감가상각 대신 바로 받는 세금 공제를 검토하라고 권할 뿐, 이것을 자본 지출의 정의로 설명하지 않는다. Learn 단원 6에는 없다.
- **처리**: 쓰지 않는다. 감가상각·세금 같은 회계 세부는 이 주제에서 쓰지 않는다 — 자본 지출과 운영 지출은 언제·어떻게 내는가(미리 한꺼번에 대 시간에 걸쳐 계속)로만 가른다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.capex-opex`

## G8 — 운영 지출에는 「종량제 사용이 없다」 (phase 100)

- **용어집**: 「운영 비용」이라는 이름으로, 운영 지출은 필요할 때 쓰고 바로 청구되며 같은 해 세금에서 공제된다고 한 뒤, 선결제 비용과 종량제 사용이 없다고 한다 — [용어집 1-50]
- **공식 문서**: Learn 단원 6은 클라우드 서비스를 쓰는 대로 내므로 운영 지출이라 하고, 클라우드 공급자의 가격 모델을 종량제라고 한다. 곧 종량제로 내는 돈이 운영 지출의 대표 예다.
  한국어판은 이것을 「운영 지출(OpEx)」이라 쓴다. 세금 공제는 Cloud Adoption Framework가 검토 사항으로만 언급한다(G7).
- **처리**: 고쳐 쓴다. 운영 지출에는 종량제로 쓰는 만큼 내는 돈이 들어간다. 이름은 「운영 지출」로 쓴다. 세금 공제는 쓰지 않는다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-computing.capex-opex`, `azure-cloud-computing.pay-as-you-go`

## G9 — 프라이빗 클라우드는 조직이 직접 데이터 센터를 짓고 운영해야 하는가 (phase 100)

- **용어집**: 프라이빗 클라우드는 물리적으로 분리되어 보안·규제 면에서 유리하지만, 기업이 직접 서버나 데이터 센터를 구축하고 운영해야 하므로 비용이 더 들 수 있다고 한다 — [용어집 1-7]
- **공식 문서**: Learn 「Define cloud models」은 프라이빗을 사업장 안의 데이터 센터에도, 사업장 밖의 전용 데이터 센터에도 둘 수 있고 제3자가 운영할 수도 있다고 한다. 하드웨어를 사서 유지 관리·업데이트하는 일은 조직 몫이라고 비교표에 적는다.
  사전 「What is a private cloud?」도 사업장 안이나 제3자 공급자가 호스트한다고 한다. 비용이 더 든다는 것은 Learn 단원과 맞는다.
- **처리**: 한정해 쓴다. 「조직 전용 하드웨어를 조직이 사서 유지 관리한다」와 「비용이 더 든다」는 쓰고, 「데이터 센터를 반드시 직접 짓고 운영한다」는 쓰지 않는다 — 데이터 센터는 사업장 밖 제3자가 운영할 수도 있다(D11과 같은 이유).
  「물리적으로 분리」는 Learn 비교표의 「데이터가 다른 테넌트의 데이터와 같은 곳에 놓이지 않는다」와 사전의 「리소스를 다른 사용자와 나눠 쓰지 않는다」로 쓴다.
- **쓰인 곳**: (쓰일 곳) `azure-cloud-models.private-cloud`, `PublicPrivateCloudDiagram`

## G10 — 확장성의 대표 예를 자동 크기 조정으로 드는 것 (phase 101)

- **용어집**: 확장성을 트래픽이 늘면 VM 수를 늘리고 수요가 줄면 자원을 자동으로 줄이는 클라우드의 특성이라 하고, 오토 스케일링을 그 대표로 든다 — [용어집 1-15]
- **공식 문서**: Learn 「Describe the benefits of high availability and scalability in the cloud」는 확장성을 수요에 맞춰 리소스를 조정하는 능력이라 하고, 수평 크기 조정을 자동으로도 수동으로도 한다고 한다.
  사전 「What is elasticity in cloud computing?」은 확장성은 용량에 관한 것, 수요에 맞춘 **자동**·실시간 조정은 탄력성이라고 가르고, 「What are business continuity, …」도 리소스를 더하고 빼는 능력(확장성)과 그것을 빨리 하는 능력(탄력성)을 나눈다.
  같은 덤프의 [덤프 NO.115]도 자동 크기 조정을 탄력성의 예로 답한다.
- **처리**: 한정해 쓴다. 확장성은 「수요에 맞춰 리소스를 늘리고 줄이는 능력(자동이나 수동)」으로 쓰고, 자동 크기 조정을 확장성의 대표 예로 들지 않는다. 「수요가 바뀌는 그때그때 자동으로」는 탄력성을 가르는 말로 쓴다.
  이름은 「클라우드 확장성」이 아니라 Microsoft 한국어 문서의 「확장성」이다.
- **쓰인 곳**: `azure-cloud-benefits.scalability`, `azure-cloud-benefits.elasticity`

## G11 — 고가용성의 「빠른 복구」와 「대부분 SLA 99.9% 이상」 (phase 101)

- **용어집**: 고가용성을 시스템이 장애가 나도 빠르게 복구하거나 장애 조치하는 능력이라 하고, 대부분의 클라우드 서비스가 SLA로 99.9% 이상을 보장한다고 한다 — [용어집 1-16]
- **공식 문서**: Learn 「Describe the benefits of high availability and scalability in the cloud」는 고가용성을 어떤 중단이나 사건이 생기든 가용성을 가장 높게 지키는 데 초점을 둔 것이라 하고, Azure의 가동 시간 보장은 서비스마다 다르며 SLA에 담긴다고 한다.
  장애에서 회복해 계속 동작하는 능력은 Learn 「Describe the benefits of reliability and predictability in the cloud」가 **안정성**으로 정의한다. 「대부분 99.9% 이상」은 받은 문서 어디에도 없다 — 「What are business continuity, …」의 99.9%는 가동 시간 요구의 예일 뿐이다.
- **처리**: 고쳐 쓴다. 고가용성은 「쓸 수 있는 시간을 가장 길게 지키는 것」으로 쓰고, 「장애에서 회복하는 능력」은 안정성에 둔다. SLA 수치는 쓰지 않는다(guide 「배경」 — 서비스마다의 SLA 수치를 쓰지 않는다).
- **쓰인 곳**: `azure-cloud-benefits.high-availability`, `azure-cloud-benefits.reliability`

## G12 — 신뢰성을 「예측 가능한 성능」으로 정의하는 것 (phase 101)

- **용어집**: 신뢰성을 시스템이 예측 가능한 성능으로 안정적으로 동작하는 능력이라 하고, 클라우드가 보안 패치 등을 자동으로 적용해 가동 시간을 최대로 한다고 한다 — [용어집 1-17]
- **공식 문서**: Learn 「Describe the benefits of reliability and predictability in the cloud」는 안정성을 시스템이 장애에서 회복해 계속 동작하는 능력이라 정의하고, 성능을 내다보는 것은 같은 단원의 성능 예측 가능성으로 따로 둔다.
  패치가 자동으로 적용되는 것은 Learn 「Describe the benefits of security and governance in the cloud」가 **운영 모델에 따라** 그렇다고 하며 보안·거버넌스의 이점으로 든다(IaaS면 운영 체제와 설치한 소프트웨어의 패치를 쓰는 쪽이 관리한다).
- **처리**: 고쳐 쓴다. 안정성은 「장애에서 회복해 계속 동작하는 능력」으로 쓴다. 「예측 가능한 성능」은 예측 가능성에, 패치의 자동 적용은 「운영 모델에 따라」로 한정해 보안과 거버넌스에 둔다. 이름은 「신뢰성」이 아니라 Microsoft 한국어 문서의 「안정성」이다.
- **쓰인 곳**: `azure-cloud-benefits.reliability`, `azure-cloud-benefits.predictability`, `azure-cloud-benefits.security-governance`

## G13 — 일관된 보안 — 「고객은 애플리케이션 계층이나 데이터 암호화만」 (phase 101)

- **용어집**: 클라우드가 전 세계 데이터 센터에 표준화된 보안 정책을 적용하므로, 고객은 애플리케이션 계층이나 데이터 암호화만 잘 관리하면 되고 그 밑의 인프라는 공급자가 패치·점검한다고 한다 — [용어집 1-19]
- **공식 문서**: Learn 「Describe the benefits of security and governance in the cloud」는 IaaS를 쓰면 운영 체제와 설치한 소프트웨어의 패치·유지 관리를 쓰는 쪽이 맡고, 패치를 맡기고 싶으면 PaaS나 SaaS가 낫다고 한다 — 쓰는 쪽이 맡는 범위는 서비스 유형에 따라 다르다.
  VM 안의 패치를 쓰는 쪽이 관리한다는 것은 phase 100의 G1과 같다. 「표준화된 보안 프레임워크를 모든 데이터 센터에」라는 말은 받은 문서에 없다.
- **처리**: 고쳐 쓴다. 쓰는 쪽이 맡는 보안의 범위는 서비스 유형에 따라 다르다고 쓴다(IaaS면 운영 체제와 소프트웨어의 패치까지). 「일관된 보안」이라는 이름과 「모든 데이터 센터에 표준화된 보안」은 쓰지 않는다 — Learn 단원의 이름은 「보안과 거버넌스」(한국어판 「보안 및 거버넌스」)다.
- **쓰인 곳**: `azure-cloud-benefits.security-governance`

## G14 — 예측 가능 비용의 「일정 규모 이상」과 관리 효율성의 「백업 간소화」 (phase 101)

- **용어집**: 사용량에 따른 과금 구조가 투명해 일정 규모 이상 쓰면 예상 비용을 비교적 정확히 낼 수 있다고 하고 — [용어집 1-18], 관리 효율성 덕분에 장애 감지·모니터링·백업이 간소해진다고 한다 — [용어집 1-21]
- **공식 문서**: Learn 「Describe the benefits of reliability and predictability in the cloud」의 비용 예측 가능성은 리소스 사용을 실시간으로 추적·모니터링하고 분석과 Azure 가격 계산기로 비용을 내다보는 것이다. 사용 규모에 따라 정확도가 달라진다는 말은 없다.
  Learn 「Describe the benefits of manageability in the cloud」의 관리 효율성은 클라우드 관리(자동 크기 조정·템플릿 배포·상태 모니터링과 실패한 리소스 교체·지표 경고)와 클라우드에서의 관리(웹 포털·CLI·API·PowerShell) 둘이고, 백업은 들지 않는다.
- **처리**: 한정해 쓴다. 비용 예측 가능성과 관리 효율성은 Learn 단원이 드는 것만 쓴다. 「일정 규모 이상」과 관리 효율성의 예로서의 「백업」은 쓰지 않는다.

## G15 — SLA가 보장하는 것, 크레딧 「환급」, 곱한 SLA (phase 101)

- **용어집**: SLA를 클라우드 공급자가 가용성·성능·지원 수준 등을 보장하는 계약이라 하고, 99.9% 가용성에 못 미치면 서비스 크레딧을 환급해 준다는 예를 들며, 여러 서비스를 엮은 아키텍처의 실효 SLA는 곱셈으로 셈해야 한다고 한다 — [용어집 1-35]
- **공식 문서**: Well-Architected 「Architecture strategies for defining reliability targets」는 Azure SLA를 가동 시간과 연결에 대한 Microsoft의 약속이라 하고, SLA에 크레딧을 받는 절차가 들어 있다고 한다.
  「How to read a service-level agreement (SLA)」는 대부분의 SLA가 가동 시간·가용성을 약속하고 성능·복구 시간·데이터 내구성을 약속하는 것도 있다고 하며(지원 수준은 들지 않는다), 크레딧은 보통 저절로 주어지지 않고 고객이 청구해야 한다고 하고(D24),
  SLA를 곱한 복합 SLA는 서비스가 서로 따로 멈춘다고 가정한 대략의 상한일 뿐이라 믿을 수 없다고 한다. Cloud Adoption Framework 「Protect your cloud estate」는 중요 경로의 SLA를 곱해 복합 SLA를 어림하라고 한다.
- **처리**: 한정해 쓴다. Azure SLA가 약속하는 것은 Well-Architected 문서대로 가동 시간과 연결로 쓴다. 「지원 수준」과 「99.9% 미달 시」라는 수치는 쓰지 않는다. 크레딧은 D24대로 쓴다.
  곱셈은 Cloud Adoption Framework대로 쓰되 SLA 읽는 법 문서의 한계(서로 따로 멈춘다는 가정, 대략의 상한)를 함께 쓴다 — 곱한 값을 Microsoft가 약속하는 SLA처럼 쓰지 않는다.
- **쓰인 곳**: `azure-sla-lifecycle.sla`, `azure-sla-lifecycle.service-credit`, `azure-sla-lifecycle.composite-sla`

## G16 — 99.9% SLA는 한 달 중단을 수십 분으로 제한하나 (phase 101)

- **용어집**: 업타임을 SLA를 재는 지표라 하고, 99.9% SLA는 한 달 다운타임이 수십 분 안으로 제한된다는 뜻이라고 한다 — [용어집 1-22]
- **공식 문서**: Well-Architected 지표 문서의 표는 99.9%를 한 달 중단 시간으로 바꾸면 약 43.2분이라 하고, 「What are business continuity, high availability, and disaster recovery?」도 약 43분이라 한다 — 셈은 맞다.
  그러나 「How to read a service-level agreement (SLA)」는 99.9% SLA가 서비스를 늘 쓸 수 있다는 보장도, 그만큼만 멈춘다는 뜻도 아니며, 무엇을 중단으로 셀지는 SLA의 정의가 정한다고 한다. SLA는 그 수준에 못 미쳤을 때 고객이 보상을 받는 조건부 약속이다.
- **처리**: 한정해 쓴다. 99.9%를 한 달 약 43분으로 바꾸는 셈은 예시 값으로 쓸 수 있다. 「SLA가 중단을 그만큼으로 제한한다(막아 준다)」고는 쓰지 않는다.
- **쓰인 곳**: `azure-sla-lifecycle.sla`

## G17 — PaaS에서 개발자는 「코드 작성에만」 집중하는가 (phase 101)

- **용어집**: PaaS는 런타임·데이터베이스·웹 서버 같은 플랫폼을 통째로 주고, 개발자는 코드 작성에만 집중하며 인프라 관리와 패치는 클라우드가 맡는다고 한다 — [용어집 1-4]
- **공식 문서**: Learn 「Describe cloud service types」 단원 3은 PaaS에서 고객이 앱 코드·데이터·액세스 제어에 집중하고, 서비스 구성에 따라 일부 네트워크·앱 보안 설정은 함께 맡는다고 한다. 「Shared responsibility in the cloud」의 책임 표에서도 PaaS의 애플리케이션·네트워크 제어는 함께 맡는 것이고, 고객 데이터·구성과 설정·ID와 사용자는 고객 몫이다.
  운영 체제·데이터베이스의 라이선스와 패치를 고객이 신경 쓰지 않는다는 것(단원 3)과 PaaS에 운영 체제·런타임·데이터베이스·미들웨어가 들어 있다는 것(PaaS 사전)은 맞다.
- **처리**: 한정해 쓴다. 공급자가 플랫폼과 그 패치를 맡는다는 것은 쓴다. 「코드 작성에만」은 쓰지 않고, 고객이 앱 코드와 함께 데이터·액세스 제어를 맡고 일부 보안 설정을 함께 맡는다고 쓴다.
- **쓰인 곳**: `azure-service-types.paas`

## G20 — 「Azure 리전」이라는 표기와 「다른 리전으로 페일오버해 고가용성」 (phase 102)

- **용어집**: 지역을 「Azure 리전」으로 적고, 데이터 센터가 있는 지리적 구역이라 한다. 리전을 골라 배포하면 지연 시간이나 규제 요구를 맞출 수 있고, 장애 때 다른 리전으로 페일오버를 설정해 고가용성을 얻는다고 하며, 예로 한국 중부·한국 남부를 든다 — [용어집 2-1]
- **공식 문서**: Learn 단원 5 한국어판과 「What are Azure regions?」 한국어판은 region을 「지역」, failover를 「장애 조치」로 옮긴다(phase 101 표기와 같다). 지역을 고를 때 대기 시간과 데이터 상주를 따진다는 것은 「What are Azure regions?」와 맞다.
  「Azure region pairs and nonpaired regions」는 짝 지역에 배포하는 것만으로는 장애 조치가 저절로 생기지 않고 고가용성과 재해 복구 계획은 고객이 세운다고 하며, 「What are Azure regions?」는 여러 지역을 함께 쓰면 여러 장애에 견디고 재해 복구의 선택지가 많아진다고 한다. 「What are availability zones?」는 운영 워크로드가 먼저 여러 가용성 영역을 쓰게 하라고 한다.
- **처리**: 고쳐 쓴다. 이름은 「지역」·「장애 조치」로 쓴다. 다른 지역으로의 장애 조치는 고객이 설계하고 구성하는 것이고 지역 전체의 중단에 대비하는 쪽(재해 복구)으로 쓴다 — 한 지역 안의 장애에는 가용성 영역이 먼저다. 실제 지역 이름(한국 중부·한국 남부)은 예로 들지 않는다(guide 「예시 값」 — 이름표를 쓴다).
- **쓰인 곳**: (쓰일 곳) `azure-regions-zones.region`, `azure-regions-zones.region-pairs`

## G21 — 지역 쌍: 「각 리전을 보통 쌍으로 묶는다」와 「복구를 자동화한다」 (phase 102)

- **용어집**: Azure가 각 리전을 보통 쌍으로 묶어 재해 복구와 백업에 대비하고, 한 리전이 다운되어도 같은 쌍의 다른 리전에서 서비스를 복구하도록 자동화한다고 한다. 예로 미국 동부와 미국 서부를 든다 — [용어집 2-2]
- **공식 문서**: 「Azure region pairs and nonpaired regions」(2026-10-15)는 Microsoft가 **일부** 지역을 짝짓고 짝이 없는 지역도 많다고 하며, 「What are Azure regions?」는 새 지역 다수가 짝이 없다고 한다. 같은 문서는 짝 지역에 두는 것만으로 장애 조치가 저절로 생기지 않고, Microsoft가 관리하는 짝 사이 장애 조치를 주된 재해 복구 방법으로 삼지 말라고 한다. Learn 단원 5도 모든 서비스가 저절로 복제·장애 조치하지는 않아 고객이 복구와 복제를 구성한다고 한다.
  미국 동부와 미국 서부가 서로의 짝이라는 것은 짝 목록과 맞다.
- **처리**: 고쳐 쓴다. 「Microsoft가 일부 지역을 짝지어 둔다」, 「짝에 두는 것만으로 저절로 장애 조치되지 않고 복구와 복제는 고객이 구성한다」로 쓴다. 짝의 예(미국 동부·미국 서부)는 쓸 수 있다.
- **쓰인 곳**: (쓰일 곳) `azure-regions-zones.region-pairs`

## G22 — 데이터 센터 「전 세계 수백 개」와 「지역 환경에 최적화」 (phase 102)

- **용어집**: Azure가 전 세계 수백 개의 데이터 센터를 네트워크로 이어 서비스를 제공하고, 지역 환경(전력·날씨)에 최적화된 인프라로 높은 안정성과 효율을 유지한다고 한다 — [용어집 2-5]

- **쓰인 곳**: (쓰일 곳) `azure-regions-zones.datacenter`

## G23 — 데이터 주권에 「소버린 리전이 대응한다」 (phase 102)

- **용어집**: 데이터 주권을 특정 국가·지역 법규에 따라 데이터의 저장 위치와 이동을 제한하는 것이라 하고, 금융·공공 분야는 지역 안의 데이터 센터를 요구하기도 해 리전 선택이 중요하며, 소버린 리전이 이에 대응한다고 한다 — [용어집 1-25]
- **공식 문서**: 「What are Azure regions?」는 지리마다 데이터 상주 경계가 있고 데이터 상주 요구가 있으면 그 지리 안의 지역을 고르라고 한다. 같은 문서는 일부 지역이 소버린 클라우드 지리에 속해 데이터 상주 규제가 엄격한 특정 지역의 고객이 쓴다고 한다. Learn 단원 5는 소버린 지역을 규정 준수나 법적 이유로 쓰는, 주 Azure와 떨어진 인스턴스라 한다.
  「What are availability zones?」는 데이터 상주나 주권 요구로 한 지역에 묶인 워크로드가 여러 가용성 영역을 쓰라고 한다 — 그런 요구가 보통 지역에서도 맞춰진다는 뜻이다. 금융·공공 분야에 대한 말은 받은 문서에 없다.
- **처리**: 한정해 쓴다. 데이터를 둘 곳에 대한 요구는 먼저 지리 안의 지역을 고르는 것으로 맞춘다고 쓰고, 소버린 지역은 규정 준수·법적 이유로 쓰는 따로 떨어진 인스턴스로 쓴다 — 「데이터 주권 요구 = 소버린 지역」으로 잇지 않는다. 금융·공공 분야의 예는 쓰지 않는다.
- **쓰인 곳**: (쓰일 곳) `azure-regions-zones.region`, `azure-regions-zones.sovereign-regions`

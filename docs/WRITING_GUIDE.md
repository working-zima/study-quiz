# 개념 글 작성 기준

개념의 요약·본문과 문항의 문제문·해설을 쓰거나 고칠 때 따르는 기준이다. 사용자가 2026-10-27 정했다(ADR-056).
네트워크 과목과 Azure 과목의 글은 모두 이 기준을 따른다(Azure는 ADR-060). AWS 과목의 기존 글은 소급해 고치지 않는다 — 새로 쓰거나 고치는 글만 따른다.

이 기준은 **문장을 어떻게 쓸지**를 정한다. **무엇을 쓸지**(사실)는 여전히 각 과목의 출처 규칙이 정한다 — 원본에 없는 사실을 지어내지 않고,
원본 문장을 옮기지 않으며(ADR-009), 원본이 틀렸으면 과목의 기준 출처대로 고친다(네트워크는 표준 — ADR-055, Azure는 Microsoft 공식 문서 — ADR-060). 아래 「기술적 정확성」은 그 규칙과 같은 말이다.

아래 1~6절, 「맥락을 생략하지 마라」 절, 「객관식 문제의 문장과 선택지 구성 원칙」 절은 사용자가 준 기준을 그대로 옮긴 것이다(말투도 그대로 두었다).
「나쁜 예」로 든 문장은 phase 69가 쓴 요약문과 문항 n011의 문제문이다. 객관식 절은 4지선다에 쓰고, 그 2·3·6·7항(자연스러운 문장, 이해와 판단의 구별,
불필요한 정보 제거, 정답의 명확성)은 예/아니요 문항(ADR-054)에도 쓴다.

## 1. 가장 중요한 목표

개념을 처음 접하는 비전공자가 읽었을 때, 별도의 검색이나 추가 설명 없이도 해당 개념이 무엇인지 직관적으로 이해할 수 있어야 해.

단순히 기술적으로 정확한 정의를 작성하는 것이 아니라, 독자가 머릿속으로 실제 동작과 역할을 떠올릴 수 있도록 설명하는 것이 목표야.

설명의 우선순위는 다음과 같아.

1. 직관적으로 이해할 수 있는가?
2. 기술적으로 정확한가?
3. 비슷한 개념과 구별할 수 있는가?
4. 실제 상황에서 어떻게 사용되는지 이해할 수 있는가?

단, 쉽게 설명한다는 이유로 사실을 왜곡하거나 중요한 개념을 생략해서는 안 돼.

## 2. 제목 바로 아래의 한 줄 설명

모든 개념은 제목 바로 아래에 핵심을 요약한 한 문장을 작성해. (이 앱에서는 개념의 `summary`다.)

이 한 문장은 가장 중요해.

독자가 본문을 읽지 않고 제목과 한 문장만 읽어도 해당 개념이 무엇인지 대략적인 감을 잡을 수 있어야 해.

### 작성 원칙

* 사전적인 정의보다 직관적인 이해를 우선해.
* 가능하면 이미 알고 있는 일상적인 개념으로 설명해.
* 무엇이며, 어떤 역할을 하는지 명확하게 알려 줘.
* 개념의 중요한 특징이나 동작이 자연스럽게 드러나도록 작성해.
* 불필요하게 추상적인 표현은 사용하지 마.
* 다른 전문용어를 알아야 이해되는 설명은 피해야 해.
* 해당 개념의 명칭만 반복하는 순환적인 정의를 작성하지 마.
* 짧고 명확한 한 문장으로 작성하되, 글자 수를 줄이기 위해 이해하기 어려운 문장을 만들지는 마.

### 예시

**네트워크 장비**

나쁜 예:
호스트 사이에서 메시지를 받아 다음 노드로 넘겨주는 중간 노드다.

좋은 예:
컴퓨터나 휴대폰이 보낸 데이터가 목적지까지 도착하도록 중간에서 전달해 주는 장치다.

**트래픽**

나쁜 예:
일정 시간 동안 네트워크 안을 흐르는 정보의 양이다.

좋은 예:
인터넷이나 네트워크를 통해 오가는 데이터의 양을 말하며, 한꺼번에 많이 몰리면 통신이 느려질 수 있다.

**처리율**

나쁜 예:
일정한 시간 동안 네트워크로 실제 전달을 마친 데이터의 양이다.

좋은 예:
네트워크를 통해 실제로 전달된 데이터의 양으로, 보통 1초 동안 얼마나 많은 데이터를 전송했는지로 나타낸다.

핵심은 설명을 짧게 만드는 것이 아니라, 처음 접하는 사람도 의미를 바로 이해할 수 있게 만드는 거야.

## 3. 본문 설명

한 줄 설명을 통해 직관적으로 이해했다면, 본문에서는 그 개념을 더 정확하고 깊이 있게 이해할 수 있도록 설명해.

본문은 다음 흐름을 권장해.

1. **개념**: 무엇을 의미하는가?
2. **원리**: 어떻게 동작하는가?
3. **예시**: 실제로 어떤 상황에서 사용되는가?
4. **특징**: 다른 개념과 구별되는 핵심적인 특징은 무엇인가?

다만 모든 개념에 이 네 가지를 억지로 적용하지는 마. 해당 개념을 이해하는 데 필요한 내용만 자연스럽게 설명해.

### 본문 작성 원칙

* 독자가 처음 배우는 사람이라고 가정해.
* 새로운 전문용어가 등장하면 그 의미를 함께 설명해.
* 하나의 개념을 설명하기 위해 여러 개의 새로운 개념을 동시에 도입하지 마.
* 이미 설명한 내용을 표현만 바꿔 반복하지 마.
* 「바로 다음 개념에서 다룬다」처럼 글의 진행만 알리는 문장은 쓰지 마. 뒤에서 자세히 다룰 용어가 지금 필요하면 그 자리에서 한 줄로 풀고 넘어가.
* 단순한 정의의 나열보다 원인과 결과가 연결되는 설명을 작성해.
* 필요한 경우 일상적인 사례를 활용하되, 비유가 실제 기술적 동작과 다르다면 그 차이를 밝혀 줘.
* 기술적으로 정확하더라도 지나치게 복잡한 설명은 학습 단계에 맞게 나누어 설명해.

## 4. 비슷한 개념과의 차이

초보자가 혼동하기 쉬운 개념은 서로 어떤 차이가 있는지 명확히 설명해.

예를 들어 트래픽, 전송 속도, 처리율, 대역폭은 모두 네트워크에서 데이터의 양이나 속도와 관계가 있어.

따라서 각각의 정의만 알려 주면 독자는 모두 비슷한 개념이라고 생각하기 쉬워.

이런 경우에는 각 개념이 무엇을 측정하거나 표현하는지, 어떤 상황에서 구별해서 사용하는지 설명해.

단순히 A는 무엇이고 B는 무엇이라고 반복하기보다는 왜 서로 다른 개념으로 구분하는지 이해할 수 있어야 해.

## 5. 기술적 정확성

쉽게 설명하는 것만큼 중요한 것이 정확성이야.

* 이해를 돕기 위해 사실과 다른 설명을 만들지 마.
* 특정 상황에서만 성립하는 내용을 일반적인 사실처럼 설명하지 마.
* 정확한 정의와 직관적인 설명이 다를 수 있다면 본문에서 그 차이를 설명해.
* 기술적으로 잘못된 내용이 원문에 있다면 그대로 유지하지 말고 수정해.
* 확실하지 않은 부분은 임의로 추측하지 말고 별도로 알려 줘.

## 6. 최종 검토

작성한 모든 설명을 다음 기준으로 다시 검토해.

1. 제목과 첫 문장만 읽어도 개념이 무엇인지 이해할 수 있는가?
2. 첫 문장을 이해하기 위해 다른 전문용어를 공부해야 하지는 않는가?
3. 본문을 읽으면 실제로 어떻게 동작하는지 떠올릴 수 있는가?
4. 비슷한 개념과의 차이를 이해할 수 있는가?
5. 기술적으로 틀리거나 지나치게 단순화한 설명은 없는가?
6. 초보자에게 불필요하게 어려운 표현이나 반복되는 문장은 없는가?

어느 하나라도 충족하지 못한다면 다시 작성해.

**최종 목표는 독자가 개념을 단순히 암기하는 것이 아니라, 이해한 내용을 자기 말로 설명할 수 있게 만드는 것이야.**

## 초보자가 이해하는 데 필요한 맥락을 생략하지 마.

가장 중요하게 지켜야 할 원칙 중 하나는 독자가 아직 배우지 않은 내용을 이미 알고 있다고 가정하지 않는 거야.

특히 어떤 동작이나 현상을 설명할 때는 그 동작이 이루어지는 상황을 독자가 머릿속에 그릴 수 있도록 작성해.

### 나쁜 설명의 예시

**패킷 손실**

보내고 받는 과정에서 잃어버린 패킷의 정도로, 보통 백분율로 나타낸다.

이 설명은 초보자에게 적합하지 않아.

독자는 무엇을 보내고 받는 것인지, 누가 누구에게 보내는 것인지, 패킷이 무엇인지조차 알지 못할 수 있기 때문이야.

### 좋은 설명의 예시

**패킷 손실**

컴퓨터가 네트워크를 통해 다른 컴퓨터에 데이터를 보낼 때, 작은 데이터 묶음인 패킷 일부가 목적지에 도착하지 못하는 현상이다.

이 설명은 누가, 무엇을, 어디로 보내는 상황에서 어떤 문제가 발생하는지를 알려 줘.

### 반드시 지켜야 할 작성 원칙

1. **행위의 주체를 생략하지 마.**
   * 누가 또는 무엇이 해당 동작을 수행하는지 알 수 있어야 해.
2. **행위의 대상을 명확하게 설명해.**
   * 무엇을 보내고, 받고, 저장하고, 처리하는지 구체적으로 밝혀 줘.
3. **동작이 이루어지는 상황을 알려 줘.**
   * 어디에서 어디로 이동하는지, 어떤 상황에서 발생하는지 이해할 수 있어야 해.
4. **추상적인 표현에 의존하지 마.**
   * '보내고 받는 과정', '데이터를 처리하는 방식', '정보를 전달하는 구조' 같은 표현만으로 설명을 끝내지 마.
   * 누가 무엇을 어떻게 하는지 구체적으로 설명해.
5. **독자가 모르는 개념으로 다른 개념을 설명하지 마.**
   * 새로운 전문용어가 반드시 필요하다면, 그 의미를 짧게 풀어 설명해.
   * 특히 제목에 포함된 전문용어를 본문에서 그대로 반복하는 것으로 정의를 대신하지 마.
6. **개념을 이해하는 데 필요한 정보와 부가 정보를 구분해.**
   * 정의의 첫 문장에서는 해당 개념이 무엇인지 이해시키는 데 집중해.
   * 계산 방법, 측정 단위, 세부 분류처럼 부가적인 정보는 필요한 경우 본문에서 설명해.
7. **맥락을 보충하되 불필요하게 장황하게 만들지 마.**
   * 모든 문장에 누가, 무엇을, 어디로, 어떻게를 기계적으로 나열할 필요는 없어.
   * 다만 그중 하나가 빠져 독자가 상황을 이해할 수 없다면 반드시 보완해야 해.

### 최종 검토 기준

설명을 완성했다면 처음 배우는 사람의 입장에서 다음을 확인해.

* 누가 무엇을 하는지 알 수 있는가?
* 어떤 대상에 어떤 일이 발생하는지 알 수 있는가?
* 어떤 상황에서 등장하는 개념인지 떠올릴 수 있는가?
* 설명에 등장하는 단어를 이해하기 위해 또 다른 설명을 찾아봐야 하는가?
* 개념의 의미보다 부가적인 정보가 먼저 등장하지는 않는가?

**무엇보다 독자가 알아서 빈칸을 채워야만 이해할 수 있는 설명을 작성하지 마.**

설명하는 사람이 알고 있다는 이유로 생략한 정보가, 처음 배우는 사람에게는 개념을 이해하는 데 가장 중요한 정보일 수 있다는 사실을 항상 고려해.

## 객관식 문제의 문장과 선택지 구성 원칙

객관식 문제를 출제할 때는 독자가 질문을 쉽게 이해하면서도, 정답을 선택하기 위해 개념을 생각하도록 만들어야 해.

특히 다음 사항을 지켜 줘.

### 1. 교재의 정의를 그대로 문제로 만들지 마.

교재에 작성된 정의에서 개념의 이름만 제거하고 끝에 '무엇인가?'를 붙이는 방식은 지양해.

이런 방식은 개념을 이해했는지보다 특정 문장을 암기했는지 평가하기 쉬워.

개념의 특성에 따라 실제 상황을 제시하거나, 동작 원리를 묻거나, 개념 간 차이를 판단하는 문제를 만들어 줘.

### 2. 실제 사람이 질문하는 것처럼 자연스럽게 작성해.

다음과 같은 문장은 피해야 해.

"실제로 잰 값도, 넘을 수 없는 최대치도 아니라 그 네트워크에서 기대할 수 있는 빠르기를 bps·Mbps·Gbps 같은 초당 비트 수로 나타낸 지표는?"

이 문장은 지나치게 압축적이고, 일상적으로 사용하지 않는 표현이 많아.

문제를 작성한 후 실제 사람이 다른 사람에게 질문한다고 생각하고 문장을 검토해.

소리 내어 읽었을 때 어색하거나, 한 번 읽어서 이해하기 어렵다면 다시 작성해.

### 3. 질문을 이해하는 과정과 정답을 판단하는 과정을 구별해.

독자가 문제를 읽고 무엇을 묻는지 이해하는 것은 쉬워야 해.

반면 정답을 선택하는 과정에서는 학습한 개념을 떠올리고 판단할 필요가 있어야 해.

즉, 질문 자체를 어렵게 작성해서 난이도를 높이지 마.

### 4. 선택지 사이의 차이를 명확하게 만들어.

정답과 오답은 기술적으로 구별할 수 있어야 해.

서로 비슷한 개념을 선택지에 포함하는 것은 괜찮지만, 그 차이를 판단할 수 있는 충분한 조건을 문제에 제시해야 해.

교재에서 임의로 구분한 표현이나 특정 문장의 암기 여부에 따라 정답이 달라지는 문제는 만들지 마.

정답이 둘 이상으로 해석될 수 있다면 문제나 선택지를 수정해.

### 5. 개념에 적합한 질문 방식을 선택해.

모든 문제를 같은 형식으로 출제하지 마.

개념의 특징과 학습 목표에 따라 다음 중 적합한 방식을 선택해.

* 개념 확인: 개념의 의미를 이해했는지 확인
* 원리 이해: 어떤 방식으로 동작하는지 확인
* 상황 적용: 실제 상황에서 해당 개념을 적용할 수 있는지 확인
* 개념 비교: 비슷한 개념을 정확하게 구별할 수 있는지 확인
* 원인과 결과: 특정 현상이 발생하는 이유와 결과를 이해했는지 확인

문제 유형을 다양하게 만드는 것 자체가 목표는 아니야. 학습하려는 개념에 가장 적합한 질문을 선택하는 것이 중요해.

### 6. 불필요한 정보는 제거해.

문제에 등장하는 모든 정보는 질문의 상황을 이해하거나 정답을 판단하는 데 도움이 되어야 해.

정답을 판단하는 데 필요하지 않은 전문용어, 수치, 조건, 부정문을 불필요하게 나열하지 마.

단, 실제 문제 해결 능력을 평가하기 위해 필요한 조건이나 정보까지 제거해서는 안 돼.

### 7. 정답의 명확성을 검증해.

객관식 문제를 완성한 후 반드시 다음을 확인해.

1. 질문을 한 번 읽으면 무엇을 묻는지 이해할 수 있는가?
2. 문장을 해석하는 과정에서 불필요한 추론이 필요한가?
3. 정답을 선택하는 데 필요한 정보가 충분한가?
4. 정답이 기술적으로 명확하며 다른 선택지도 정답이 될 여지는 없는가?
5. 오답이 단순히 엉뚱한 내용이 아니라, 실제로 혼동할 수 있는 개념을 바탕으로 구성되었는가?
6. 교재의 문장을 암기하지 않았더라도 개념을 이해했다면 풀 수 있는가?

**가장 중요한 원칙은 질문은 쉽게 이해할 수 있도록, 선택은 충분한 생각이 필요하도록 만드는 것이야.**
